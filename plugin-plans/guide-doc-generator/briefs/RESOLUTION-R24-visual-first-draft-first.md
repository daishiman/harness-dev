# RESOLUTION R24 — 図解優先・たたき台優先への方針転換

- 起点: 利用者フィードバック 2026-08-18 (`/handout-build` の初回実走の直後)
- 影響コンポーネント: C01 / C05 / C07 / C12
- 追加した正本: `plugins/guide-doc-generator/config/handout-visual-policy.json`
  (plan 側の同内容表現は `briefs/config/handout-visual-policy.json`)
- 参照実物: `plugins/guide-doc-generator/examples/reference/claude-guide-v2.html`
  と、その実測記録 `plugins/guide-doc-generator/examples/granularity-anchor.md`

## 指摘された 3 点

| # | 指摘 | 現象 |
|---|---|---|
| 1 | 成果物が出るまでが遅すぎる | 必須項目を 1 問ずつ確定してから設計に入るため、初回 HTML までの往復が項目数に比例した |
| 2 | 文章が長すぎて読む気が起きない | 部品の中に段落が入り、カード 1 枚が 100 文字超になった |
| 3 | 図解がない | 初回実走の成果物は概念図解 0 枚。関係の説明がすべて散文へ逆流した |

3 は 2 の原因でもある。**長文が生まれる箇所は、たいてい図解にできる関係を文章で
代用している箇所**である。順序・分岐・2 軸の位置づけは並べるだけでは出せないため、
図解を持たない資料は必ずその分を散文で払う。

## 裁定

### D1. 図解の下限を機械検査へ載せる (C12)

推奨として prompt に書くだけでは、締切のある生成で必ず散文へ退化する。閾値を
`handout-visual-policy.json#thresholds` に置き、C12 が警告として発火する。

| コード | 意味 |
|---|---|
| `W-VISUAL-ABSENT` | main セクションに目で形が分かる部品が無い |
| `W-DIAGRAM-FEW` | 概念図解が main セクション数に対して不足 |
| `W-TEXT-HEAVY` | セクション内の部品の過半が TEXT |
| `W-TEXT-RUN` | TEXT が連続し、画面上 1 つの長文と区別が付かない |

error ではなく warning とする理由: 値域の縛りを error にすると既存の構成データと
最小例が一斉に落ちる。**「警告 0 件で完了」という強制は C01 のゴールシーク完了
チェックリスト側が持つ**。層を分けることで、機械検査の互換性を壊さずに編集方針
だけを厳しくできる。

### D2. 文字量の上限を役割ごとに持つ (C12)

総量ではなく **1 部品あたり** で縛る。資料が読まれない原因は総量ではなく、1 つの
カードに段落が入っていることである。上限は参照実物の実測値から引いた
(`examples/granularity-anchor.md` に n・中央値・p90・最大の記録がある)。

### D3. たたき台優先 (C01 / C07)

速さは「質問を減らすこと」ではなく **「確定を待たずに一度出すこと」** で得る。

- 素材から読み取れる項目は読み取って仮置きし、読み取れない項目だけを **1 回**の
  質問へまとめる
- 初回は `overview` 粒度で出す。粒度を上げるのは利用者が現物を見て指した箇所だけ
- 仮置きした項目は生成レポートで一覧にする。構成データ側には印を持たせない
  (provenance は C12 の閉じた語彙であり、推定の別を持つ層ではない)
- 第 1 稿では挿絵生成 (C21) と可読性レビュー (C03) を回さない。決定論ゲート
  (C16/C17/C18/C22) は数百ミリ秒で終わるので外さない

### D4. 粒度の基準点を実物で持つ (C05)

「サンプルと同じ粒度で」を散文の指示に留めず、参照実物の実測値として持つ。
数値の正本は `handout-visual-policy.json`、由来の記録は `examples/granularity-anchor.md`。

参照実物には概念図解が無い (マスコットと装飾 SVG だけ) ため、本 plugin の基準点は
**「参照実物の文字量 + 概念図解」** とする。文字量は参照実物のとおり、図解は
参照実物に無いものを足す。

### D5. 粒度は用途によらず一定・網羅より取捨選択 (C01 / C05 / C23)

利用者の追補 (2026-08-18): 「どの資料でも同様の粒度で。情報を入れすぎず必要な情報だけに
絞る。漏れなく全て表現するより、要点を絞って文章ではなく箇条書きで簡潔に」。

- **粒度は doc_type ごとの裁量ではない**。用途プリセットが変えるのはセクションの順序と
  推奨部品であって、1 部品あたりの情報量ではない。C23 の `granularity_defaults` は
  「説明の詳しさ」を決めるものであり、載せる項目数を増やす根拠にしない。
- **選別は書き手の仕事**。全部載せた資料は読み手にとって「どれが大事か分からない資料」
  になる。素材の項目数と資料の項目数は一致しなくてよい。
- **散文は最後の手段**。関係は図解、列挙は箇条書き・カード・表。散文が要るのは、形にした
  項目どうしの関係を説明するときだけ。
- 落とした項目は生成レポートで「載せなかった」と明示する。黙って消さない。付録は網羅欲の
  逃がし先ではない。

正本は `handout-visual-policy.json#content_selection`。この原則自体は機械検査しない
(「要点か否か」は値域で判定できない)。代理指標として `micro_copy` と `thresholds` が
発火し、強制は D1 と同じく C01 の完了条件が持つ。

### D6. 節は主張で始め、そこから段階的に厚くする (C01 / C05 / C12)

利用者の追補 (2026-08-18): 「冒頭でまず各セクションごとに何を言いたいかをしっかり伝えた後、
それを説明していくように徐々に補足説明や図解を入れる形で立ち位置を整える」。

D1-D5 は「何を載せるか」と「どの形で載せるか」を決めたが、**節の中でどの順に置くか**は
決めていなかった。図解を増やした結果、節がいきなり図から始まり「何の主張を支える図なのか
分からないまま図を読まされる」形が生まれた。図解優先は配置順の指示ではない。

正本は `handout-visual-policy.json#opening.section_opening`。

| step | 置くもの | 答えるもの |
|---|---|---|
| 1 | `lead_line` | 何が言えるか |
| 2 | 要点を並べる部品 (カード・表・チェックリスト) | その主張の中身は何か |
| 3 | `DIAGRAM` | なぜそう言えるか・どうつながっているか |
| 4 | `TEXT` (任意・1 本まで) | 形にしても残る補足 |

- **step は飛ばしてよいが、順番は入れ替えない。** 読み手は全員が最後まで読むわけではない。
  どこで読むのをやめても、そこまでで筋が通っている必要がある。
- **`lead_line` は主張の言い切りにする。** 「〜について」「〜の整理」で終える話題の提示は、
  読み手にとって見出しの言い換えでしかない。見出しが場所を示し、`lead_line` が結論を示す。
- **step 4 が要るのは、step 2-3 の形が足りていない合図**である。TEXT を足す前に、形へ
  落とせないかを先に疑う。

機械検査できるのは「節を散文で始めていないか」(`W-OPENS-PROSE`)、「冒頭 3 要素が
宣言の長さに収まっているか」(`W-HERO-LONG`)、「冒頭の総量が 1 画面に収まるか」
(`W-HERO-HEAVY`)、「`lead_line` が 1 行か」(`W-LEADLINE-LONG`) の 4 つだけである。
step 2 と step 3 の前後、および言い切りか話題の提示かは値域で判定できないため、
D1 と同じく強制は C01 の完了条件が持つ。

**冒頭は 1 フィールドずつではなく総量でも縛る** (`opening.hero_total`)。初回実走の
成果物は目的 44・背景 61・ゴール 39 と、個別上限をどれも超えていなかったにもかかわらず、
hero に 5 つの箇条リストが縦に積まれた結果 465 文字 15 行になった。`W-HERO-LONG` は
文字数の長いフィールドしか見ないため、短い行の積み上げを取り逃がす。上限 400 字の
根拠は原稿用紙 1 枚であり、個別上限の合計 (60 + 80 + 50) に箇条 8 件 × 25 字を
足した値ともほぼ一致する。

溢れたときに削るのは「読み終えたときの持ち帰り」(覚えておくこと・覚えなくてよいこと)
である。これは読む前の判断材料ではないので、本編末尾か `role=appendix` の節へ移す。
ただし schema が `minItems: 1` を課すフィールドは冒頭から消せない。**移すのであって
黙って落とさない** (D5)。

## 却下した案

- **part id ごとに `comprehension_mode` をカタログへ持たせる案**: 部品カタログは
  「id 語彙の正本」であって編集方針の置き場ではない。視覚部品の集合は方針側の
  関心事なので `handout-visual-policy.json#visual_parts.ids` に置く。
- **図解の下限を error にする案**: D1 の理由により却下。強制は C01 の完了条件が持つ。
- **provenance に `draft-inferred` を足す案**: provenance は C12 が閉じた語彙として
  持つ層であり、推定の別はそこに属さない。仮置きの開示は生成レポートで行う。
