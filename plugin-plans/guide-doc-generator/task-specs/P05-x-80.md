# dispatch-ready-set が stage_gate.deferred_to_release を知らず draft でも defer 対象を ready に出す

## 由来

build 実行中に `P04-C22-01` が発見したタスク (change_level=
structural)。本 spec は planner の外ループ (accept-discovered-task.py) が
discovered-task form から決定論生成したものであり、derive 由来の spec と同じ契約で扱う。

**発見理由**: route-build-plan.json の stage_gate は --stage draft で 52 node (P03-x 全 4 / P04 全 33 / P05-x-01..05 / P06..P13) を deferred_to_release として defer するが、TG-C01 dispatch-ready-set.py はこの plan を入力に取らず task-graph と task-state だけで ready_batch を計算する。結果 draft build 中に P04-Cxx が ready として出続け、dispatcher が defer 対象を 8 件 dispatch した (うち 4 件は done まで到達)。成果自体は release で再利用されるため無駄にはならないが、draft の意味 (使える実体を先に出す) が dispatcher の裁量頼みになり、機構として stage を守れていない。実測: generation_queue は 9 件 (build:C04/C23/C13/C14/C15/C16/C17/C21 と task:P01-x-01) しかないのに ready_batch は 20 件超を返した。TG-C01 に --plan を渡して deferred を除外するか、ready_batch の各要素へ deferred フラグを付けて dispatcher が機械的に落とせるようにする。

**発見時の証跡**: `plugins/harness-creator/scripts/dispatch-ready-set.py`

## 作業

`plugins/harness-creator/scripts/` の範囲で上記を解消する。編集先 (write_scope) と
完了トークン (produces) は別物である点に注意する — 実体の変更は write_scope 配下へ行い、
完了したことの記録を `plugin-plans/guide-doc-generator/discovered/P05-x-80.md` へ残す。write_scope は複数タスクで共有されうるため
成果物の鍵にはできない (producer 一意制約)。

## 受入条件

dispatch-ready-set.py が route-build-plan.json を入力に取れる形へ拡張され、--stage draft の plan を渡したとき ready_batch に deferred_to_release の 52 件が 1 件も現れないことを実測する。plan 未指定時は従来どおり全件を返す後方互換も同時に実測する。deferred 対象を 1 件 ready へ混ぜる変異で赤になることを確認し、検査が空ゲートでないことを示す。
