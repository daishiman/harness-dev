利用者が 2026-08-17 に追加した要件 R22 (goal-spec C61-C66) を設計正本へ反映する leaf。要件の原文は「詳しく詳細に伝えるパターンと、勉強会のように大まかに伝えるパターン、レポートのように詳細に伝えるパターンがある。根拠だったりとか、作成する成果物によって、どこまで具体的に、詳細に書くのかという粒度が変わってくるので、その辺もヒアリングしながら整えられるようにしておいてほしい」。

設計判断は 2 つある。

**判断 1 — 粒度は 1 軸ではなく 2 軸である。** 挙げられた 3 パターンのうち「詳しく詳細に伝える」と「レポートのように詳細に伝える」はどちらも詳細だが同じものではない。両者を分けている実質は**根拠・出典をどこまで書くか**であり、説明の詳しさとは独立に動く。1 軸に畳むと「詳しいが根拠は不要」(社内向け操作説明) と「粗いが根拠は示す」(経営向け要約) が表現できなくなる。したがって `detail_level` (overview / standard / detailed) と `evidence_depth` (none / cited / sourced) を直交する 2 つの必須フィールドとして持ち、片方の値から他方を決定しない。

**判断 2 — 粒度を用途プリセットへ埋め込まない。** 「勉強会のように大まかに」は勉強会という用途の**傾向**であって定義ではない。粒度を R20 のプリセットに焼き込むと「勉強会だから必ず粗い」が型として固定される。これは R21 の presentation_order で確定した「時と場合の問題を片方に固定してはならない」と同一構造なので同じ扱いにする — プリセットは既定値を与えるだけで、粒度は独立に上書きできる。既定由来か明示指定かは provenance として記録し、既定のまま通ったのか意図して選ばれたのかを後から区別できるようにする。

責務の割り当ては新規 component を作らず既存へ載せる。ヒアリング (C64) は C01 と C05、スキーマ必須化と 2 軸独立の検査 (C61/C62) は C12、プリセット既定値 (C61 の既定側) は C23、文字数上限の modulate (C63) はテーマトークン正本を持つ C04 と適用側の C11、水準間の共有の型の不変 (C65) は C11 のテスト、宣言と実態の一致 (C66) は C22 と集約側の C09。

C63 は数値の正本を 1 箇所に保つことが要点である。R21 C52 が既に `text_limits.block_body_max_chars` をテーマトークンへ置いているので、detail_level ごとの値も同じトークンファイルが持ち、スクリプト側へ数値を書かない。スクリプトは detail_level をキーにトークンを引くだけにする。

C66 は「宣言だけして実態が伴わない」ことを防ぐ検査である。detailed を宣言しながら記述量が overview 相当しかない資料、evidence_depth=sourced を宣言しながら出典が 1 つも無い資料は、既存のどのゲートも通過してしまう。宣言値は生成物の自己申告なので、実測との突合が無ければ意味を持たない。

C64 のヒアリングは無回答で停止しない。用途プリセット由来の既定値を提示したうえで上書きの要否だけを聞き、回答が無ければ既定を採用する。R19 のヒアリング必須項目 (各セクションの非空 goal) とは性質が異なり、粒度は既定が常に存在するため必須回答にする必要がない。

要件の一次入力は `goal-spec.json` (C61-C66) だが、これは task-graph 上に producer を持たない plan 外の入力なので `consumes` には宣言しない (宣言すると (e) 未生産成果物の消費で落ちる)。産出物は自身の解決記録 `RESOLUTION-R22.md` とする — 反映先の `component-inventory.json` と各 brief は P02/P03 の leaf が producer であり、規則 (c) により本 leaf は producer を名乗れない。本 leaf は P04-x-02 の後に直列化する (両者の write_scope が briefs/ で重なる)。
