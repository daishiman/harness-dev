`P05-x-23` の完了時に起票。**原因が移動したのに受け皿が更新されていなかった** (PAT-5 系) タスク。

> `test_round_trip_equivalence` の当初の所有者 `P05-x-11` は write_scope が `plugins/guide-doc-generator/schemas` のみで、**現在の原因である C20 の抽出粒度 (`scripts/extract-handout-config.py`) へ書けない**。

`P05-x-20` が定量化した残差 (これが直すべき対象の一覧):

- section の `role` / `ties_to` / `attainment_step` / `glossary` が復元されない
- 部品内テキストが兄弟要素ごとに分かれず**連結される** (ステップ部品が `"1資料を開く手元で開く5分"` になる)
- 比較表・二択・DL ボタン・フローが**別部品の形で**復元される
- タブ部品の `panel_parts` が平坦化される
- 図解部品の `diagram_id` に部品 id が入る

なお `P05-x-23` の worker も「抽出結果のセクションに blocks/parts が丸ごと出ない C11↔C20 の往復欠落 (AC-C11-15)」と**独立に同じ所見**を報告している。

## 進め方

1. **残差を 1 件ずつ潰すのでなく、まず「なぜこの形で落ちるか」を 1 段上で読むこと。** 上の 5 項目は「テキストの取り方」「部品の同定」「入れ子の保存」の 3 系統に分かれる可能性が高い。個別対処を 5 回積むと、6 件目の残差で同じことを繰り返す。
2. **同定はクラス名を根拠に行う** (`P05-x-23` が確立した規約)。裸の `<img>` のような「タグだけを根拠にした同定」は行わない — クラス名を持たない画像は本文中の装飾と区別できず、部品として拾うと**構造を捏造する**ことになる。
3. **部品 id を新たに列挙しないこと。** 照合表の鍵は `data_block_type` であり、部品 id との対応はカタログとの join で導出する (`PART-CLASS-MAP-RESOLUTION.md` が正本)。ここで id を書き下すと AC-C11-19 が赤くなる。
4. `ROUNDTRIP-CONTRACT.md` の裁定と矛盾したら、**実装を先に書いてから裁定を後付けしない**。先に裁定を更新し、更新理由を書く。なお `assets[]` の data URI 保持については **`P05-x-28` が裁定中**なので、その決着に依存する部分は触らず `P05-x-28` へ委ねること。
5. **等価判定が素通りしていないことを実測する。** 構成データを 1 箇所変えて往復させ、**壊れることを確かめる**。緑になっただけでは、等価判定が実質何も見ていない可能性を排除できない。
6. 着手前に 4 スイートの失敗テスト名を採取し、完了後に**名前集合の差分**で判定する。
7. 判断と実測結果を `schemas/RESOLUTION-P05-x-31.md` へ記録する (本 leaf の産出成果物)。
8. `git stash` を使わないこと。
