`P05-x-08` が build 中に発見したタスク。発見理由は次のとおり。

> C11 の render-handout.py に 2 件の実装欠陥が確定した。(1) build_css (:885-888) が :root を css_variables からのみ組み立てるため、テーマトークンのトップレベルへアクセント色を置いても出力へ反映されず test_determinism.TokenIndirectionTest.test_accent_token_change_only_diffs_root_block が緑にならない (P05-x-08 が assets/tokens/ 側を整えたが write_scope の壁で未達)。(2) B14 (フロー) を :719 で `<ol class=flow>` として自前描画しており、script-brief-C11.json の block_to_component_map が定める「C14 の pattern=flow へ委譲。フロー表現をレンダラ側で二重に持たない」に反する。同 script の DIAGRAM 経路 (:804-819) は正しく委譲しているため B14 だけが二重実装。P04-x-09 が追加した FlowRenderingTest の 2 件がこれを検出している。両欠陥は同一ファイルのため 1 leaf へ束ねる

## 進め方

### 欠陥 (1) トークン間接参照

- `build_css` (`:885-893`) がトークンのトップレベルにある `--` 始まりキーを `css_variables` の同名キーへ上書き適用するようにする。`CSS_VARIABLES_KEY` (`:68`) 不在時の `LaunchError` は残すこと (トークンファイルの構造契約を弱めない)。
- P05-x-08 の worker が scratchpad 上の clone で 4 行のパッチを検証しており、差分が `['-  --pop-primary: #43a4f5;', '+  --pop-primary: #123456;']` の 1 行のみになることを実測している。**ただし dispatcher はこのパッチを未検証なので、鵜呑みにせず自分で測ること。**
- **アクセント実値の重複を増やさない。** 現在 `accent.base` / `accent.scale[bright].value` / `css_variables["--pop-primary"]` / トップレベル `--pop-primary` の 4 箇所に同じ色が入っている。上書き方向を決める際、どちらが正本かを明確にし、冗長になった側を削れるなら削る。ただし `assets/tokens/` は本 leaf の write_scope 外なので、削除が必要なら実施せず報告する。
- 併せて `script-brief-C11.json#theme_token_schema_ownership` に「アクセント色の入口がトップレベルにある」ことが未記載である (矛盾ではなく欠落)。brief は write_scope 外なので追記せず報告する。

### 欠陥 (2) B14 の C14 委譲

- `:719` の自前描画を、DIAGRAM 経路 (`:804-819`) と同じ `render_diagram` 委譲へ寄せる。`data-hb-diagram-pattern` が `block.pattern` の素値で出ること、部品内に inline SVG が現れること。
- `data-hb-part` / `data-hb-part-id` / `data-hb-key` / `data-hb-kind` の属性契約 (`script-brief-C11.json#html_attribute_contract`) を満たすこと。

### 欠陥 (3) chrome 境界 — hero 内マーカーの到達不能

`P05-x-11` の裁定で追加確定した欠陥。発見理由は次のとおり。

> hero は `tag("div", [..., ("data-hb-generated","true"), ...])` として出力され (`:1386-1391`)、抽出器は `:422` の `if node.attr(ATTR_GENERATED) == "true":` で**部分木を丸ごと読み飛ばす**。よって hero 内の `data-hb-field` は 1 つも読まれず、`title` すら復元できない。**「マーカーが無い」ではなく「マーカーはあるが到達できない」が正しい診断**である

- `field_span("focus_theme"…)` (`:1357`)、`target_task` + `data-hb-key` (`:1368`)、`attainment_level` (`:1373`)、`must_remember` (`:1378`)、`no_need_to_remember` (`:1383`)、`date` (`date-pill num`) は**すべて実在する**。dispatcher が独立に読解して確認済み。マーカーを足す作業ではない。
- `data-hb-generated` の意味は「著者が書いていない生成物なので復元対象外」であるはず。hero 枠自体はそれで正しいが、**枠の属性が内側の著者データまで巻き込んでいる**のが誤り。境界を枠へ限定するか、抽出器側でマーカー付きノードを例外にするか、どちらの方向で解くかは本 leaf で決めてよい。ただし**抽出器 (`extract-handout-config.py`) は write_scope 外**なので、抽出器側の変更が必要と判断したら実施せず報告すること (受け皿は `P05-x-19`)。

### 欠陥 (4) heading マーカー不在と ties_to の直列化

- `sections[].heading` は `:1511-1513` で `'<h2 class="section-label"><span class="section-num num">{}</span>{}</h2>'` として出るが `data-hb-field` を持たず、しかも**連番 span が本文と同じ要素の中に混ざる**ため、テキストを取っても `1<見出し>` になり素値へ戻せない。`data-hb-field="heading"` を付け、連番を復元対象から外れる形にする。
- `sections[].ties_to` (`:1536`) は Python の list を属性値へ直接埋めており `"['goal', …]"` という復元不能な形で出ている。`ROUNDTRIP-CONTRACT.md` の裁定 (スペース区切りトークン列) に従って直列化する。**この形式は P05-x-11 の worker が契約に規定が無い中で決めた設計判断**であり、裁定文書が正本。従わない場合は理由を述べたうえで裁定文書側の変更を報告すること (裁定文書は write_scope 外)。
- `notes_enabled` は裁定で `data-hb-notes-enabled` という**新設マーカー**が割り当てられている。マーカー名は worker の命名で既存 brief に無いため、brief への反映は `P05-x-21` が担当する。本 leaf は裁定文書の名前をそのまま実装する。

### 欠陥 (5) 日付ピルの配置が brief 違反

`P05-x-09` が build 中に発見した。発見理由は次のとおり。

> `build_hero` (`:1332-1336`) が `field_span("date", …, klass="date-pill num")` を **hero 内**へ出す一方、`build_header` (`:1405-1416`) の `header.pop-header` は nav のみを内包する。`script-brief-C11.json` 手順 13 は「値をそのまま **header の `.date-pill`** として 1 個だけ出す」と明記しており、C18 の `DATE-01` (日付表記が冒頭に無い) が正しく renderer が違反している。config に配置を指示する手段が無いため fixture 側では原理的に吸収できない

- `.date-pill` を `header.pop-header` 内 (nav と同階層、hero より文書順で前) へ出す。dispatcher が brief と実装を独立に突合して確認済み。
- **brief は「1 個だけ」と定めている。** header へ足して hero にも残す解は 2 個になり別の違反を生む。
- これが直れば `test_language_gate_passes` は緑になる見込み。ただし DATE-01 以外の診断が同テスト内に隠れている可能性があるため、**実測で確認すること** (P05-x-09 は「正規化を直したら第 2 の原因が露出した」という経緯そのものである)。
- `header` には `data-hb-generated="true"` が付いている (`:1411`)。日付を header へ移すと**欠陥 (3) の読み飛ばし問題の対象が広がる**ので、(3) と (5) は同時に設計すること。

## 共通の規律

- `write_scope` の外へは 1 バイトも書かない。範囲外の修正が必要になったら手を出さず、何をどう直すべきかを報告する。

- 実行前後で `tests/render-handout.py` の**失敗テスト名の集合**を採取して比較する (件数だけの比較は並行 build 下で他 leaf の書込と交絡する)。
- テストは Python 3.10+ の標準ライブラリのみ (`unittest`)。
