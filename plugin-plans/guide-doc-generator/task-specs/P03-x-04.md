利用者が実際に行った研修のフィードバックとして 2026-08-17 に追加された要件群 R21 (goal-spec C46-C59) を、23 component の設計正本へ反映する leaf。

この要件群の性質は R11 (抽象↔具体の往復) と同じ**文章構造の型への制約**であり、個別の生成物を手で直して解決する種類のものではない。原則は 4 つ: (1) 目的に直結しない内容は離脱を招くので型として排除する、(2) 説明は短いほどよく、長い説明は既定で畳む、(3) 機能名から説明を始めず「何ができるか」の具体例を先に見せる、(4) まず読み手に触ってもらう。

最大の設計判断は presentation_order である。デモ先行 (demo_first) と説明先行 (explain_first) はどちらが優れているかではなく聴き手の習熟度に依存する時と場合の問題なので、片方を型として固定してはならない。同時に、新たなヒアリング項目を増やすことも避ける — R19 が既に取得している `prior_knowledge` から既定値を決定論導出し、ユーザーの明示上書きだけを受け付ける形にする。両モードで C44 の共有の型 (sticky 目次 / 日付表記 / 目的・背景・ゴール明示 / 抽象↔具体の往復 / アイコン規約 / 単一ファイル自己完結) は保持され、差分は部品の並びに限定される。これは R20 のプリセット機構が既に持つ不変条件と同じ構造なので、新機構を足さず同じ機構へ相乗りさせる。

追補分 (C56-C59) は 4 つの独立した判断を足す。**C56**: demo_first で最初に出すのは概念図ではなく実際の画面である — 概念図から入ると「何ができるか」が像を結ばないため、抽象図の先行提示を型として禁じる。**C57**: 覚える対象を絞るだけでは足りず「覚えなくてよい範囲」を対で明示する — 明示しない限り読み手は全部を覚える対象と見なして負荷が下がらないので、両枠を必須にする。**C58**: 受講者が達成したい具体業務 (車両収支の自動化など) をヒアリング必須項目へ追加し、各セクションのその紐づけを検査する。R19 が既に持つ読者像・前提知識・利用シーンは属性であって達成目標ではないため別軸のフィールドが要る。**C59**: 対話枠 (受講者の悩み・やりたいことを聞き出す時間) を必須セクションとし所要時間の下限割合を検査する。時間配分に載せない限り「時間があれば聞く」枠に退化して必ず削られる。C59 の所要時間フィールドは R20 のアジェンダ用途が既に要求する時間配分と同一機構へ相乗りさせ、二重に持たない。

C55 (図表・グラフの欠落検査) は既存の検証ゲート component の判定項目追加として扱い、新規 component を作らない。「生成したはずのグラフが表示されない」は R01 の外部参照ゼロ検査を通過してしまう欠陥クラスなので、独立した検査項目が要る。

要件の一次入力は `goal-spec.json` (C46-C59) だが、これは task-graph 上に producer を持たない plan 外の入力なので `consumes` には宣言しない (宣言すると (e) 未生産成果物の消費で落ちる)。

本 leaf は P03-x-03 の後に直列化する。両者の write_scope が plan dir 全体で重なり、かつ P03-x-03 が確定させる部品カタログ正本 (`config/handout-parts.json`) と用途語彙正本の上に R21 の部品追加が乗るためである。P04 のテスト先行 wave は本 leaf の後に置く — R21 を反映する前にテストを書くと、冒頭の情報過多を許す受入基準がテストへ固着する。
