## ブリーフの owner 宣言と本 leaf の関係 (誤読を避けるための明示)

ブリーフの「単独 owner は C11」は**語彙の正本がどこにあるかの宣言 (canon authority)** であり、「そのファイルを誰が書くか (write authority)」ではない。`write_scope` は非空 string 1 本しか取れない仕様 (`derive-task-graph.py:173` / `validate-task-graph.py:416`) なので、`scripts/<x>.py` を持つ component leaf が同時に `config/<y>.json` を持つことは構造上できない。

本 leaf は write authority を単独で引き受け、canon authority はブリーフ宣言のまま各 component に残す。この分離は望ましい副作用を持つ:

- **script が自分の語彙を書き換えられない**。C11 の「part id を実装へ列挙しない」・C12 の「閾値を script へ書かない」・C23 の「他 component は語彙を一切列挙しない」は、いずれも「データとそれを読むコードを分ける」ことを要求している。write_scope の分離はこれを構造として保証する (`P05-x-02` が `assets/` に対して行ったのと同じ形)。
- 語彙の追加・プリセットの差し替えが script 変更を伴わないことが、レビューなしに graph から読める。

逆向きの禁止: **C11 / C12 / C19 / C23 の build leaf は `config/` へ 1 バイトも書かない。**

## 節単位の視覚部品要件 (P05-x-03-acceptance-hardening)

受入条件 (3a)-(3c) は利用者指定 2026-08-18 追補「図解と画像は毎回セクションごとに必ず追加する」の機械化であり、正本は
`improvement/visual-per-section-decision.json#decision` (diagram_per_main_section.value=1 / image_per_main_section.value=1 /
role_split.roles=screenshot|illustration)。本 spec は値を再定義せず、そこを参照する。

### なぜキーの存在では足りないか

書き換え前の受入条件は「各 preset の section_order / recommended_parts / notes / … を持つこと」であり、キーが在ることしか問うて
いなかった。この形は中身が空でも、中身が要件と真逆でも緑になる。実測 (2026-08-19・出荷 `config/handout-purposes.json`) では
8 preset・43 セクションのすべてが DIAGRAM を持たず、42 セクションが IMG を持たず、43 セクションが `image_role` を宣言していない。
旧受入条件はこの状態を合格と判定する。3 点を明示要求へ変えたことで、同じデータが 43 件の違反として赤になる。

### 空ゲートでないことの示し方

- **(3a)**: いずれか 1 節の `recommended_parts` から DIAGRAM を 1 件外すと、その節が違反として数えられる。
- **(3b)**: 同様に IMG を 1 件外すと赤になる。DIAGRAM を残したまま IMG だけ外して赤になることで、2 つの条件が独立に効いている
  ことが分かる (視覚部品の総称で数えていれば IMG だけの欠落は素通りする)。
- **(3c)**: `image_role` を `"diagram"` のような値域外の文字列へ変えると赤になる。キーの有無ではなく値域を見ていることの確認で、
  キー存在だけを見る実装ならこの変異が素通りする。

### 判定単位

「main セクション」は `section_order[]` の要素のうち、資料本編を構成する節を指す。付録・表紙相当の節を除外する規則を C23 が
持つ場合はそれに従い、本 spec 側で第 2 の定義を作らない。除外規則が無い場合は `section_order[]` の全要素を対象とする
(除外を発明すると、除外に逃がすことで緑にできてしまう)。
