`P05-x-07` が build 中に発見したタスク。発見理由は次のとおり。

> P05-x-07 が `verify-handout-a11y-print.py` を「部品 id のリテラル列挙」から「`config/handout-parts.json` を `data_block_type` 述語で実行時に引く」形へ変えた結果、この script は**新しい実行時依存**と**新しい失敗経路 (カタログ不在・不正時の exit 2)** を獲得した。しかし宣言正本である `script-brief-C17.json` にはどちらも記載が無い。同様に hero 内フィールドの解決規約が `script-brief-C22.json` に無い。brief は `plugin-plans/` 配下で P05-x-07 の write_scope 外だったため、worker は正しく手を出さず報告に留めた

## 進め方

1. **まず実装を読む。** `verify-handout-a11y-print.py` の `PARTS_RELPATH` (`:65`) / `CatalogError` (`:495`) / `load_part_ids_by_block_type()` (`:507`) / 注入点 (`:1221`) / 捕捉点 (`:1314`) を確認し、**どういう条件で exit 2 になるかを実際に再現する** (カタログを一時的に退避またはリネームして起動する。**`git stash` を使わずスクラッチへ `cp` すること**。確認後は必ず元へ戻し、戻したことを報告に含める)。
2. `script-brief-C17.json` へ (a) `config/handout-parts.json` への実行時依存、(b) カタログ読取失敗時の exit 2 を宣言する。**既存の exit code 定義と番号が衝突しないか必ず確認すること** — 既存に 2 が別の意味で使われていたら実装側が誤りである可能性があり、その場合は brief を無理に合わせず矛盾として報告する (実装は write_scope 外)。
3. `script-brief-C22.json` へ hero 内フィールドの解決規約を宣言する。現状 renderer は `title` / `date` / `duration` / `focus_theme` / `target_task` / `attainment_level` / `must_remember` / `no_need_to_remember` を hero 内へ出しているが、`P05-x-18` が **`date` を header へ移す**予定であり、`P05-x-11` の裁定で **chrome 境界 (`data-hb-generated` による読み飛ばし範囲)** も変わる。よって「どの要素の中にあるか」でなく「**どのマーカーで引くか**」を規約として書き、位置に依存しない形にすること。
4. **診断コードやシンボルの棚卸しに `grep -oE '\b<pattern>'` を使わないこと。** macOS の BSD grep は日本語を含む長い UTF-8 行で語境界判定が壊れ、存在しない切れた一致を出す。`\b` を外すか Python の `re.findall` を使う。dispatcher が実際にこれで誤った前提を作っている。
5. **`script-brief-C20.json` に触れない。** `P05-x-21` が同じ `briefs/` ディレクトリで当該ファイルを編集する。write_scope はディレクトリだが、**編集してよいのは C17 / C22 の 2 ファイルと自分の RESOLUTION 文書だけ**。
6. 編集後に `json.load` で妥当性を確認し、トップレベルキーの集合が編集前後で保存されていることを実測する。
7. 裁定と作業内容を `briefs/RESOLUTION-P05-x-24.md` へ記録する (これが本 leaf の産出成果物)。
