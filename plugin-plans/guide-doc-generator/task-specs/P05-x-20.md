`P05-x-11` が build 中に発見したタスク。**本 build で最も重い発見**であり、発見理由は次のとおり。

> C11 (renderer) と C12 (schema) の入力契約が 2 点で乖離しており、schema 準拠の config を renderer へ渡すと (a) `normalized` / `nav` が `additionalProperties:false` に弾かれ (b) `sections[].parts` が読まれず `blocks` を探すため部品が 1 件も描画されない (実測 `blocks_by_type: {}`)。**round-trip 以前に、正規の入力経路が通っていない**。この乖離が解けない限り、どの項目にマーカーを刻んでも round-trip は成立しない

## 乖離の実体 (dispatcher が独立に確認済み)

| # | renderer 側 | schema 側 |
|---|---|---|
| (a) | `:387` `if config.get("normalized") is not True:` を問題とする | top-level properties に `normalized` が無く `additionalProperties:false` |
| (b) | `:441-443` `nav = config.get("nav")` 不在を問題とする | top-level properties に `nav` が無い |
| (c) | `:1523` `for block in section.get("blocks") or []:` | section は `parts` を宣言し `required` にも `parts` が入る。`blocks` は存在しない |

## 進め方

1. **まず裁定する。** 取りうる解は少なくとも 3 通りある。
   - (A) schema を正本とし renderer を直す (`normalized`/`nav` 必須を撤廃し `parts` を走査する)
   - (B) 正規化後の形を schema へ明示する (`normalized`/`nav` を properties へ追加し、正規化前後を別の schema として分ける)
   - (C) C12 の `--normalize` 出力を renderer の期待形へ寄せる中間層を置く
   **どれを採るにせよ、`additionalProperties:false` を `true` へ緩める・`required` を外すといった「検査を弱めて通す」解は採らない。** P05-x-11 が同じ誘惑を退けており、その判断と整合させること。
2. 裁定の根拠として `script-brief-C11.json` / `script-brief-C12.json` の入力契約記述を突合し、**どちらの brief が何を約束しているか**を確認する。brief 間にも矛盾があれば、それ自体を記録して報告する (brief は write_scope 外)。
3. `nav` については、C11 が目次データを config から受け取る設計なのか sections から導出する設計なのかで意味が変わる。`sections[].id`/`heading` から導出可能なら config へ持たせる必要が無い可能性がある — **導出値を契約へ書き下す (PAT-1) の再発を作らないこと**。
4. **write_scope は `plugins/guide-doc-generator/` 全体と広い。** これは裁定の結論が schema 側・renderer 側どちらに落ちるか事前に決められないため。ただし広い scope は他 leaf との衝突を招くので、**実際に書き換えたファイルを最小限に保ち、報告で列挙すること**。
5. 実行前後で 3 スイート (`render-handout.py` / `validate-handout-config.py` / `extract-handout-config.py`) の**失敗テスト名の集合**を採取して比較する (件数だけの比較は並行 build 下で他 leaf の書込と交絡する)。
6. **テストの assert を弱めない。** 削除・許容範囲の拡大・skip の追加はいずれも不可。テストは Python 3.10+ の標準ライブラリのみ (`unittest`)。
