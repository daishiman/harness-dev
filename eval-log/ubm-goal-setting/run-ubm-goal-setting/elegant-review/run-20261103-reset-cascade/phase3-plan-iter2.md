# Phase 3 改善計画（iteration 2）— 並列 executor 共通契約

前提: `phase3-plan.md`（iteration 1）の「書き方の原則」と確定事項 A〜F は引き続き有効。本書はその**差分**で、矛盾する場合は本書が優先する。
正本の指摘一覧: 同じディレクトリの `findings.json`（loop_count=1・30思考法・65 issue）。担当ファイルの issue は次で引ける:

```bash
python3 -c "import json,sys;d=json.load(open('findings.json'));[print(f['paradigm_id'],i['condition_signal'],i['severity'],i['location'].get('line'),'|',i['description'],'\n  =>',i['recommended_intervention'],'\n') for f in d['paradigm_findings'] for i in f.get('issues',[]) if sys.argv[1] in i['location']['file']]" <ファイル名の一部>
```

`recommended_intervention` に【意味の変更あり】とある指摘は、下の確定事項 G〜L の範囲でだけ直す。範囲外の意味の変更は直さずに報告する。

## 書き方の原則（iteration 1 から再掲せず、追加分だけ）

1. 追記ではなく置換（R4）。古い規則文・古い例を残したまま新しい文を足さない。
2. 規則の本文は `output-formats.md` の共通部品A〜F にだけ置き、他ファイルは 1 行参照（`` `output-formats.md` の「共通部品A 行動行」 ``）。
3. 担当外のファイルは編集しない。必要なら報告の「他レーンへの依頼」に書く。
4. git commit / push / stash / reset / checkout はしない。

## 確定事項（iteration 2・ユーザー承認済み 2026-11-03）

### G 月報の提出用＝管理用の射影（Q1: 射影に統一）
- 提出用は管理用と**同じ項目名・件数・単位・期日**を持つ。管理用の行から **チェックボックス・グループ見出し（`### → `）・成果目標の2行目（`→ 売上貢献：…`）・本文中の個人名** だけを外したもの。人数・件数への集約（合算）はしない。
- そのため**全層共通で、項目名（「：」より前）に個人名を入れない**。対象の人は「：」の後の本文に書く（例: 管理用 `- 提案の受諾：Bさんの受諾1件　期日6/20` → 提出用 `- 提案の受諾：受諾1件　期日6/20`）。グループ見出しも `### → 提案の受諾：Bさんの受諾（100000円）` の形。
- 「人数・件数に集約して書く。個人名で割らない」「貢献額の合計は管理用と同値にする」（OF L1222 付近）の記述は削除し、上の射影規則への参照に置換する。検査器の提出用照合（項目名・数量・単位・期日）はそのまま使う。

### H 週の正本＝【今週の行動目標】（Q2: 行動目標を正本）
- 週報で済／未済のチェックを付けるのは **【今週の行動目標（行動管理・優先順位付き）】の行動行だけ**（Daily.md の embed もここを参照する）。MTG 後のお礼・告知連絡などの送付も、支える成果グループ（または `### → （関係維持）`）の行動行として置く。
- **日付索引**（新設・共通部品A の一部）: `- {M/D（曜）}：{項目名}、{項目名}`。チェックボックスなし。その日の「やらないこと」は同じ行の末尾に `｜やらない：{内容}` を付ける（行動の無い日は `- {M/D（曜）}：なし｜やらない：{内容}`）。索引に書く項目名は同じ文書の行動目標に実在すること。
- 【今週の大きな到達ライン】は日付索引の形にする（見出し名は変えない）。月報の【今月の日別タスク】も同じ日付索引の形にする（項目名は【プロジェクト別タスク】か管理用の行動目標に実在すること）。
- 週報の【プロジェクト別タスク】は**出力しない**（週報の実行管理は「行動目標＋日付索引」の1方式。方式1／方式2 の区別は廃止）。共通部品F の表で週報＝出力しない。
- 月報の【プロジェクト別タスク】（旧詳細版・詳細依頼時）の行は共通部品A の管理用書式: `### {案件名}` ＋ `- 先方担当者: {名前}` ＋ `- [ ] {項目名}：{何をする}　期日{トークン}`。`[期日] [提出先・宛先]` の書式は廃止（宛先が判定に必要なら本文に書く）。

### I 挽回＝対応行（Q3: 対応行にする）
- 前回ブロックの「未達を挽回するための行動」の各行は次の1形だけ（売上・成果・行動、4層で共通。共通部品D）:
  `- {前回の項目名}：{起点}→{到達点}（今回の行動目標「{今回の項目名}」で実行）`
  - `{起点}→{到達点}` は行動の基準値（例 `提案2件→4件`）。期日は**今回の行動目標の側にだけ**書き、挽回行には書かない。`{今回の項目名}` は同じ文書の今回の行動目標に実在すること。
  - 未達が無ければ `- なし`。初回は `- 初回（前回正本なし）`。要因分析の `###` 小見出し以下は従来どおり（対応行の検査対象外）。
- 共通部品D の「行動は共通部品A の行動本文（何をする＋期日）で書く」と、OF L664 付近の `- **未達項目** → 行動変化` 形は、この対応行に置換する。

### J 期日の FAIL 化（Q4 採用）
- 今回の期間の行動目標の行（週報・月報管理用・月報提出用・期報・1年、および月報の【プロジェクト別タスク】）は、**行末**が `期日` ＋任意の空白＋トークン＋任意の `まで`／`までに` で終わること。無ければ FAIL。前回ブロックの転記行・習慣目標・振り返りには掛けない（前回はそのまま転記するため）。
- トークン: `M/D`（後ろに `（曜）` 可）・`YYYY-MM-DD`・`{月火水木金土日}曜`（`曜日` 可）・`毎日`・`毎朝`・`毎週`（後ろに `{曜}曜` 可）・`今週`（**週報だけ**）。土曜・日曜を追加。`毎月`・`今月中` 等はトークンではない（FAIL）。
- 正本は共通部品A の期日トークン。検査器の正規表現と OF の文言を一致させる。

### K 行動の配列を1つに（Q4 採用）
- データ契約の `action_daily`（#14）・`action_period`（#15）を **#14 `actions`（object[]）** に統合する。#15 は欠番（「#15 は欠番（#14 に統合）」と表に1行残す）。
- 要素: `{item_name: string, what: string, deadline_token: string, outcome_group: string}`。`outcome_group` は支える成果目標の項目名、または `（土台）`／`（関係維持）`。出力は `- [ ] {item_name}：{what}　期日{deadline_token}` を `outcome_group` ごとのグループ見出しの下に並べる（並び順は共通部品A の優先順位）。
- `#12-17` のような範囲参照は `#12-14, #16-17` 等へ直す。
- 新フィールド **#37 `prev_not_doing_check`**（string[] / null、週報のみ、Step 1）: 前週の週報の日付索引の `｜やらない：` 注記（旧形式では「やらない」系の子タスク）を項目に、`- {内容}：守れた` か `- {内容}：守れなかった（{M/D}）`。初回は null（出力は `- 初回（前回正本なし）`）。`{{prev_not_doing_check}}` の生成元はこれ。フィールド総数は **全36フィールド（#1-37、#15 は欠番）**。

### L 中間成果の第3の形（Q4 採用）
- 貢献0の括弧は次の3形だけ（共通部品B）:
  1. `0（{同じ文書の直接成果の項目名}を支える）` — 当期の直接成果を支える中間成果
  2. `0（{M}月の{直接成果の項目名}を支える）` — 来期以降の直接成果を支える中間成果（同じ文書に無くてよい）
  3. `0（{M}月計上・{根拠}）` — 翌期に計上する直接成果
- 直接成果＝貢献額が0より大きいもの、または形3のもの。形1の項目名は同じ文書の直接成果に実在すること（FAIL）。上の3形以外の `0（…）` は FAIL。グループ見出しの0円は `（0円）` だけ（`0円・8月の仕込み` 等は不可）。

### 見送り（ユーザー非採用・現行仕様を維持）
- 月報の簡潔版の既定化は**採用しない**。現行どおり、簡潔版は frontmatter `monthly_action_style: concise` を明示したときだけで、無指定は旧詳細版（【プロジェクト別タスク】必須）。文書はこの現行仕様に一致させる（矛盾があれば現行仕様側へ寄せる）。後続課題として報告する。

### 承認不要の既定対応（loop1 指摘から）
- 初回マーカー: 前回ブロックの各欄に `- 初回（前回正本なし）` の1行。検査器は (a) マーカー→照合を飛ばして PASS 表示、(b) 欄が空→転記漏れとして FAIL、(c) 項目名の無い旧形式→従来どおり WARN。data-contract の「初回は省略」系の記述（DC L599 付近）も共通部品D に合わせる。1年の初回は R2 で「root_cause の材料」とする。
- 週報の必須見出しに前週ブロック12見出し（【前週の売上目標】〜【前週の行動に対して未達を挽回するための行動】）を加える。目標欄に項目があるのに実績・差分の欄が無ければ FAIL。
- 軌道修正記録（共通部品E）の行書式を検査する: 【今週の見直し記録】と月報管理用【確認された情報】の `行動の見直し：` 行は `- なし` か5欄すべて非空、項目名が今回の行動目標に実在、変更前≠変更後。
- 記号（○/△/×）は実績に「書かない」に統一。`[要確認]` は「確認中」に統一。具体日は期日欄だけに書く（本文に埋め込まない）。
- `--yearly` の機械強制の説明の正本は `references/validation-gates.md` の IN3。共通部品C と他ファイルの再掲は IN3 への1行参照にする。`--no-yearly` のとき `--quarterly` と同じディレクトリに期間を含む1年目標があれば WARN。
- 「正本が勝つ」系の再掲は OF 冒頭の1か所に寄せ、他は削除または1行参照。期日の逆算規則の再掲（OF 内6か所）は「行動目標の並び順と期日の逆算」への1行参照に。
- 共通部品F の上限表は値を持たず「名前→正本の場所」にする。
- `references/version-history.md` は凍結（冒頭に「凍結。以後の版履歴は CHANGELOG.md」）し、参照元（SKILL.md・resource-map.yaml）を CHANGELOG.md に付け替える。
- スタブ2本（thinking-methods-toolkit.md / thinking-process.md）は**削除しない**（完了計画書 component-inventory の build_target が指すため。orchestrator 判断で保留）。
- policy（action-language-policy.json）への語の追加はしない（確定事項A のまま）。
