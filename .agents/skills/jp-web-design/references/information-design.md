# 情報設計の工程 — 表から始めない

**画面を「どの順で決めるか」の規律。** 装飾を最後に足しても画面は良くならない。良し悪しは、表を書く前の情報の扱い方(何を消し・何を束ね・何を大きくし・何に加工し・どの器に載せるか)でほぼ決まる。

- 何を守るか(業務構造の診断・体験の規律) = Skill `ux-design`(本書では再説明しない)/ どう描くか(色・組版・部品) = 本スキルの他リファレンス / **どの順で決めるか = 本書**。
- 開くタイミング: **新規画面の設計前**(§2)、**既存画面の改善指示を受けたとき**(§8)、「見づらい・ダサい」の指摘時(§1)、**本書に前例がない要件のとき**(§9)。
- ドメイン非依存。業種・データ・画面種別にかかわらず同じ工程を適用する。
- **本書は事例集ではなく導出の仕組みである。** 表・カタログは出発点にすぎず、当てはまらない場合は §5-1 の判断軸と §9 の手順で導く。「載っていないからできない」は成立しない。

## 0. 適用範囲 — 表が正解の画面もある(先に読む)

本工程は**すべての画面に適用する**が、Step 6 で選ぶ出力形式は用途で変わる。

- **読んで判断する画面**(一覧・詳細・ホーム・レポート・相手に見せながら話す画面) → カード/リスト等になることが多い。
- **打ち込む・突き合わせる画面**(台帳入力・照合・一括編集・大量比較) → **表が正解**。一覧性と打鍵効率が最優先で、これをカード化すると劣化する。

禁じているのは表そのものではなく、**「とりあえず表から書き始めて、そこで思考を止めること」**。表を選ぶ場合も Step 0〜5 は必ず通す(表の列順・列幅・加工・グループ化は、優先順位を決めた結果として初めて決まる)。

## 1. アンチパターン — 「設計 → 装飾」の順で作った画面に出る6症状

レビューではまずこの6つを探す。1つでも当たれば装飾の修正ではなく**工程の最初に戻る**(§8)。

1. **全項目にラベルが付き**、ラベルと値が同じ視覚的重みで並んでいる。
2. **DBの値がそのまま出ている**(生年月日・ISO日時・コード値・真偽値・内部ID)。
3. **グループ化も優先順位もなく**、全情報が同じサイズ・同じ間隔で均一に並んでいる。
4. **説明文で操作を補っている**(「対象を選択して削除ボタンを押してください」)。
5. **装飾が彩りとして入っている**(表ヘッダーのブランド色ベタ塗り+白抜き文字・カテゴリごとの色分け・格子罫線)。
6. **ボタンが密集**していて指で押し分けられない(44px未満・間隔なし)。

> 症状3〜5は「情報が整理されていないことを、装飾で埋め合わせようとした跡」。足した装飾を剥がすところから始める。
> **6つに当てはまらない違和感**は、症状ではなく工程のどこを飛ばしたかで特定する(§2の各Stepを順に自問する)。

## 2. 工程8ステップ(Step 0〜7)— 順序を飛ばさない

### Step 0. 使われる場面を1文で書く
**誰が・どこで・何をしながら・何の端末で・1回に何件扱うか。** これが後続すべての判断基準になる(体験設計の入口3点と同じ問い)。
例: 「担当者が相手の目の前で、会話しながら、タブレットで、1件分を見る」/「事務が自席のPCで、原票を見ながら、月次60件を上から打ち込む」。
場面が書けないうちは画面を描かない。書けたら、以降の全ステップでこの1文に照らして決める。

### Step 1. ラベルを全部消す
使えるデータ項目を並べ、**ラベル(項目名)をいったん全部外して値だけにする**。ラベルは「無いと困るもの」だけを後から戻す。最初から全項目にラベルを付けると、ラベルと値が同量の文字として画面を埋め、どこを読めばいいか分からなくなる。

### Step 2. 伝わらないものだけ補う(§3)
値だけで意味が伝わらない項目にのみ、**最小の語**を戻す。ラベル行を足すのではなく、値に接辞として溶かせないかを先に試す(「No.123」「1985年生まれ」)。

### Step 3. グループ化する(原則3〜4群)
**基準は「データの種類」ではなく「同時に使うか」**。
例: `識別する情報`(番号・名称・画像) / `連絡・接触に使う情報`(電話・メール・住所) / `判断と会話の材料`(実績・状態・属性)。
第一階層は3〜4群を原則とする。5群以上なら使わないものを詳細画面へ送れないか再検討する。それでも超過する方が判断・比較・入力を早くする場合は、場面と超過理由を標準の `docs/product/T2-experience-spec.md`(プロジェクトに同等責務の既存正本がある場合はその正本)に残して採用する。

### Step 4. 優先順位をつける(群間 → 群内)
Step 0 の場面で**先に見るもの**が上位。群間・群内の2階層で順位を確定させる。

- 群内は「**主役1つ + 従属**」。主役はサイズ・太さで立て、それ以外は静かに保つ(`typography-numerals.md` §1、主役:本文=2.5倍以上)。
- 順位が付けられない = その画面に載せるべきでない情報が混じっている。
- **群の境界は余白で作る**(§6)。罫線・背景色・囲みを足す前に、群間の余白を倍にして解決できないか試す。

### Step 5. 表示用に加工する(§4)
DBの値をそのまま画面に出さない。Step 0 の場面で**そのまま使える形**に変換する。

### Step 6. 表示形式を導出し、優先順に配置する(§5・§6)
既成のカタログから選ぶのではなく、**判断軸から器を導く**(§5)。決まった器に、Step 4 の優先順で配置する。**優先度が高いものを上か左**に置くのが基本(視線の起点)。並び順(昇順/降順)も場面から決める。

### Step 7. 機能を足し、装飾で意味を伝える(§7)
**機能追加はここまで来てから**。先に機能から並べるとボタンが情報を押しのける。装飾は「今風にする」ためではなく、**押せる・選択中・重要・隠れ機能がある**の4つを伝えるためだけに使う。

## 3. ラベル剥がし

**原則: ラベルの役割は「値の意味を一意に決めること」だけ。値の書式・文脈・配置がその役割を果たしているなら、ラベルは重複であり削る。** 下表は代表例であり、載っていない項目もこの原則で判断する。

| 状況 | 扱い |
|---|---|
| 値の書式で意味が一意に決まる(氏名・住所・メール・画像・金額) | **ラベル不要**。値だけ置く |
| 数字・コードだけで意味が決まらない(番号・年・件数) | **接辞で溶かす**(「No.123」「1985年生まれ」「86件」) |
| 対比して読む詳細画面で項目が多い | **定義リスト**(`grid-cols-[8rem_1fr]`)でラベル列を固定幅に(`layout-responsive.md` §1) |
| 同じ項目が縦に何行も並ぶ(表) | ラベルは**列ヘッダーに1回だけ**。行ごとに繰り返さない |

- ラベルを残すときは**値より小さく・muted**。値=濃く太い/ラベル・単位=小さくmuted の文法を崩さない(`typography-numerals.md` §3)。
- **入力UI(フォーム)のラベルは消さない。** 剥がしてよいのは読む専用の表示だけ。placeholder をラベル代わりにしない規律(`components.md` §2)はそのまま維持する。
- ラベルを消した結果「これは何の値か」を説明文で補い始めたら、剥がしすぎ。ラベルを1つ戻す方が短い。
- **スクリーンリーダー用のラベルは消さない**。視覚的に省いた項目は `aria-label` / 視覚的非表示テキストで補う(見た目の省略と支援技術の省略を混同しない)。

### 3-1. 文章とフローの認知負荷(短文化の正本)

目的は文字数だけを減らすことではなく、**迷い・判断回数・画面遷移・例外分岐を減らし、次の操作を見れば分かる状態にすること**。次を設計・検収の共通契約とする。

- **1画面1主目的・主要アクション1つ**。目的を1文で言えない画面は分ける。一方、同じ目的のための確認だけを別画面へ送り、遷移を増やさない。
- 主要フローは原則**3操作・30秒以内**。各段階で求める判断は1つにし、例外・詳細・低頻度設定は段階的に開示する。超える場合はT2へ実測値と業務上の理由を残す。
- ボタン・ラベル・見出しは**利用者の業務語による1句**にする。内部用語・技術語を出さず、ボタンは次の行動を表す短い動詞にする。
- **常設の補足説明は0件**。可視DOMへ置ける文章は、見出し・ラベル・値・状態・エラーと次の操作・不可逆警告に限る。業務上必要な補足と開発注記を混同せず、前者もまずラベル・状態・その場の操作へ置き換える。
- 仕様、実装理由、CSS・クラス・トークン・レイアウト・操作規則、デバッグ注記は可視DOMへ出さない。参照カタログの説明文・サンプル固有文言もアプリへコピーせず、開発者向け情報はMarkdown、HTMLコメント、検査へ置く。
- エラーは短く「何が起きたか」と「次にできること」を示し、再試行・修正・戻る等の操作を発生箇所の近くに置く。データ保持の説明は不安が生じる場合だけ1句加える。
- 最頻業務はマニュアルなしで進め、戻る・再入力・同じ確認を反復させない。例外処理は通常経路を分岐だらけにせず、その場で復帰できる形を優先する。

## 4. 表示用データ加工 — DBの値を画面に直接出さない

**原則: その場面で人が頭の中で行う変換を、システムが肩代わりする**(テスラーの法則: 複雑さの総量は減らないので、システム側が背負う)。「この値を見た人は、次に何に読み替えるか」を問い、その読み替え後を表示する。下表は代表例であり、載っていない値もこの問いで導く。

| 生の値 | 画面での形 | 人が行っていた読み替え |
|---|---|---|
| 生年月日 `1985-04-02` | 基準日時点の年齢(例: `2026-04-02時点で41歳`。生年月日は補助表示) | 基準日との差を年齢に |
| 絶対日時 `2026-08-04 14:30` | `1週間前` / `明日 14:30` | 今との前後関係に |
| コード値 `status=2` | 業務の言葉(`進行中`) | コード表の参照 |
| 真偽値 `true/false` | 状態語 + バッジ(`予約済` / `未予約`) | 真偽から業務の意味に |
| 内部ID `usr_8f3a…` | 人が識別できる名称 | IDから対象の同定に |
| 氏名・名称 | よみがな併記(読み上げる場面はよみがなを主に) | 表記から読みに |
| 数量・金額 `12345678` | `¥12,345,678`(単位は列ヘッダー) | 桁の数え直し |
| 単位違いの値(秒・バイト・メートル) | 場面の単位に換算(`3分20秒`・`1.2 MB`) | 単位換算 |
| 複数値の集合 | 件数 + 代表値(`他3件`) | 数えて要約 |
| NULL・0件 | 理由を1行(`未登録` / `対象期間にデータなし`) | 空欄の意味の推測 |

- **加工してはいけない場面**: 突合・監査・Excel出力・入力欄の値。ここは**生値が正**。相対日時や丸めた数値を出すと照合できなくなる。
- 相対表示にしたときは、**正確な値への到達経路を残す**(詳細画面・`title` 属性・ホバー)。
- 加工が「推測で埋める」になっていないか確認する。読み取れない値を推定で表示しない。
- 加工ロジックは**表示用フォーマッタとして1箇所に集約**する(相対日時・状態語・単位付与を画面ごとに書かない)。同じ値が画面によって違う表記になるのが最も混乱する。

### 4-1. 画像の採否と強調 — 役割が言えない画像は足さない

画像は先に次のどれかに分類し、その役割が使われる場面の判断を早くする場合だけ置く。

| 役割 | 採否・強調の基準 |
|---|---|
| **識別**(人物・物品・場所の同定) | 名称より早く対象を見つけられるなら主役候補。同じ比率と焦点でトリミングする |
| **証拠**(原本・写真・領収書・スクリーンショット) | 判断に必要な部分を切らず、原寸または原本への到達経路を残す |
| **説明**(図解・手順・比較) | 本文の理解を短縮するなら採用。近接する見出しまたはキャプションで「何を読む図か」を示す |
| **装飾**(雰囲気だけを足す) | タスクへの寄与が言えなければ原則削除。残す例外は `alt=""` とし支援技術からも装飾として扱う |

- **alt**: 識別・証拠・説明は画像の目的と内容を簡潔に記す。周辺テキストの重複読み上げは避ける。
- **キャプション**: 撮影日・出典・比較条件・証拠の文脈が必要な場合に付ける。altと同文を繰り返さない。
- **トリミング**: 識別画像は焦点と比率を反復し、証拠・説明画像は判断に必要な範囲を切らない。
- **4幅検収**: 375/768/1280/1600pxで、重要部分の欠落・読めない画像内文字・不要な拡大・レイアウトシフトがないかを実測する。幅と高さまたは `aspect-ratio` を予約する。

## 5. 表示形式の導出 — カタログから選ばず、場面から導く

**「一覧といえば表」「今風にするならカード」という選び方をしない。形式は Step 0 の1文を判断軸で測った結果として決まる。** カタログ(§5-4)は出発点であり、当てはまるものが無ければ §5-3 で合成・分割・新規採用の手順に進む。

### 5-1. 6つの判断軸(Step 0 の1文から測る)

| 軸 | 問い | 取りうる値 |
|---|---|---|
| ① 主目的 | この画面で人は何をするか | 読む / 探す / 比較する / 打ち込む / 選ぶ / 流れを追う |
| ② 1件あたりの情報量 | 一度に見せる項目数 | 1〜3 / 4〜8 / 9以上 |
| ③ 件数と一覧性 | 一度に俯瞰する件数 | 〜10 / 〜100 / 100以上 |
| ④ 識別の主役 | 人は何を手がかりに対象を見つけるか | テキスト / 数値 / 画像 / 位置 / 時刻 |
| ⑤ 項目間の関係 | データ同士は何でつながっているか | 独立 / 順序 / 階層 / 時間 / 空間 / 状態遷移 |
| ⑥ 求められる操作 | 一覧の上で何をするか | 閲覧のみ / 並べ替え・絞り込み / その場編集 / 一括処理 / 手で並べ替え |

6軸を Step 0 の1文から埋める。埋まらない軸があれば、場面の1文が不足している(§2 Step 0 に戻る)。

### 5-2. 導出ルール(上から順に評価し、最初に該当したものを骨格にする)

1. **⑤の関係が支配的なら、まず関係を写す器を選ぶ。** 時間=タイムライン/カレンダー、空間=地図、状態遷移=かんばん、階層=ツリー。関係を持つデータを平坦な一覧に落とすと、人が頭の中で関係を再構成することになる。
2. **①が「打ち込む・突き合わせる」なら表。** 同じ項目を縦に何十件も比較・入力する動作は2次元格子が最速。ここでカード化しない。
3. **④が画像・位置なら、その手がかりを最大化する器**(グリッド・地図)。テキストを主にしない。
4. **②が1〜3項目かつ③が多いならリスト。** 縦1列・下罫線1本が最も件数に強い。
5. **②が4〜8項目で、件ごとに操作・状態がある**ならカード。1件が独立した意思決定の単位になる場合。
6. **②が9項目以上なら、まず一覧から減らす。** 第一階層は原則3項目に絞り、残りは詳細画面へ送る。突合・比較・入力で超過する方が速い場合は、場面と理由をT2または同等正本に残し、表など一覧性の高い形式を使う。
7. **①が「比較する」で対象が2〜3件なら、器より数字。** 「先月 11.2% → 今月 18.6%(+7.4pt)」がバーや表より速い(`components.md` §10)。
8. 上のどれにも決まらない → §5-3。

### 5-3. 該当が複数/どれも当てはまらないとき

- **合成する**: 原則は主形式を1つ決め、他は従属要素として埋め込む(表の行内にサムネイル、カード内にミニ表)。対等な2形式が同時に必要な例外は、それぞれの判断上の役割と、分割・切替より早い理由をT2または同等正本に残して採用する。
- **分割する**: 軸①が2つ以上ある(読む画面と打ち込む画面が同居している)なら、形式ではなく**画面を分ける**。形式の工夫で1画面に押し込まない。
- **切り替えを許す**: 同じデータに正当な2つの見方がある場合のみ、表示切替を置く(一覧/カレンダーなど)。既定はどちらかに決め、選択は記憶する。**逃げとして切替を置かない**(既定が決められない=場面が曖昧)。
- **カタログに無い形を採る3条件**(すべて満たすこと):
  1. **何の関係を写しているか**を1文で言える(軸⑤に対応している)。
  2. **世の中に前例がある**(ヤコブの法則: 利用者は他アプリの慣習を持ち込む)。完全な発明はしない。
  3. **初見で操作が分かる**(§7の4問に装飾だけで答えられる)。
  満たさないなら、既知の形(リストか表)に落とす。
- **迷ったらリストから始める。** 情報量に素直で、SPでも崩れず、後からカード・表のどちらにも寄せられる。

### 5-4. 形式カタログ(**非網羅**・出発点)

| 形式 | 写している関係・強み | 典型的な軸の組み合わせ |
|---|---|---|
| 表(テーブル) | 同一項目の縦比較・入力 | ①打ち込む/比較する ②4以上 ③〜100+ ⑥並べ替え・その場編集 |
| リスト | 並び順・件数への強さ | ①探す/読む ②1〜3 ③多い ④テキスト |
| カード | 1件=1つの意思決定単位 | ①読む/選ぶ ②4〜8 ③〜100 ⑥件ごとの操作 |
| グリッド | 見た目での識別 | ④画像 ①探す |
| タイムライン | 出来事の前後関係 | ⑤時間 ①流れを追う |
| カレンダー | 日付上の配置と空き | ⑤時間 ①選ぶ(予約・空き確認) |
| かんばん | 状態遷移と手での移動 | ⑤状態遷移 ⑥手で並べ替え |
| ツリー | 包含・階層 | ⑤階層 ①探す |
| 地図 | 位置関係 | ⑤空間 ④位置 |
| マスタ-ディテール(分割ビュー) | 一覧を保ったまま1件を深く見る | ③多い + ②9以上 の両立が必要なとき(PC幅のみ) |
| 詳細(定義リスト) | 1件の全項目の対比 | ②9以上 ③1件 |
| ウィザード | 判断の順序 | ①打ち込む ⑤順序 判断が多段 |
| チャート | 量・推移・構成比 | ①比較する ③多い(`components.md` §10 の3条件を満たすときだけ) |

### 5-5. 形式にかかわらず守ること

- **一括操作が業務要件にある一覧は、形式を問わず選択を成立させる**(全選択・選択バー・範囲選択)。カード・グリッド・かんばんでも同じ。一括選択の標準装備は体験設計の規律が優先し、「見た目のためにチェックボックスを消す」は認めない。
- 1件あたりの**第一階層は原則3項目まで**(名前・キー数値・状態)。残りは詳細か折りたたみへ送る。突合・比較・入力で超過する方が早い場合は理由をT2または同等正本に残す。
- 区切りは**下罫線1本または余白**。格子罫線は使わない。行数が多く横に目で追う表だけ、平賀の `--table-stripe-bg` で交互行を付けてよい(任意の色で塗らない)。
- 行アクション(編集・削除)は**常時表示か明示の「…」メニュー**。hoverでしか出さない(タッチで発見不能)。
- SPでは形式を切り替えてよい(PC=表/分割ビュー → SP=カード/リスト)。切替は**コンテナクエリ**で書く(`layout-responsive.md` §3・§4)。
- 並び順は場面から決める。「最新を見ることがほとんど」なら降順を既定にする。

### 5-6. 採用前の検証(これを通していない形式選定は未完了)

1. **実データ・実件数で見る**: 0件 / 1件 / 10件 / 想定最大件数。0件と1件で間延びしないか、最大件数でスクロールが破綻しないか。
2. **文字量が2倍でも崩れないか**(名称が長い実データ・多言語化)。コンテナクエリで耐える。
3. **4幅で実測**(375/768/1280/1600px)。SPで形式を変えるならその理由が言えるか。
4. **1文テスト**: 「この形式でないと、誰の何が何秒遅くなるか」を言えるか。**言えなければ既定形式(リストか表)に戻す。** 好みで選んだ形式は入れない。

## 6. 配置の4原則 — グループ化を視覚に落とす

Step 3〜4 で決めた「群と優先順位」を、**装飾ではなく配置で**表現する手段。迷ったらこの4つに戻る。

| 原則 | 意味 | 実装 |
|---|---|---|
| **近接** | 関係あるものを近づけ、無関係なものを離す | 群内 `gap-1〜2` / 群間はその2〜3倍。線を引く前に余白で分ける |
| **整列** | 見えない縦のラインを通す | 左端を揃える。中央揃えを多用しない。数値は右揃えで桁位置を揃える |
| **強弱(対比)** | 差をつけるなら中途半端にせず大胆に | 主役:本文=2.5倍以上。1.2倍差はメリハリではなくノイズ |
| **反復** | 同じ意味のものは同じ見た目で繰り返す | 値/ラベル/単位の描き分け・バッジ・ボタン階層を全画面で統一 |

- **線と背景色は最後の手段**。近接と整列で群が読めるなら罫線は要らない。線を1本引く前に、余白を倍にして解決しないか試す。
- 視線の起点は**左上**。優先度の高い情報とページの主役をここに置き、CTAは慣習どおりの位置に置く(`typography-numerals.md` §4)。
- 反復が崩れると「同じものが違って見える」。1画面で例外を作らない。

## 7. 装飾は意味を伝えるためだけに使う

装飾で答えるのは次の4問だけ。それ以外の装飾は足さない。

| 伝えたいこと | 手段 |
|---|---|
| ここは押せる | `action-primary-bg` 塗り/罫線ボタン + 動詞ラベル、リンクは `link` +下線(`typography-numerals.md` §4) |
| いま選択中である | `surface-selected` の面 + `border-control`(表の選択行は `table-selected-*`)。色だけに頼らずチェック状態も見せる |
| ここが重要である | サイズと太さ(色を足さない)。主役は1画面1つ |
| ここに機能が隠れている | 「…」メニュー・`<details>` の開閉記号など、開くことが分かる形 |

**彩りとして入れがちな禁止リスト**(いずれも `SKILL.md` §4 の絶対ルールに接続):

- 表ヘッダーのブランド色ベタ塗り + 白抜き文字 → ヘッダーは `--table-head-bg`(淡い面)+ `--table-head-text` の太字 + 下罫線。
- 任意色の交互塗り → 下罫線1本 + 必要なら `--table-stripe-bg`、hoverは `--table-hover-bg`。
- カテゴリ・分類ごとの色分け(色相が増える) → チップ/バッジの塗り・罫線・打消し線で区別(`components.md` §3)。
- カード左端の色帯 → 禁止(恒久ルール)。
- 「それらしさ」のためのアイコン → 迷ったらアイコンなし(`components.md` §8)。

新しい装飾を足したくなったら「**4問のどれに答えているか**」を言う。言えないものは足さない。

## 8. 既存画面のリライト手順(改善指示を受けたとき)

「見づらい」「ダサい」と言われた画面は、**装飾を足して直らない**。§1で症状を特定したうえで、次の順で戻す。装飾の追加は最後まで行わない。

1. **剥がす** — 症状5の装飾(ブランド色のベタ塗り・任意色の交互塗り・分類色・格子罫線・飾りアイコン)を全部外し、白地+罫線1本の素の状態に戻す。ここで画面が読みやすくなることが多い。
2. **場面を書く** — Step 0 の1文を書く(既存画面は「誰がいつ使うか」が曖昧なまま作られていることが多い)。実データと実件数を用意する。
3. **削る** — その場面で使わない項目・飾りの統計・説明文を落とす。削った項目は詳細画面か折りたたみに退避させ、消さない。
4. **束ねて順位をつける** — Step 3〜4。ここで初めて「何が主役か」が決まる。
5. **加工する** — Step 5。生値のまま出ている項目を表示用に変換する。
6. **器を選び直す** — §5 で導出し直す。形式ごと替えるべきなら替える(部分的な手直しで済ませない)。
7. **機能を戻す** — 元画面にあった操作を漏れなく戻す。**このとき機能を落とさない**(見た目のために操作を消すと業務が止まる)。落とす提案をする場合は理由とともに明示して合意を取る。
8. **意味の装飾だけ足す** — §7の4問に答える装飾のみ。
9. **並べて比較する** — 変更前/変更後を同じ実データで並べ、「どの判断が何秒速くなるか」を言葉で説明できることを確認する。説明できない変更は好みの問題であり、入れない。

## 9. 本書に前例がない要件への適用(自己拡張の手順)

**新しい画面種別・新しいデータ・見たことのない要求に当たったとき、「本書に載っていない」で止めない。** 次の手順で導き、通常の判断と前例のない例外を分けて残す。本書は事例を増やすことではなく、この手順が回ることで対応範囲が広がる。

1. **原理に還元する** — 迷ったら次の4つだけに戻る。ほぼ全ての設計判断はここから導ける。
   ① 使われる場面の1文(§2 Step 0) ② 情報の群と優先順位(Step 3〜4) ③ データの関係を写す器(§5) ④ 意味だけを伝える装飾(§7)。
2. **判断軸で測る** — §5-1 の6軸は一覧以外にも使える(下表)。軸が埋まらないなら、要件のヒアリングが足りていない。
3. **前例を探す** — 世の中で確立した慣習を先に探す(ヤコブの法則)。独創は操作体系ではなくコンテンツで発揮する。
4. **最小で作って実データで検証** — §5-6 の4つの検証(実件数・文字量2倍・4幅・1文テスト)を通す。通らなければ既定形式に戻す。
5. **判断の種類に応じて記録する** — 通常の表示形式・ラベル・加工・画像の判断は標準の `docs/product/T2-experience-spec.md`(プロジェクトに同等責務の既存正本がある場合はその正本)に残す。**前例のない例外だけ** `docs/product/design-decisions.md` を必要に応じて作成し、「**場面の1文 / 選んだ形 / 決め手になった軸 / 却下した候補と理由**」を1行で残す。次に同種の画面を作るときはT2または同等正本を先に読み、例外判断が関係するときだけ `design-decisions.md` も読む。
6. **3回使われた判断はスキルに昇格させる** — 同じ判断が3画面で繰り返されたら、本書または該当リファレンスに規律として書き足す(`skill-creator` を使う)。事例のまま放置しない。
