# 入力の実装作法(SKILL.md §4 の詳細)

体験設計の全体像・§4の要旨は `../SKILL.md` を参照。ここでは入力フォーム実装時の具体パターンを扱う。

## 4-1. 入力中の状態保存(下書き) — 入力を絶対に失わせない

**リロード・誤タップ・画面遷移・エラーで入力が消えるのは最悪のUX。入力欄が2つ以上あるフォームには下書き保存を標準装備する。**

1. **自動保存**: 入力のたびに debounce 500ms〜1s で `localStorage` に保存(キーは `アプリ名:フォーム名:v1`)。ログイン済み・複数端末要件ならサーバー下書きに昇格。
2. **復元は黙ってやらない**: 再訪時は下書きを流し込んだ上で「入力途中の下書きを復元しました」+**破棄ボタン**を明示する。黙って復元すると「なぜ埋まっているのか」が不安になる。
3. **保存の可視化**: 常時自動保存するエディタ型UI(Notion/Google Docs/しずかなインターネット型)は保存ボタンを置かない代わりに「保存済み 12:45」の状態表示を常設する。保存失敗も正直に出す。
4. **後始末**: 送信成功で下書きを必ず削除。TTL(例: 7日)で古い下書きを破棄。個人情報を含む下書きはローカル保存の是非を要件で確認する。
5. モーダル/ステップUIも同様: 閉じる・戻るで入力を破棄しない。破棄されるときだけ確認を挟む。
6. `beforeunload` 警告は最後の砦。自動保存があれば原則不要(警告で引き止めるより、消えない仕組みにする)。

実装は `assets/ux-patterns.tsx` の `useDraft`(コピーして使う)。

## 4-2. 気が利く入力の作法(安定実装パターン)

- **オートフォーカス**: 画面の目的が入力なら最初のフィールドに自動フォーカス(SPはキーボードが即開いて邪魔にならない文脈のみ)。
- **バリデーションのタイミング**: 入力中に赤くしない。**判定はblur時、解除は修正中リアルタイム**(reward early, punish late)。
- **送信ボタンをdisabledで黙らせない**: 押させて、最初のエラーへスクロール+フォーカス。
- **IME配慮(日本語必須)**: 変換確定のEnterで送信しない(`isComposing` / `compositionend` を確認)。日本語入力中のキーハンドラ暴発を防ぐ。
- **送信トリガの規律(Enter即送信を避ける)**:
  - 不可逆・対外的な送信(メール・投稿・登録)は**Enterで即送信しない**。誤送信は取り返しがつかない。
  - 複数フィールドのフォーム: Enterは**次のフィールドへ移動**(最後のフィールドでも送信しない)。送信は主要CTAボタンだけ。
  - テキストエリア: Enter=改行。**⌘+Enter(macOS)/ Ctrl+Enter(Windows)を送信のアクセラレータ**として併設する(GitHubコメント・Nani翻訳等で確立した慣習)。OS判定(`navigator.platform`)で⌘/Ctrl表記を出し分ける。
  - 修飾キー送信は**あくまで加速装置**。主経路は常に見えるボタンで、修飾キーを知らなくても困らないこと。ショートカットは**キーキャップUIでボタン近傍に表示**して隠し機能にしない(見た目は jp-web-design `references/motion-a11y.md` のキーキャップUI節)。
  - 検索・絞り込みのような**可逆な操作はEnter実行してよい**(単一入力欄+Enterは慣習)。
- **貼り付けに寛容**: スペース・ハイフン・全角・カンマ混じりを受けて正規化(ポステルの法則)。自動整形でカーソル位置を壊さない。
- **属性を正しく**: `autocomplete` / `inputmode` / `enterkeyhint` を用途通りに付ける(住所・メール・電話はブラウザの自動入力を活かす)。
- **前回値・履歴から選ばせる**(認識>想起)。同じ値を2度打たせない。

実装は `assets/ux-patterns.tsx` の `useSubmitKeys` / `useLateValidation`。

## 4-3. 動作とデザインの一致

「押したら何が起きるか」を見た目が予告し、実際の挙動がそれを裏切らないこと(Zenn/しずかなインターネット開発者 catnose の設計原則)。

- 遷移するのか・その場で保存されるのか・時間がかかるのかを、ボタンの見た目とラベルが先に伝える。時間がかかる処理は「かかる」と見せる(SKILL.md §11)。
- UIを最初に作り、**自分が最初のユーザー**として最頻フローを実データで毎日通す。ユーザーに聞く前に自分が違和感に気づける状態を保つ。
- 機能は最小限に保つ。**機能追加は負債になりがち** — 「使わない機能をつけない」を維持し、使われない機能は削る(削減提案は成果)。

## 4-4. 入力の作法をシステム内で統一する(自動計算値の扱いを含む)

**同一システム内で入力の作法を分岐させない。** タブ・ステップごとに空欄の意味(未入力か0か)・初期値の入れ方・保存の単位が違うと、利用者は画面を移るたびに「ここはどうだったか」を思い出す必要が生じる。実装都合の一貫性より、**利用者から見た一貫性**を優先する(原則: 記憶させず認識させる)。

1. **自動計算値は欄の中に初期値として入れる**。欄外に別表記で添えるのは最悪 — 欄の中と外で視線が往復し、しかも「この空欄は未入力なのか自動なのか」が判別できない。
2. 欄に自動値を入れる場合は、**「自動のまま」と「人が入れた」を見た目とデータの両方で区別する**(薄い文字+印 ↔ 通常の文字。データ側にも由来を持つ)。見た目だけの区別にすると、**触っていない値を確認済みとして確定**してしまう。由来をデータで持つ設計は SKILL.md §8・app-excellence `references/data-lifecycle.md` §1 と同じ考え方。
3. 各欄に「**自動に戻す**」を添える(§5-3 の「戻せる」を欄単位で成立させる)。
4. **入力部品は共通化し、ステップごとに同じ実装を書かない**。Enterで次の欄(§4-2)・表計算からの貼り付け・単位表示・桁区切りは1箇所に集約する。同じ挙動を2箇所に書いた時点で、いずれ片方だけ直る。

## 4-5. 一覧入力の視線移動(数十〜百件を上から打つ画面)

表形式で「見る対象(参照する値)」と「入力する欄」が横に大きく離れると、**行ごとに視線が画面を横断する**。これは1件では気づかず、50件目で疲労として現れる。

- 参照列と入力列を近づける。離さざるを得ないときは**列幅・区切り・行のホバー強調**で行を追跡できるようにする。
- **数値は右揃えで桁位置を縦に揃え、等幅数字(`tabular-nums`)を使う**。入力中に桁がガタつかないこと(jp-web-design §3-3)。
- 補助文言・注意書きが**主動線(上から下への打鍵)を分断しない位置**に置く。行間に説明を挟まない。
- **判断基準: 担当者が数十〜百件を上から順に打ち込むとき、手も目も止まらないか**。装飾を足す方向ではなく、迷いと視線移動を減らす方向で判断する。実データ相当の件数で自分が打ってみて決める(SKILL.md §13)。
