# 02. Experience Design — 体験は「原則→心理学→状態」の3段で設計する

このプレイブックの役割は、センスを工程に変換すること。Apple/Netflix/LINE/GOから抽出した原則を**判断が割れたときの優先順位付きルール**として定義する。

## §1. 体験10原則(競合したら番号の若い方が勝つ)

1. **速さは最上位の機能である**(Netflix)。0.4秒(Doherty閾値)を超える待ちには必ず反応を返す。体感速度 > 実速度: 楽観的UI・スケルトン・先読みで「待たされた記憶」を作らない。
2. **システムの状態を常に見せる**(GO)。いま何が起きているか・次に何が起きるか・あとどれくらいかを画面が語る。不確実なものは隠さず予測として見せる(「およそ3分」)。
3. **確認より取り消し**(Apple)。「本当に削除しますか?」を増やすのではなく、Undo・ゴミ箱・下書き自動保存で失敗を無害化する。破壊的操作のみ確認を残す。
4. **選択肢を減らす**(Hick's law / Netflix)。1画面の主要アクションは1つ、選択肢は5つ以下。減らせないなら段階的開示(progressive disclosure)で隠す。賢い既定値を必ず入れる。
5. **親指で完結させる**(LINE)。主要操作は画面下半分・44pt以上のタップ領域。片手・移動中・電波1本を標準の利用状況と想定する。
6. **プラットフォームの慣習に従う**(Jakob's law)。ユーザーは人生の大半を他のアプリで過ごしている。独創はコンテンツで発揮し、操作体系では発揮しない。
7. **記憶させない、認識させる**。入力済みの再入力を求めない。選ばせるときは思い出させず見せて選ばせる。前回の続きから再開できる(Zeigarnik: 中断は必ず保存)。
8. **文字より状態で伝える**(LINE)。説明文を書く前に、レイアウト・色・アイコン・既定値で伝えられないか考える。書くなら短く、ボタンは動詞(「保存する」)。
9. **ピークとエンドを設計する**(peak-end rule)。ジャーニーで最も感情が動く1点(ピーク)と完了の瞬間(エンド)を明示的に設計する。例: 集計が一瞬で出る驚き+「今月は20時間節約できました」で締める。
10. **通知は礼儀**(LINE)。ユーザーの利益になる通知だけを、本人にだけ、適切な時刻に。既定はオフ寄り。バッジと督促で行動を強制しない。

## §2. UX心理学の適用ルール(詳細は references/checklists/ux-psychology.md)

心理学は**ユーザーの目標達成を速く・楽に・確実にするためだけ**に使う。エンゲージメント延命・誤クリック誘発・解約妨害への使用は禁止(倫理ガードと法的リスク: 景表法・特商法)。主要な適用点:

- **初回体験**: 最初の5分で「自分の課題が解決される」実感(Ahaモーメント)まで最短導線を引く。空状態はチュートリアルを兼ねる(§3)
- **進捗**: 複数ステップにはプログレス表示+endowed progress(既に進んでいる状態から開始)。goal gradientはゴール直前の後押しに
- **不安の除去**: 操作の可逆性を明示(「あとで変更できます」)、待ち時間には理由(「集計を計算しています」)
- **習慣化**: トリガー(業務の自然な瞬間)→行動(30秒で完了)→報酬(即時の見える成果)の環を設計。ただしストリークやFOMOで縛らない

## §3. 状態設計 — 全画面に6状態を定義する(UIスタック)

「正常系だけデザインされた画面」を禁止する。T2で全画面に以下を定義する:

| 状態 | 設計基準 |
|---|---|
| 理想 | データが十分にある状態。ここだけ作って終わらない |
| **空** | 初回訪問の顔。次にすべき行動を1つ提示(CTAつき)。イラストより行動 |
| ローディング | 0.4秒超はスケルトン(スピナーより体感が速い)。1秒超は進捗+理由 |
| 部分 | データ1〜2件でも間延びしないレイアウト |
| エラー | ①何が起きたか②データは無事か③次に何をすべきか、を平易に。再試行ボタン必須。技術用語・エラーコードを主文に出さない |
| オフライン/低速 | 閲覧は可能に(キャッシュ)。入力は保持して再送(消さない) |

## §4. ジャーニー設計の手順

1. T1のL3(to-beシナリオ)を画面遷移図に落とす(主要ジャーニーは3タップ/30秒以内を目標)
2. 各画面に §3 の6状態と、§1原則の適用点を注記
3. ピーク/エンド(原則9)の位置を1つずつ指定
4. マイクロコピーと手数は jp-web-design `references/information-design.md` §3-1 の認知負荷契約を正本として検収する(本書では重複定義しない)
5. **各画面の情報設計を工程で通す**(Skill `jp-web-design` `references/information-design.md` §2): 使われる場面の1文 → ラベル剥がし → **伝わらないものだけ最小限補う** → グループ化(原則3〜4群。超過理由は記録) → 優先順位 → 表示用データ加工 → 表示形式の導出(6判断軸) → 機能追加と意味づけの装飾。**表を書くところから設計を始めない**(原則8「文字より状態で伝える」の実行手順にあたる)。通常判断はT2へ記録し、前例のない例外だけ同 §9 の手順で導出して `docs/product/design-decisions.md` に記録する
6. 可視UIありでは jp-web-design `references/catalog-default-contract.md` を読み、同契約が指定するprofileを固定する。profile provenanceをT2へ記録してからデザイントークン(references/04-build-standards.md §1)で見た目を確定する。参考デザイン(Canva・スクリーンショット)があれば色・密度・質感を参考にするが、画面構造は業務から導く。profile選択・明示上書き・`NON_VISUAL`・検査の詳細は同契約だけを正本とする
7. hover / pressed / focus / 入場 / 展開 / 処理中 / 完了・失敗を画面ごとに定義する。動きは因果の説明に限定し、`prefers-reduced-motion` で停止しても意味が残るようにする(jp-web-design `references/motion-a11y.md`)

**ゲート条件(T2)**: 全画面に6状態/ピークとエンドが指定済み/主要ジャーニーが3タップ以内 or 超える根拠が書いてある/**各画面に「使われる場面の1文」と一覧レイアウト形式の選定理由がある**/可視UIはcatalog-default profileのprovenanceがあり、非可視案件は`NON_VISUAL(理由)`がある。
