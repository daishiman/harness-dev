app-orchestrator エージェントを起動して、既存アプリに以下の改善を加えてください。

**まず現在の段階を判定する**: `git fetch --tags --prune` を試み、exact `v1`・`v1.*`・以降のrelease tag、T4等の明示的なv1+ project marker、デプロイ経路・production Environment・default branch保護・PR運用の信号を照合する。**main 直反映は、正本がpre-v1/v0と明示する新規AIDDプロジェクトだけ**。既存repoで確信がない、fetchできない、または信号が矛盾する場合は追加開発モード相当の安全側(ブランチ + PR)で進める。

## 実行ルール

- 必ず Agent ツールで `app-orchestrator` サブエージェントを起動すること。自分で直接実装しない。
- エージェントには、release tag / project marker / デプロイ・保護信号の判定結果を明示して渡す(v1+は「追加開発モード」、明確な新規pre-v1 AIDDは「v0→v1 の育てるループ」、不確実な既存repoは「ブランチ + PRの安全側」)。
- 依頼内容が空の場合: `docs/product/backlog.md`、障害ログ、利用頻度、未完了の導線を調べ、影響度・緊急度・確信度・依存関係・可逆性で採点し、最有力の1件を自動選択する。
- 依頼内容に複数の要望が含まれる場合: 内部で分解・順位付けし、依存関係を満たす最初の1件を選ぶ。比較表を質問として返さない。
- `Evidence → Decide → Draft → Validate → Diff` で、修正パッチ、動作する代表導線、診断レポートのいずれかを先に完成させる。ユーザーには選択肢ではなく、成果物への差分だけを判断してもらう。
- **Cloudflare MCP の user scope 登録と wrangler 実行はエージェントが代行する。OAuth 認証と git 管理外の `.mcp.json` だけ本人が行う**(INV-11)。着手前にエージェントが `claude mcp list` を見て、壊れている登録を `claude mcp add` で自分で直し、git 管理下の `.mcp.json` は差分を提示して承認後に直す(追加開発モード手順0.5)。今回の改善でbindings変更またはobservability調査が必要な場合だけ、その対象1件の `/mcp` 承認を依頼し、未使用MCPの認証は求めない。承認は待たずに作業を進める。
- 質問してよいのは、認証情報、契約・課金、法務、公開、削除、本番データ変更など本人しか決められない境界だけ。その場合もローカルのプレビューまたはdry-runを先に作る。
- v1+ または不確実な既存repoは、追加開発モードの手順0〜6(ブランチ作成→実装→PR→依頼者の了承1回→マージ→デプロイ)で進める。明確な新規pre-v1 AIDDだけブランチと PR を作らず、main 直反映 + push で進める(自動デプロイの選定済み経路があれば push、初回の限定デプロイだけ clean な確定コミットから `wrangler deploy`)。依頼者への確認は「preview で試して問題ないか」の1回だけに抑える。
- エージェント完了後の報告は非エンジニアが読める言葉で書く: 「今回できるようになったこと / 試してほしい操作 / 更新後の残課題リスト / 次の候補」の順にまとめる。git 用語は使わない(app-orchestrator の語彙対応表に従う)。
