# 例外処理・エラー設計・攻撃別対処

Claude CodeがMCP/CLIで自律実装する際、ミドルウェア・バックエンド層で必ず満たす処理品質の基準。

## 1. エラーレスポンス設計（正直だが漏らさない）

| 状況 | クライアントへ返すもの | 返してはいけないもの |
|---|---|---|
| 未認証 | 401 + 汎用メッセージ | 「ユーザーが存在しない」等の存在ヒント |
| 権限なし | 403 + 汎用メッセージ | 必要ロール名・内部判定ロジック |
| 検証エラー | 400 + フィールド別の修正方法 | スタックトレース |
| 見つからない | 404 | テーブル名・クエリ |
| サーバー内部 | 500 + 相関ID | スタックトレース・SQL・環境変数・パス |
| レート制限 | 429 + Retry-After | 制限の内部しきい値詳細 |

原則:
- **本番でスタックトレース・SQL・内部パスをレスポンスに含めない**。開発環境のみ詳細表示。
- エラーには**相関ID**（`crypto.randomUUID()`）を発行し、ログとレスポンスの両方に入れて突合可能にする。
- ログイン失敗は「メールまたはパスワードが違います」に統一（ユーザー列挙防止）。
- 認証・認可チェックは**ハンドラの先頭**で行い、失敗したら以降の処理・DB接続に進まない。

## 2. ミドルウェア層の標準構成（Hono / Workers）

リクエストは必ずこの順で通す:

```text
1. リクエストID発行・ログ開始
2. CORS（許可オリジンは明示リスト。ワイルドカード禁止）
3. セキュリティヘッダー付与
4. ボディサイズ上限（例: 1MB。ファイルアップロードは別途）
5. レート制限（cf-connecting-ip基準）
6. 認証（セッション検証）
7. 認可（ロール・テナント境界）
8. 入力バリデーション（zod。parse失敗は400）
9. ハンドラ本体（try/catchで囲み、未捕捉例外は500+相関IDに変換）
```

- グローバルエラーハンドラ（Honoなら`app.onError`）を必ず設置し、未処理例外がWorkerのデフォルト応答（詳細漏えいの可能性）に落ちないようにする。
- `waitUntil`に渡すPromiseにも`.catch()`を付ける（floating promiseは例外を握りつぶすか、Workerをクラッシュさせる）。

## 3. 攻撃別対処表

| 攻撃 | 対処 |
|---|---|
| SQLインジェクション | D1は`prepare().bind()`のみ。文字列連結・テンプレートリテラルでのSQL組み立て禁止 |
| XSS | Reactの標準エスケープに任せる。`dangerouslySetInnerHTML`は sanitize必須（DOMPurify）。CSPヘッダー設定 |
| CSRF | SameSite=Lax以上+認証ライブラリ標準のCSRF保護。状態変更はGETで行わない |
| SSRF | ユーザー入力URLへのfetch禁止。必要なら許可ドメインリストで検証。Workersは`*.workers.dev`同士のfetch不可の制約にも注意 |
| オープンリダイレクト | リダイレクト先は同一オリジンの既知パスのみ。ユーザー入力から組み立てない |
| IDOR / テナント越境 | URLやbodyのIDを信用せず、ログインユーザーの所有権をDBで毎回確認 |
| ブルートフォース / credential stuffing | 認証エンドポイントにレート制限（IP+アカウント両方）。失敗回数でバックオフ |
| DoS / コスト攻撃 | ボディサイズ上限・ページネーション必須・Turnstile（公開フォーム）・Cloudflare WAF/rate limiting rules |
| パストラバーサル | ファイルパスをユーザー入力から組み立てない。R2キーは正規化+プレフィックス固定 |
| プロンプトインジェクション（LLM組込時） | ユーザー入力をシステム指示と分離。ツール実行権限を最小化。詳細はSkill llm-api-integration |

## 4. 回復性（Resilience）

- **外部API呼び出し**: タイムアウト設定+指数バックオフ付きリトライ（最大3回）。無限リトライ禁止。
- **べき等性**: 決済・送信系は重複実行を防ぐ（クライアント生成のidempotency key、または処理済みフラグ）。
- **グレースフルデグラデーション**: LLM APIや外部サービスが落ちてもアプリの主要機能は動く設計。エラー時は「後で再試行」導線を出す。
- **データを消さない**: 削除は論理削除（status変更）を基本とし、物理削除はユーザーの明示操作+確認に限る。
- **D1クォータ超過**: 無料枠超過はエラーになる（自動課金ではない）。超過時のユーザー向けメッセージを用意し、翌日9:00 JSTリセットを案内できるようにする。

## 5. ログ設計

- 出力する: リクエストID、メソッド+パス、ステータス、所要時間、内部ユーザーID、重要操作の監査ログ
- 出さない: トークン、Cookie全文、Secret、Authorizationヘッダー、個人情報の本文、パスワード
- Workers Logs無料枠は20万イベント/日・保持3日。重要操作のみ記録し、リクエスト毎の冗長ログを出さない
