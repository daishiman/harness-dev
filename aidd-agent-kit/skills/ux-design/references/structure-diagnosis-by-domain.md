# 業務構造診断のドメイン別読み替え(§0-1 / §2-3 / §11-1 / §13-1 の補足)

SKILL.md の業務構造診断(§0-1 業務構造 → §2-3 主役と隠すもの → §11-1 操作感 → §13-1 装飾除去テスト)は、どの業務ドメインにも同じ順序で適用できるよう抽象化してある。ここでは、扱う対象の性質によってチェックの重心がどう変わるかを補足する。**値や具体的なコンポーネント名を指定するものではなく、どこに注意を向けるかの読み替え表**である。

## ドメインの性質による重心の違い

業務画面は、中心対象の性質によっておおよそ3つの傾向に分かれる。実際の画面は複数の傾向が混ざることが多いが、**その画面で今どの傾向が支配的かを最初に見極めると、§2-3 の判断が速くなる。**

### 一覧・比較が中心の画面(多数の対象を並べて判断する)

- [ ] 1画面で同時に見比べる必要がある件数は、実際どれくらいか(体感ではなく実データで確認したか)。
- [ ] 比較に使う列・属性は、業務上どれが判断材料でどれが補足情報か区別できているか。
- [ ] 個別の対象を掘り下げる操作(詳細確認・軽微な編集)は、一覧から**離れずに**行えるか。
- [ ] 複数対象へのまとめた操作(絞り込み・一括変更)の手数は、対象が増えても線形以上に増えないか。

### 単票・入力が中心の画面(1件を深く扱う)

- [ ] 1件を最後まで処理するのに必要な情報は、今どのくらいの手順・画面数に分かれているか。まとめられる境界はどこか。
- [ ] 入力の主経路(最頻パターン)と、まれにしか使わない例外項目が、同じ強さで並んでいないか。
- [ ] 処理の状態(下書き・保存済み・確認待ち・確定)が、ユーザーに常に見える位置にあるか。
- [ ] 誤り・中断からの再開が、最初からやり直しにならずに済むか。

### 分析・把握が中心の画面(状況を俯瞰して次の判断につなげる)

- [ ] 表示している数字・グラフのそれぞれが、**見た人に何をさせたいのか**を言えるか(言えない指標は装飾)。
- [ ] 俯瞰した結果、例外や要対応が見つかったとき、そこから個別対応の画面へ**何手で**到達できるか。
- [ ] 定常的に見る値と、たまに深掘りする値が、同じ優先度で並んでいないか。
- [ ] 更新頻度・鮮度が異なる指標を、同じ見た目で並べていないか(鮮度の違いが伝わるか)。

### 操作感が中心の画面(一連の操作の手応え・進め方を検討する)

- [ ] 一覧型: 即応性より**一括操作の効果**(何件をまとめて処理できるか)が体感を左右していないか。
- [ ] 単票型: 途中で止めても後で**同じ状態から再開できるか**(下書き保存・戻る操作の可逆性)を確認したか。
- [ ] 分析型: 処理に時間がかかる操作(再集計・大量データの再描画)に対し、**待たされている実感**をユーザーがどこまで許容できるか見積もったか。

## 迷ったときの原理への還元

この手順は**画面構造の判断**(§13-1 装飾除去テストを通らなかった場合の切り分け)を対象とする。表示形式(グラフか表かカードか等)の選定を対象とする jp-web-design `references/information-design.md` §9の「前例のない要件」手順とは適用範囲が異なるため、混同しないこと。

前例のない要件、あるいはどのパターンにも当てはまらない画面に出会ったときは、次の順で考える。

1. **その画面で最も長い時間を占める作業は何か**を特定する(観察・推測でよいので言語化する)。
2. その作業を**今、何が邪魔しているか**(画面遷移・視線移動・情報の探索・確認の往復)を洗い出す。
3. 邪魔を取り除く方向で構造を選ぶ。既存のコンポーネントカタログから見た目を先に選ばない。
4. 選んだ結果を、なぜその形式にしたか1行で残す(却下した候補も添えられるとよい)。

## §13-1(装飾除去テスト)を通らなかったときの戻り先

- 情報の重要度が伝わらない → §0-1(中心対象・最頻操作)の特定が曖昧なまま進んでいる可能性が高い。
- 主作業領域が一つに定まらない → §2-3 の「主役」が複数存在している。ページや領域を分けるべきかを検討する。
- 操作してみないと結果が分からない → §11-1 の予測可能性・操作可能性が不足している。
- 装飾を外すと単に殺風景で終わる(問題は感じないが魅力もない) → これは合格の一種。装飾は構造を補強する最後の工程であり、§13-1 通過後に加えてよい。
