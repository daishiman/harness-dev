# PR / Issue テンプレートと記入例

SKILL.md §2・§5 の詳細版。実際に書くときに参照する。

---

## PR本文の設計思想

PRを読む人は2種類いる。**同じPRを、違う読者が違う目的で読む**。

| 読者 | 知りたいこと | 読むところ |
|---|---|---|
| 依頼者・利用者(非エンジニア) | 何が良くなるのか。頼んだものになっているか | §1〜§5 |
| 実装者(3ヶ月後の自分・将来の担当者) | なぜこの実装なのか。どこまで影響するか | §6〜§8 |

だから本文は上半分と下半分で**書き分ける**。上半分に専門用語を混ぜると非エンジニアが読むのをやめ、下半分を省くと将来の自分が実装意図を復元できなくなる。

テンプレート実体は `assets/PULL_REQUEST_TEMPLATE.md`(リポジトリの `.github/PULL_REQUEST_TEMPLATE.md` に設置すると `gh pr create` が自動で読み込む)。

## 記入例(良い例)

```markdown
## 1. 目的 — 何のためにやったか

評価シートを紙に印刷して配れるようにするため。

## 2. 背景 — なぜ必要だったか

評価面談では紙の評価シートを見ながら話す運用が続いており、
現状は画面をそのまま印刷するしかない。しかし印刷すると左のメニューまで
紙に写り込み、1人分がA4で2枚に割れてしまう。
面談前に人数分を手作業で整える時間が毎回30分ほど発生していた。Closes #12

## 3. やったこと — 中学生にも分かる説明

これまでは、パソコンの画面をそのまま写真に撮って紙にしていたようなものでした。
画面の左側にはいつも操作用のメニューが出ているので、それも一緒に紙に写り込み、
本文が右にずれて、1人分が紙2枚に分かれてしまっていました。

今回は「印刷するとき専用の見た目」を用意しました。印刷ボタンを押したときだけ
メニューや画面上部の帯を消して、評価シートの中身だけが紙に載るようにしています。
文章がとても長い人でも紙1枚に収まるように、文字の大きさを自動で少しだけ
小さくする仕組みも入れました。

## 4. できるようになったこと

- 評価シート画面から印刷ボタン1つで印刷できる
- 1人分が必ずA4縦1枚に収まる(手作業の調整が不要になる)
- コメントが長い人でも、切れずに全文が印刷される

## 5. 含めたこと / 含めていないこと

**含めたこと**
- 評価シート画面(1人分)の印刷
- 印刷時のメニュー・ヘッダーの非表示
- 長文コメントの自動縮小(最小10ptまで)

**含めていないこと(今回はやらない)**
- 複数人まとめての一括印刷 — 今回の面談運用では1人ずつ呼び出して印刷するため不要。
  必要になったら #20 で対応する
- PDFでの保存 — 印刷ダイアログの「PDFとして保存」で代替できるため見送り
- Firefox対応 — 余白の扱いが他ブラウザと異なり崩れる。利用対象がChrome/Safariのため
  今回は許容し、#19 に残課題として起票済み

---

## 6. 技術的にやったこと(エンジニア向け)

**変更の要点**
- `src/routes/evaluation/[id]/+page.svelte` に印刷ボタンを追加し `window.print()` を呼ぶ
- `src/app.css` に `@media print` ブロックを追加。`.sidebar` `.app-header` を `display: none`、
  `@page { size: A4 portrait; margin: 12mm }` を指定
- `src/lib/print/fitToPage.ts` を新規追加。印刷前に本文の実高さを計測し、
  1ページを超える場合のみ `font-size` を 13px → 12px → 11px → 10px の順に段階的に縮小

**設計判断**
- 印刷専用ページ(`/evaluation/[id]/print`)を別途作る案も検討したが、
  評価シートの表示ロジックが二重管理になるため不採用。`@media print` で同一コンポーネントを
  使い回す方が、項目追加時の修正漏れが起きない
- 自動縮小をCSSの `zoom` ではなくJSでの段階縮小にしたのは、`zoom` がSafariの印刷で
  無視されるため。実測で確認済み

**影響範囲**
- 画面層のみ。DB・APIの変更なし、マイグレーションなし
- `app.css` の `@media print` は全画面に効くため、他画面の印刷時もサイドバーが消える。
  意図した挙動(他画面も印刷でメニューは不要)

## 7. 確認したこと

- [x] Chrome / Safari の印刷プレビューでA4縦1枚に収まることを確認
- [x] コメント2000字のダミーデータで、全文が切れずに1枚に収まることを確認
- [x] 印刷後に画面表示のフォントサイズが元に戻ることを確認(縮小が残らない)
- [x] `pnpm test` / `pnpm run build` が通ることを確認

## 8. 注意・残課題

- Firefox は `@page` マージンの扱いが異なり余白が広めに出る(#19)
- 一括印刷は未対応(#20)
```

## 悪い例と、なぜダメか

| 書き方 | 問題 |
|---|---|
| §3に「レスポンシブ対応とprint用CSSを追加」 | 非エンジニア向けの欄に専門用語。読む人が読むのをやめる |
| §4に「PrintLayout.tsx を修正」 | ファイル名は§6に書くこと。§4は利用者から見た変化だけ |
| §5「含めていないこと」が空欄 | 「頼んだのにできていない」の食い違いはほぼここが原因 |
| §6「設計判断」が空欄 | 3ヶ月後に「なぜ別ページにしなかったのか」を思い出せず、同じ検討を再度やる |
| §7に「動作確認済み」 | 何をどこまで確認したか不明。再発時に確認漏れか仕様変更かを切り分けられない |
| §2が空欄 | 将来このコードを消していいか判断できなくなる |

### §3を書けないときのチェック

専門用語を使わずに説明できないなら、多くの場合その変更を自分が理解しきれていない。次の問いに答えられるか確認する。

1. これを入れる前、利用者は何をしていたか
2. これを入れた後、利用者は何をするようになるか
3. その差は、利用者の1日のうち何分・何回に効くか

3つとも答えられれば §3 は書ける。

## Issue本文の設計思想

Issueの読者はPRと同じ2種類だが、**時間差**がある。起票した瞬間の自分と、数週間後に着手する自分は別人である。「あのとき何に困っていたか」を復元できないIssueは、結局作り直すか、放置されて閉じられる。

だからPRと同じく上半分(非エンジニア)・下半分(エンジニア)で書き分ける。ただし**下半分は起票時に空欄でよい**。原因の見立ては着手時に埋める。ここまで埋めないと起票できない運用にすると、起票自体が面倒になり、Issueを立てなくなる方が損失が大きい。

テンプレート実体は `assets/ISSUE_TEMPLATE/`(`bug_report.md` / `feature_request.md` / `config.yml`)。

## 記入例 — 不具合(bug)

```markdown
## 1. 何が起きているか

評価シートを印刷すると、1人分が紙2枚に分かれてしまう。

## 2. 本来どうなってほしいか

1人分がA4縦1枚に収まって印刷される。

## 3. 再現手順 — この通りにやると必ず起きる

1. 評価一覧から任意の社員を開く
2. ブラウザの印刷(Cmd+P)を実行する
3. プレビューを見ると、左のメニューが紙に写り込み、本文が右にずれて2枚目に続いている

## 4. どれくらい困っているか

- [x] 手作業で回避できるが毎回手間がかかる

**発生頻度**: 毎回
**影響を受ける人**: 面談を実施する評価者全員(8名)

## 5. 今の回避策

印刷プレビューで倍率を80%に手で下げると1枚に収まることがある。
ただしコメントが長い人は収まらず、その場合はWordに貼り直して整えている。
面談前に人数分やると30分ほどかかる。

---

## 6. 技術メモ(エンジニア向け・分かる範囲で)

**環境**
Chrome 141 / macOS 15 / 2026-08-05 に確認 / /evaluation/:id

**エラー内容**
なし(表示崩れのみ)

**原因の見立て**
print用のスタイルを一切書いていないため、画面表示のレイアウトがそのまま印刷に流れている。
`@media print` でサイドバーを非表示にすれば解決しそう。

## 7. 完了の条件

- Chrome / Safari で、コメント2000字の社員でもA4縦1枚に収まって印刷される
```

## 記入例 — やりたいこと(feat)

```markdown
## 1. 困っていること

評価一覧を見ても、誰の評価が終わっていて誰がまだなのかが分からない。
締切前に未提出者へ声をかけたいが、1人ずつ開いて確認するしかない。

## 2. 背景 — なぜ今それが必要か

半期に1度の評価期間は2週間しかなく、その間に80名分の進捗を追う必要がある。
前回は締切当日に未提出が12名残っていることに気づき、締切を3日延ばした。
次回(2026年10月)までに解決したい。

## 3. こうなっていれば解決(中学生にも分かる説明)

一覧の画面を開いた瞬間に、「終わった人」「途中の人」「まだ手をつけていない人」が
色や印で見分けられる状態。誰に声をかければいいかが、一覧を上から見るだけで分かる。

## 4. 今どうやってしのいでいるか

80名を1人ずつ開いて確認し、Excelに手で転記している。1回あたり約40分。
締切前に3回ほどやるので、半期で2時間ほどかかっている。

## 5. 含めたいこと / 今回は含めなくてよいこと

**含めたいこと**
- 一覧での進捗状態の表示(未着手 / 途中 / 提出済み)
- 未提出者だけを絞り込む

**今回は含めなくてよいこと**
- 未提出者への自動リマインドメール — まず目視で足りるか試したい。
  必要と分かってから別Issueで起票する
- 部署ごとの集計グラフ — 今回の困りごと(誰に声をかけるか)とは別の話

---

## 6. 技術メモ(エンジニア向け・分かる範囲で)

**想定される作業**
評価テーブルに状態カラムがなく、回答レコードの有無から導出している。
一覧APIで件数を集計して返す形にすればスキーマ変更なしでいけそう。

**懸念・確認が必要なこと**
80名分の集計をN+1クエリで回すと一覧の表示が遅くなる。集計クエリ1本にまとめる必要あり。

## 7. 完了の条件

- 評価一覧で各社員の状態(未着手 / 途中 / 提出済み)が一目で分かる
- 未提出者だけに絞り込める
- 一覧の表示が現状より遅くならない(体感1秒以内)
```

## Issueの悪い例と、なぜダメか

| 書き方 | 問題 |
|---|---|
| タイトルだけで本文が空 | 1週間後に自分でも意味が分からなくなる。起票した意味が消える |
| §1が「印刷機能を直す」 | 何がどう困っているか不明。直したつもりでもズレる |
| §3(要望)が「CSVエクスポート機能を追加する」 | 解決策で書いている。実装がCSVに固定され、より安い解決策の道が閉じる |
| §4「どれくらい困っているか」が空 | 優先順位がつけられず、Issue一覧が並列に積まれて選べなくなる |
| §7「完了の条件」が空 | どこまでやれば終わりか分からず、着手後に作業が膨らむ |
| §6を埋めないと起票できない運用 | 起票が面倒になり、Issueを立てなくなる。空欄可にする方が得 |

## ラベル運用

個人開発では**多くても6個**。増やすと分類に迷って結局使わなくなる。

| ラベル | 用途 |
|---|---|
| `bug` | 想定どおり動いていない |
| `feat` | 新しくできるようにしたいこと |
| `chore` | 依存更新・設定・雑務 |
| `blocked` | 自分以外の判断・外部要因で止まっている |
| `someday` | やりたいが今期はやらない。定期的に見直して閉じる |

作成コマンド:

```bash
gh label create blocked --color "d93f0b" --description "他者判断・外部要因で止まっている"
gh label create someday --color "cccccc" --description "今はやらない"
```

## よく使う gh コマンド応用

```bash
# Issueからブランチを作る(番号入りブランチ名が自動生成される)
gh issue develop --repo "$GITHUB_REPOSITORY" 12 --checkout

# 自分に割り当てられた未完了Issueだけ見る
gh issue list --repo "$GITHUB_REPOSITORY" --assignee @me --state open

# PRにIssueを紐付け忘れたときの追記
gh pr edit --repo "$GITHUB_REPOSITORY" 34 --body-file -    # 標準入力から差し替え

# マージ済みPRを一覧で振り返る(週次の棚卸しに使う)
gh pr list --repo "$GITHUB_REPOSITORY" --state merged --limit 20

# CIが通ってから自動でマージする
gh pr merge --repo "$GITHUB_REPOSITORY" --squash --delete-branch --auto
```
