# x-longpost-creator 設計ノート

X (旧 Twitter) の長文投稿を作り、その投稿に添えるサムネイルまで通す plugin の設計記録。
利用手順は [plugins/x-longpost-creator/README.md](../plugins/x-longpost-creator/README.md)、
変更履歴は [CHANGELOG.md](../plugins/x-longpost-creator/CHANGELOG.md) が正本である。
本ノートは「なぜその形にしたか」だけを残す。

## 1. 何を解く plugin か

音声メモの文字起こしとキャッチコピーを渡すと、1800〜2200 文字の長文投稿が
**PC 向け (改行が段落単位) とスマホ向け (1 文 1 行) の 2 パターン**で出てくる。
文章が確定した後、別セッションで X 用 5:2 と note 用 1280x670 のサムネイル 2 枚を作る。

手作業でやると毎回ぶれるのは、文体・文字数・タイトル長・見出し構成・絵文字の有無といった
**数えられる制約**である。ここを人間の注意力に頼るのをやめ、Node スクリプトで機械的に止める。
逆に、テーマの選び方・言い回し・図の構図といった**数えられない判断**は LLM に残す。
この線引きが plugin 全体の設計原則 (Script First / LLM for Creativity) の実体である。

## 2. 5 つの skill に割った理由

| skill | 担当 | effect |
|---|---|---|
| `run-x-longpost-create` | 長文投稿 1 本を作りファイルへ出す | local-artifact |
| `run-x-multipost-create` | 文字起こしから短文 8 本 (+要約型 1 本) | conversation-output |
| `run-x-shortpost-optimize` | 任意の文章 1 本を短文投稿へ整える | conversation-output |
| `run-x-visual-generate` | 確定した投稿から画像を作る | local-artifact |
| `ref-x-longpost-canon` | 規定が食い違ったときの正本索引 | reference |

分割の基準は「入力が違うか」「成果物の置き場が違うか」の 2 点である。
短文 8 本は文字起こしだけで作れて長文を必要としないので独立させた。
画像生成は**課金が発生し、かつ本文が確定した後でしか始められない**ので、
長文作成とは別セッションに切った。同じセッションに置くと、本文を直すたびに
「もう作った画像は捨てるのか」という判断が毎回混ざる。

`ref-x-longpost-canon` は成果物を作らない。文字数の測定単位のように
複数の skill・script・reference にまたがる規定について、
どれが正本かだけを答える。これが無いと、同じ数値が 3 箇所に散って静かにずれる。

## 3. 文字数の測定単位を 2 系統に分けた話

本 plugin には数え方の違う 2 つの物差しがある。

- `count-chars.js`: **空白・改行を除いた**文字数。本文量 (1800〜2200 / 400〜499) を判定する
- `validate-title.js` / `validate-headings.js`: **空白を含む NFC コードポイント数**。タイトル 50 字・見出し 12〜28 字を判定する

統一したくなるが、統一できない。本文量は「読者が読む分量」なので改行を数えたくない。
タイトル長は「タイムラインで表示が切れるか」なので空白も 1 文字として効く。
目的が違うので物差しも違う。**代わりに、文字数を書く箇所には必ず測定単位を併記する**
という規律を SKILL.md に据えた。単位を書かない数値は、読み手が勝手にどちらかを想像する。

## 4. 図解とサムネイルで画風の正本を分けた話

当初はサムネイルを図解の画風 (純白背景・白黒・赤い ✕ 印) から派生させようとして失敗した。
図解は「読んだ人に理解させる絵」で、白い紙の上の説明図として正しい。
サムネイルは「スクロールする指を止めさせる絵」で、貼り先の白い UI に溶けては困るし、
赤は煽り広告の記号に読み替えられる。**目的が正面から逆**だった。

そこで片方を曲げるのではなく、`diagram-style-canon.md` と `thumbnail-style-canon.md` の
2 本の独立した正本に分けた。共有するのは `visual-structure.json` (本文の構造解釈) だけで、
画風は共有しない。

配色は「色数」ではなく**役割**で縛っている。
オフホワイト #F8F3E6 / 墨黒 #1A1A1A / セージ #C1C2A0 (構造: 線・台・輪) /
テラコッタ #D87C45 (帯 1 枚だけ) の 4 色で、彩度の低いセージが構造を、
高彩度のテラコッタが 1 箇所の焦点を担う。
生成指示で「アクセントは 1 色だけ」と書くと、**どちらを捨てるかを生成系が勝手に決める**。
役割まで書いて初めて安定した。

## 5. 課金の前に 2 層の検査を置いた話

画像生成は 1 枚あたり概ね 1〜2 分かかり、実際に課金される。
出力を見てから直すループは、そのまま金額になる。そこで生成**前**に 2 層置いた。

1. `build-visual-prompts.js` — 構造データ側の検査 (ゾーン数・字数・禁止語・絵文字)
2. `lint-thumbnail-prompt.js --structure` — プロンプト文の検査 (TL-01〜TL-12)

TL-11 は「構造データに書いた文言と、画像内に入れる文言が一致すること」、
TL-12 は「2 枚のサムネイルの STYLE / TYPOGRAPHY / NEGATIVE が完全一致すること」を見る。
どちらも生成してから目で気づける種類の事故だが、気づいた時点で課金は終わっている。

生成後は `validate-visual-assets.js --strict` が PNG 署名・寸法・比率・不透明背景・規定色を見る。
ここまでは機械で閉じる。**閉じられないのは「絵として何が描かれたか」だけ**なので、
そこだけ `record-thumbnail-review.js` で人間の目視 5 項目 (人物なし / 情報商材的でない /
文字が読めて正しい / 優しいオフホワイト / インパクト) を receipt に記録する。
`embed-visual-paths.js` は receipt の SHA256 と現物の PNG hash が一致しなければ止まる。
目視した画像と差し込む画像が別物になる経路を、これで塞いでいる。

## 6. 成果物を先に見せる (artifact-first)

5 skill すべてが `artifact-delivery-v1` の状態機械を持つ。要点は 1 つで、
**利用者が現物を見て accept-as-is / light / standard / detailed を選ぶまで、
意味評価もリライトも走らせない**。数えられる機械検証だけを通した実成果物を先に出す。

1.2.1 での修正はこの規定の機械宣言に関するものだった。本文の
「Post-choice selected improvement execution」節には元からそう書いてあったが、
`lint-entrypoint-artifact-first.py` は frontmatter の `feedback_contract.activation_state`
を見る。宣言が無い `max_iterations: 3` は「選択前に回りうる改善ループ」と判定されて
fail-closed で止まっていた。散文と機械宣言の食い違いであり、規定そのものは変えていない。
