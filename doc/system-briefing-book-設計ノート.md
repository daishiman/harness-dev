# system-briefing-book 設計ノート

業務システムの打ち合わせ資料 (ヒアリング結果・要件定義書・仕様書・画面ボード・まとめ HTML) を、
毎回同じ工程・同じ型・同じ品質で作る plugin の設計記録。
利用手順は [plugins/system-briefing-book/README.md](../plugins/system-briefing-book/README.md)、
章立てと番号の決まりは [references/document-structure.md](../plugins/system-briefing-book/references/document-structure.md)、
質問・選択肢・聞く回・既定案・行き先は [hearing-catalog.json](../plugins/system-briefing-book/assets/data/hearing-catalog.json)、聞き方と答えの扱いは [run-briefing-hearing の hearing-guide.md](../plugins/system-briefing-book/skills/run-briefing-hearing/references/hearing-guide.md) が正本である。
本ノートは「なぜその形にしたか」を残す。規則は理由の説明に要る分だけ引き、細かい決まりは正本へのリンクにする。
引いた数や名前が正本とずれていないかは [tests/test_system_briefing_book_design_note.py](../tests/test_system_briefing_book_design_note.py) が確かめる。

## 1. 何を解く plugin か

業務システムを頼まれたとき、最初の打ち合わせまでに要るのは「何を作るか」と「どう動くか」の合意である。
ところが、話を聞く人はエンジニアでないことが多く、聞き漏れ (権限・データ・止まったとき) は
実装の段になって初めて見つかる。逆に、エンジニアの言葉 (認証方式・DB の型・性能値) で聞くと、
答える側が止まってしまう。

この plugin は、素材と短いヒアリングから資料一式を作り、
**聞くのは業務の大きな流れだけ、技術の判断は AI が案にして「決めること」へ回す**という線を引く。
アプリの実装はしない。できた要件定義書と仕様書を、実装のスキルへ渡すところまでが範囲である。

## 2. 7 つの skill に割った理由

| skill | 担当 |
|---|---|
| `run-briefing` | 司令塔。工程の順番と確認点 (★) で止まる所を持つ |
| `run-briefing-hearing` | ヒアリング.md を書く唯一の担当 |
| `run-briefing-docs` | 要件定義書と仕様書を書く |
| `run-briefing-boards` | 仕様書からページ構成を決め、画面ボードを作って PNG にし、はみ出しを検査する |
| `run-briefing-book` | 全部を目次つきの 1 ファイルの HTML にまとめる |
| `assign-briefing-evaluator` | 確認点で、作り手とは別の目で正確さ・言葉・見た目・シンプルさを見る |
| `run-skill-feedback` | 利用者からの「こう直してほしい」を改善要望として送る |

分割の基準は「書く文書が違うか」である。ヒアリング.md を書くのは hearing だけにした。
docs は足りない聞き取りを自分で書き足さず、決めること (Q 番号) として司令塔へ返し、
司令塔がそれを hearing の followup に渡す。書き手を 1 つに絞らないと、
同じ答えが 2 か所で違う形に直され、どちらが正しいか分からなくなる。
評価者を別の skill にしたのは、資料を作った文脈のまま自分の資料を見ると、見落としも同じになるからである。

## 3. ヒアリングを「大きな流れだけ」にした話

質問は 36 問あるが、実際に聞くのは 24 問 (1 回 4 問 × 6 回まで) で、残りの 12 問は既定案で埋める。
聞き方 (選択肢の数、おすすめの付け方、「全部おすすめ」の扱い) は
[hearing-guide.md](../plugins/system-briefing-book/skills/run-briefing-hearing/references/hearing-guide.md) の 2 章にある。

もとからの 24 問は、目的と範囲・画面の共通ルール・しくみと基盤・運用を聞く。
0.2.3 であとから足した 12 問が拾うのは、要件定義書と仕様書を書くのに要るが、非エンジニアにも答えられる事柄である。

- **仕事の流れ**: だれが何をして、次にだれへ渡すか
- **画面と権限**: 管理する人の画面を分けるか、だれが直せて・消せるか、使う人をどこで足し外しするか
- **データ**: 今の紙や表のどの欄を残すか、1 日や 1 か月で増える件数、今あるデータを移すか
- **安全**: 人に見られると困る情報が入るか、会社の外から使うか、だれがいつ直したかを残すか
- **運用**: 止まったら仕事はどうなるか、使う時間帯 (止めて直してよい時間)

既定案で埋める 12 問と、あとから足した 12 問は別の組である。足した質問の多くは聞く側に入っている。

聞かないものも決めてある。画面の寸法・製品名・件数の上限のような細かい値は聞かずに既定案で埋め、
決めることに回す。聞き足すのは、資料全体の土台になる核心の 5 問
(使う人・いちばん困っていること・最初の版でやること・先々広げたいこと・仕事の流れ) だけで、
1 問につき 2 回までとする。答えが出るまで聞き続けると、打ち合わせの前に相手が疲れてしまう。

1 つの質問に 2 つのことを混ぜない。ただし「だれが直せて、だれが消せるか」のように、
1 つの選択肢で両方に答えられる組は例外にした。分けると、同じ人に同じ場面を 2 回想像させることになる。

内容の重なる質問は組にした。使う人を足し外しする場所 (H28) と、それをする人 (H21) は、
H28 の答えで人まで分かれば H21 は聞かずに埋める。答えどうしが食い違ったとき、たとえば
「管理の画面は作らない」(H26) のに「人の出し入れはアプリの管理のメニューで」(H28) と答えたときは、
H26 を案として残し、H28 を `未定` にして決めることへ回す。AI がどちらかに寄せて黙って確定させると、
だれも合意していない決定が資料に載るためである。組と食い違いの決まりは
[hearing-guide.md](../plugins/system-briefing-book/skills/run-briefing-hearing/references/hearing-guide.md) の 4 章にある。

## 4. H 番号を質問ごとに固定した話

ヒアリングの答えには H 番号が付き、仕様書の表は `(聞き取り:H27)` のようにその番号を根拠として書く。
この書き方は「ヒアリング.md のこの行を見よ」という指し先で、出どころが既定案の行も同じ形で指す
(お手本の仕様書は、既定案の H26・H28 をこの形で指している)。だから、答えが聞き取りか既定案かの区別は、
ヒアリング.md の出どころの列に置く (5 章)。

最初は、表の順に番号を振り (A1 → H01 … D4 → H24)、素材から足した質問があると、
その章の最後に入れて後ろの番号を 1 つずつ下げていた。これだと、同じ質問でも案件ごとに番号が変わり、
質問の表に問いを足せば、過去の資料の根拠とも合わなくなる。

そこで番号を質問に結び付けた。もとからの 24 問は H01〜H24 のまま、あとから足した 12 問は H25〜H36 とし、
聞かなかった質問も同じ番号で書く。素材から足した質問や、名前を挙げて頼まれた機能 (`要望`) は、
文書全体の最後の番号の続き (H37 から) に足す。表の並び順と番号の並び順は一致しないが、
番号が変わらないことのほうを優先した。

## 5. 既定案と聞き取りを分けて記録する話

答えの出どころは `聞き取り` / `素材:<ファイル名>` / `既定案` / `未定` / `要望` の 5 つのどれかで書く。
**既定案は合意した事実ではない**。おすすめのまま進めた答えも、出どころは `既定案` のまま残し、
決まったこととしては扱わない。わからない・あとでの答えは既定案で進めて `未定` とし、
ヒアリング 5 章 → 要件定義 9 章の決めること (Q 番号) → 仕様書の根拠 `決めること:Qxx` へと追える形で残す。

ただし、確認点で決めることに答えが出たとき (hearing の followup) は、おすすめの案を選んでも出どころを
`聞き取り` にする。そこでは利用者が案を見たうえで決めたからである。

この区別がないと、打ち合わせの場で「それは決まったんでしたっけ」が起きる。
資料が整っているほど、案と合意の区別は見た目からは消えるので、出どころの列で機械的に残す。

## 6. 答えの受け皿を先に用意した話

質問を足しても、答えを書く場所が無ければ資料に出てこない。0.2.3 で質問を足したときは、
質問ごとの行き先を質問の表 (今は hearing-catalog.json の `destinations`) に書き、受け皿の側も合わせて確かめた。

仕様書の `画面区分:`・`稼働構成:`・`監視と復旧:` は前からある欄なので、そこに書く中身
(件数の見込み、止まったときのしのぎ方など) を足すだけにした。新しく足したのは、要件定義書 7 章 (守ること) の
量・止まったとき・使う時間帯の行である。どの答えをどの欄へ書くかは
[document-structure.md](../plugins/system-briefing-book/references/document-structure.md) にある。

お手本 (配車表の読み取り) も同じ形に直し、新しい質問の答えがどこに写るかを見て確かめられるようにした。

## 7. 最初の版を小さく保つ話

最初の版は「こういうことがやれます」が伝わる最小限に絞る。聞いている途中で出てきた広げる案は、
最初の版に入れずに仕様書 8 章 (最初の版に入れないもの) の「次に広げる候補」へ回す。
打ち合わせの前に資料を大きくすると、相手は何を確かめればよいか分からなくなる。

## 8. 同じ入力から同じ HTML を作る話

まとめ HTML は、同じ文書・`briefing.json`・ボードの画像・`_src/tokens.css` から作れば、同じバイト列になるようにした。
目次の下の「作成」に組み立てた時刻が入るので、比べるときは環境変数 `SOURCE_DATE_EPOCH` で時刻を固定する。
画像は HTML に埋め込み、外のファイルを読まずに 1 ファイルで開ける。
バイトが一致するので、改善の前後で何が変わったかを差分で見られる。

これは「同じ入力から同じものができるか」の話である。参考にした資料をどこまで再現できたかは別の問いで、
構造の比較で差を出し、合格かどうかは参考の版・意味と範囲・見た目を突き合わせて別に決める。
構造が一致しても、再現できたことにはならない
([references/workflow.md](../plugins/system-briefing-book/references/workflow.md) の「再現の測り方」)。

## 9. 見た目を jp-web-design に合わせた話

まとめ HTML と画面ボードの既定の見た目は、同じリポジトリにある aidd-agent-kit の jp-web-design
(標準カラーと、その使い方の決まり) に従う。plugin が自分で色を選ぶと、キットが色を直しても資料だけが古い色で残り、
作るたびに AI が色を選べば、同じ素材でも見た目が揺れる。正本を 1 つにして、毎回同じ見た目を出すためにこうした。

ボードとまとめ HTML が読む `_src/tokens.css` は、次の 3 つをこの順につないで作る。同じ名前は後に書いたものが勝つ。

1. ボードの言葉: ボードの部品が使う名前をキットの役割へつなぐ。値を持つのはキットに無いもの
   (ボードの地、注記の番号、注意の枠線、端末の枠と影、押せる大きさ、文字の束、角丸) だけ
2. 標準カラー: キットの CSS を 1 バイトも変えずに写したもの
3. 案件の上書き: `briefing.json` の `palette` に CSS を指定したときだけ

標準カラーをリンクでなく写しにしたのは、plugin は単独で配られ、使う場所にキットがあるとは限らないからである。
その代わり、写しの出所とハッシュを記録し、`scripts/extract-kit-palette.mjs` と
[tests/test_palette.py](../plugins/system-briefing-book/tests/test_palette.py) で確かめる。
キットとの照合 (`--kit --check`) はキットがあるこのリポジトリでだけ動く。配られた先では、
写しが記録どおりで手で書き換えられていないか (`--verify`) だけを確かめる。
ボードの言葉はキットの名前を書き換えない。キットの名前を plugin 側で決め直すと、どちらが正本か分からなくなる。

案件の色に合わせるときの約束は、キットの決まりどおり基本色 (`--p-*`) だけの上書きにした。役割の色はすべて基本色に
付いてくるので、上書きは数行で済む。役割を直接書いても効くが、キットの役割が変わったときに付いてこない (12 章)。
標準カラーにもボードの言葉にも無い名前を上書きすると注意が出る。綴りを誤ると、上書きが黙って効かないためである。
手順は [assets/css/standard-attribution.md](../plugins/system-briefing-book/assets/css/standard-attribution.md) にある。

配色の正は `briefing.json` の `palette` の 1 か所にした。init は既にある `briefing.json` を書き換えない。
そのため、作り直すたびに引数で配色を渡す形だと、引数を付け忘れた回だけ標準の色に戻り、記録と実物が黙ってずれる。
いまの init は、`briefing.json` があればその `palette` で `_src/tokens.css` を作り、記録と違う `--palette` を渡されると止まる。
init は `palette` を `materials` と同じく `briefing.json` のあるフォルダからの相対で書くので、素材と配色の CSS をまとめて動かしても同じ色で作り直せる。
`--refresh-css` を付け忘れたときは、作り直さなかった CSS が記録から作るものと違えば init が知らせる。同じ入力からは同じバイト列になるので、比べるだけで分かる。

色だけでなく、キットの使い方の決まりも既定にした。カードの端に色の帯を付けない、アイコンを自作しない、などである。
CSS で判定できるものはテストで見て、残りは確認点で目で見る。一覧は
[references/page-patterns.md](../plugins/system-briefing-book/references/page-patterns.md) にある。

## 10. 配色に会社の名前を付けない話

既定の配色は `standard` (標準カラー) と呼ぶ。この配色は、もとは特定の取引先向けに作った暫定案だった。
名前に会社名が残ると、別の会社の資料を作るたびに「この会社の色なのか」と読み手が迷い、
取引先の名前が無関係な資料や例文に出回る。そこで、キットと 2 つの plugin (system-briefing-book と
ubm-goal-setting の例文) から会社名を外し、配色は「正式に承認された配色ではない、差し替え前提の標準」とだけ書いた。

`briefing.json` の `palette` は `standard` か CSS ファイルの場所しか受け付けない。古い名前を書いた既存の
`briefing.json` は検査で止まるので、`standard` に書き換える。読み替えの互換は置かなかった。
古い名前を受け付け続けると、その名前がまた資料や例文へ写るためである。

## 11. 配色を書く前に確かめる話

配色の CSS で役割の名前が 1 つ足りなくても、値の綴りを誤っていても、以前は `_src/tokens.css` をそのまま書き、
ボードとまとめ HTML を作っていた。ブラウザは読めない値を黙って捨てるので、壊れた色でも止まらずに、
それらしい見た目で出来上がる。打ち合わせの直前に色の抜けに気づいても、どの版から壊れていたかを追えない。
そこで、書く前に確かめ、だめなら何も書かずに止めることにした。

確かめるのは `scripts/lib/design-tokens.mjs` で、`tokens.css` のトップレベルの `:root` 宣言だけを配色として読む。
役割の不足、空値、`initial` などの未確定値、参照切れ、循環参照、`@import` を見つけたら止める。
必須の役割名はこの plugin に並べて書かず、標準カラーの組み立て (`scripts/lib/palette.mjs`) から読む。
名前の一覧を 2 か所に持つと、キットの版を上げるたびに片方を直し忘れるからである。

止める場所は 3 つある。init は書く前に止まる (exit 2)。描画とまとめは、`tokens.css` が無いか不正なら
`TOKENS-MISSING` か `TOKENS-INVALID` で止まる。まとめだけ別の色に替えて成功扱いにすると、ボードとまとめ HTML の色が
黙ってずれるためである。直し方は `init --refresh-css` で、init を回し直すのは run-briefing なので、
まとめの表でも直し先を run-briefing にした。

ただし、`palette` が指す CSS が動いて見つからなくなっても、`--refresh-css` を付けない再 init なら、
すでに配った資料の `tokens.css` は残す。作り直さない回まで止めると、配色の元を片付けただけで、
色の正しい資料まで作り直せなくなる。手順と決まりの正本は
[references/design-contract.md](../plugins/system-briefing-book/references/design-contract.md) にある。

## 12. まだ残っていること

### やること

- 原資料 v0.4 の 6 画面を正規の入力から作り直し、見た目が再現できるかの受入検証 (harness-hbg)。
- run-briefing の工程5と工程6に、boards から返る「案件の色が要る」と、まとめの `TOKENS-*` を受ける手順が無い (harness-r4p)。
- content-review の low の指摘は、各 skill の verdict の `negative_feedback` に残している。
  主なものは、まとめの表で `EXTERNAL-REF` (head) の直し先が boards のままなことと、
  `FIRST-VERSION-MANY` の文言が「最初の版を小さく」の方針と逆に読めることである。
- お手本の `_check/docs.json` に、検査を回した場所の絶対パスが入る。別の場所で検査を回すと、
  この 1 行が書き換わって版の上げ忘れ検査が反応する。相対パスで書くのが望ましい (harness-a5r)。
- 作業コピーの改行が CRLF になると plugin の fingerprint がずれる (0.2.2 で一度直した)。
  `.gitattributes` で改行を固定すると再発しない (harness-a5r)。

### 受け入れた制約

- 配色の旧名は、公開済みの commit の履歴と、すでに利用者の手元へ入れたキットの写しには残る。履歴の書き換えはしていない。
- 案件の配色の約束は「基本色だけの上書き」に変わった。役割まで全部書いた古い形の CSS も上書きとして効くが、
  キットの版が上がったときに役割の変更へ付いてこない。見つけたら基本色だけの形へ書き直す。
  キットが改名した基本色を書いた古い CSS は、init が「標準カラーにもボードにも無い名前」として注意を出す。
