# rubric 更新提案: PG-001 / REG-001 を実行可能な記述へ訂正する

## なぜ提案なのか (直接編集しない理由)

`scripts/hook-guard-rubric.py` が canonical rubric への直接編集を拒否する。
理由は Goodhart 防止 — 「検査が落ちたので検査の側を書き換える」を、採点器を
書いている当人が単独でできてはならない。本提案の proposer は
assign-skill-design-evaluator の被覆率監査であり、`proposer != approver`
を満たすには別の承認者が要る。よって本ファイルは提案に留め、rubric 本体は
承認後に改める。

## 現状: 2 つの rule が「書かれたとおりには実行できない」

採点器 `render-findings-score.py` は現在この 2 件を `pending_human`
(`blocked_on: "rubric-text"`) として出力する。silent pass にはしていないが、
機械判定はできていない。

### PG-001 (high)

現行 check:

> `prompts/<R-id>.yaml exists for every R-id`

実測 (2026-08-14, `plugins/` 配下):

| 対象 | 件数 |
|------|------|
| `prompts/*.yaml` | **0** |
| `prompts/*.md` | **187** |
| `prompts/` を持つ skill | 77 / 全 116 skill |

記述どおりに実装すると、prompts を持つ 77 skill が全て high で落ちる。
つまり rule が要求する形式は repo のどこにも存在しない。実態は
`R1-orchestrate.md` `R2-agent-structure-designer.md` のように
`R<n>[a-z]?-<slug>.md` である。

### REG-001 (high)

現行 check の後半 `validate-build-trace.py` は `build-trace.json` を引数に
要求するが、`plugins/` 配下の `build-trace.json` は **0 件**。
前半の `validate-plugin-completeness.py` は exit 0 (22 plugins complete) で
通る。rule の半分が、対象成果物が存在しないという理由で恒久的に判定不能。

## 提案する変更

### 変更 1: PG-001 の check を実態の命名へ追従させる

```diff
- "check": "prompts/<R-id>.yaml exists for every R-id"
+ "check": "prompts/ を持つ skill では、その中の全ファイルが
+           'R<n>[a-z]?-<slug>.md' 形式である。prompts/ が無い skill は skip (PASS)"
```

rule の**意図**(責務 R-id と prompt ファイルが 1:1 で追跡できること) は
変えない。追跡子の物理形式を yaml から md へ合わせるだけ。

### 変更 2: REG-001 の後半を対象存在で条件づける

```diff
- "check": "validate-plugin-completeness.py が exit 0 かつ
-           validate-build-trace.py が exit 0"
+ "check": "validate-plugin-completeness.py が exit 0。
+           build-trace.json が存在する plugin についてのみ
+           validate-build-trace.py が exit 0 (存在しなければ当該部分は N/A)"
```

「成果物が無いので検査できない」を「検査したので合格」と言わないための
条件づけ。将来 `build-trace.json` を持つ plugin が現れた時点で自動的に
検査対象へ入る。

## 影響評価

`R<n>[a-z]?-<slug>.md` を当てた場合の違反件数 = **2 件**。

| ファイル | 現状 |
|----------|------|
| `dev-graph/skills/run-dev-graph-decompose/prompts/R2b-feature-planning.md` | `R2b` — 数字の後に枝番の英字 |
| `dev-graph/skills/run-dev-graph-requirements/prompts/R2b-readiness.md` | 同上 |

この 2 件があるため、正規表現は `R\d+-` ではなく `R\d+[a-z]?-` とする。
枝番を許すと `R2` と `R2b` が別責務なのか派生なのかが名前から読めない、
という別の論点はあるが、それは本提案の範囲外 (別提案で扱う)。

上記の形にした場合の **expected_fail_rate_delta: 0** (違反 0 件)。
REG-001 の変更も、`build-trace.json` が 0 件である以上 fail 件数は変わらない。

## semver 判定

**minor (1.3.0 → 1.4.0) / 猶予期間 7 日**を提案する。

文言のみの訂正なので patch に見えるが、patch を選ばない。現行の 2 rule は
判定不能として `pending_human` へ退避されており、**訂正後は初めて機械判定が
効き始める**。採点対象 skill から見た実効的な振る舞いが変わる以上、
即時発効の patch ではなく猶予期間つきの minor が妥当と判断した。
「文言だけだから patch」は、判定不能→判定可能という状態遷移を
見えなくする。
