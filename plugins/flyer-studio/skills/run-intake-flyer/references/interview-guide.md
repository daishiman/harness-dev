# ヒアリングの聞き方

[run-intake-flyer](../SKILL.md) で利用者に聞くときの判断の指針。質問そのもの（文言・選択肢・聞く条件・必須かどうか）の正本は[intake-questions.json](../../../references/intake-questions.json)で、ここには書かない。公開範囲と様式・配色の規則は[design-rules](../../../references/design-rules.md)と[style-profiles](../../../references/style-profiles.md)を正本とし、ここでは聞き方に関わる点だけを書く。

## 聞き方の原則

- 全質問を 1 枚のシートで一度に出し、分かる項目だけ答えてもらう。追加で聞くのは intake-residual が返した不足・矛盾・確認だけにし、既に答えのある質問を聞き直さない。
- 依頼文や支給資料で分かる値は prefill に写して「確認のみ」にし、利用者に同じことを書かせない。
- 制作に要る事実（確定事実）と、後から調整できる好みを分けて扱う。事実は推測で埋めず、好みは「おまかせ」を受け付けて比較案で決める。
- 自由に書かれた希望を選択肢へ無理に押し込まない。様式は自由回答で受け、短いラベルのまま記録する。
- 「かっこよく」「バランスよく」のような言葉は、実現したい状態へ言い換えて確かめる（例: 主題を最初に読めて、日時・会場・料金がひとまとまりに見え、探さず読める）。

## 事実の扱い

- 確定事実は今回の回答か今回の資料からだけ受け取る（E2）。前回の値・preset の値・前回までの傾向（suggestion）は下書きで、利用者が今回の値と認めたものだけを使う。
- 「前回と同じ」と言われたら、具体的な値を読み返して今回の値として記録する。
- 読み返しでは、機械で検査しにくい点を確かめる: 催しの名前と主催者・ブランド名の区別、回数（古い回の転用）、登壇者の氏名の正字と主従、会場の施設・階・部屋と駅との位置関係、料金が税込か・何を含むか、申込先が今の URL か。
- 仮の値（「未定」「TBD」など）は仮置きとして記録され、未解決のまま残る。仮置きを確定と混同しない。
- 依頼主ごとの固定の値（依頼主名・会場・ロゴの種類・過去の案数など）は質問や選択肢に書かず、`references/presets/<id>/` の preset にだけ置く。preset は利用者が選んだ案件でだけ読む。

## 素材と公開範囲

- 用意済みの写真やロゴは、サムネイル・短い名前・使用条件を付けた一覧で見せて選んでもらう。ファイルの場所だけを並べて選ばせない。preset に属する素材は、その preset を選んだ案件でだけ見せる。
- ロゴは「支給ロゴを使う（ファイルを指定）／ロゴなし」で聞き、使うときは印刷に使う版のファイルを指定してもらう。既に指定があれば同じ確認を繰り返さない。
- 新しい写真は、本人と顔を出してよい人・写さない人や子供や名札・端末の画面・催事名を確かめる。基準は[design-rules §6](../../../references/design-rules.md#6-写真の公開範囲と差し替え)（DD07）、記録の形は[runtime の追加素材](../../../references/runtime.md#追加素材と生成記録)。公開範囲が分からないまま制作へ進めない。
- 用意済みの写真は決まっている公開条件の範囲で使い、別の写真や別の人物へ許可を広げない。
- 参考にするチラシは構図・書体・情報の順序の研究にだけ使う。写っている第三者の顔・氏名・他の催しの文言を素材として写さない。参考にしたファイルと、そこから取り入れる特徴を分けて記録する。

## 様式と配色の聞き取り

- 様式は毎回聞き、前回の様式を黙って使わない。様式と配色（requiredTones）は別に決める（[design-rules の「表現様式と配色は別々に選ぶ」](../../../references/design-rules.md#表現様式と配色は別々に選ぶ)）。
- 様式の名前が具体的なら、その様式で伝わるものと起きやすい失敗を[style-profiles](../../../references/style-profiles.md#様式の記述軸)（DD11）で短く伝える。雰囲気の言葉だけ・未回答・おまかせなら、intake-residual の styleProposalNeeded を受けて 2〜3 案を提案する（手順は SKILL の 7）。
- 提案は回答から読み取った根拠だけで作り、使った根拠（basisUsed）と目的への効き方（fit）を添える。実在の作家名・作品名で模倣させない（E3）。公開できる写真が無いのに写真の案を出さない。
- 漫画やイラストで実在の人を描くときは、写真の作風変換の許可を確かめる。許可が無ければ架空の人物にするか人を描かない。
- 筆文字・手書きの書体は、日本語の字形と利用許諾を確かめられるものに限る。手書きは見出しに使い、本文と条件は読みやすい書体で組む。
- 配色を「白だけ」「黒だけ」とした回答は、必須配色をその 1 系統にする回答として受け、案の違いは構図・様式・主題の方向で作る。preset の配色から変えるときは理由を残す。
- 1 案だけ欲しいと言われても、比べて選ぶために 2 案以上を作ることを伝える。

## 不明点と変更の扱い

- 調べれば分かることを利用者に繰り返し聞かない。
- 公開範囲、参加の判断を左右する事実、申込先、料金の条件は推測で確定しない。
- 軽い見た目の判断は比較案と根拠を残して進め、配置の変更のたびに承認を求めない。
- 主題・目的・写真の公開範囲など方向そのものが変わるときは、具体的な変更を見せて確かめ、承認された変更を brief.json に反映し、essence-revise で記録して essence-check を通す（R2。実行は[SKILL の手順 9](../SKILL.md#手順)）。
- 画像生成が使えないときはその時点で伝え、生成したかのような代わりの物を作らない。支給の背景か既存の背景で進めるかを確かめる。
- 文の途切れや誤変換は、指示が明確なら進める。意味が分かれる部分だけを引用して確かめる。

支給資料に今回の希望様式が明示されている場合は source=document のまま prefill から回答へ引き継ぐ。参考画像の見た目から推測した作風を、利用者が指定した希望へ自動で昇格させない。知見台帳では、資料で明示された希望を利用者の明示指定の分類に数え、元の出典は案件の intake.json に保持する。
