# 現物診断・改善提案の契約

目標は「何を変えるべきか」と「何を残すべきか」を実画像から説明し、実行可能な候補へ絞ること。元画像の美しさや過去のPASSを前提にしない。編集や完成判定はここで行わない。共通規則は[stage-common](../../../references/stage-common.md)。

## 必要情報と正本

直接編集は analysis.json と元画像一覧 SOURCES.json。分析開始の mode 切替と評価用の空台帳生成・再発行時の履歴保全は、[stage-common の付随更新](../../../references/stage-common.md#所有と機械による付随更新) に従う呼出側準備で、brief・評価内容・退避記録を自由に書き換える権限ではない。

元画像/PDF/編集元、読者・価値・促す行動、最新要求、素材公開条件、保持点、案IDを受け取る。入力形式は[analysis schema](../../../schemas/analysis.schema.json)。sourcesの原本を保持し、元画像SHAと観察領域を結ぶ。新要求の必須/候補を分け、古い提案・未承認試作を完成物と混同しない。

## 判断の錨

意味群と視線の目的を先に考え、書体/pt/角度はその実現候補として選ぶ。指針はstage-commonの「知識の読み込み」どおり、目的・主従・対象認知・群の意味・画像統合・公開範囲・多様性のうち今の未達に要るものだけを読む。

各案で最初/次/対象者が分かった語、迷いと領域、残す長所、採用/維持/見送りの理由を記録する。候補の散在/回転を必須と誤認せず、読順を改善するかを比較する。必須要求の見送りや未確定情報の創作は解決にしない。比較対象を無制限に増やさず、問題を検証できる最小候補を選ぶ。

## 次行動と完了

次行動は [共通の判断手順](../../../references/stage-common.md#共通の判断手順) で選ぶ。この担当では、分析した領域・保持点・候補の採否と理由を結び、分析自体を擬似的な自動採点で合格にしない。

改善の影響が大きい、または全案共通の変更で効果が不確かなときは、executionPlanで先行試作（pilot）する案を選ぶ。pilotVariantIdsは既存案の一部に限り（全案を同時に試す計画はpilotではないため機械検査で拒否する）、その案を選んだ理由（reason）と、pilotで確かめた変更を残りの案へどう展開するか（propagation）を書く。全案へ同じ処方を一度に当てて、案ごとの長所を均さない。小さく確実な修正ならexecutionPlanを省いてよい。制作ではpilot案の独立PASSまで残りの案を描画できない（[runtime の先行試作ゲート](../../../references/runtime.md#先行試作から全案への展開)）。

全案・全適用要求の根拠と保持点が揃い、analysis-validate が通れば analysis-review-template で評価台帳を用意して、別 context の提案評価へ渡す。機械検査だけでは意味的な妥当性は確定しない。FIXは必須修正に対応した観察/採否を直し、提案全体を理由なく書き換えない。

## 専門レンズと案件固有の条件

構図・文字・色の専門レンズはstage-commonの「専門レンズの共通規則」どおりにstage=analysisで使う。統合前の所見を他担当の初見観察へ混ぜない。

選択した preset の preset.json の knowledgeFiles が指す案件知見や改訂ごとの条件は、その案件とその改訂にだけ適用する。汎用の固定構図やイベント値へ昇格させない。

## 完成評価からの戻り

premise の必須修正は元要求ID・案ID・画像領域へ結んで受け取る。戻り先と制作への分岐は [workflow の表](../../../references/workflow.md#改善と納品) に従う。intake の確認後に分析へ戻された案件では、原因と保持点から修正提案を作って再び提案評価へ渡す。元要求を都合よく書き換えない。
