# 図解の情報契約 — 図が図として成立するための下限

既存の図解仕様 (`diagram-layout-contract.md` と `diagram-*.md` の各節) が定めているのは
**幾何と上限**である。座標・寸法・色・線種・要素数の上限・複雑度の上限。
そこに無いのが**下限** — 「この型が図として成立するために、書かねばならない情報」である。

この非対称が実害を出していた。ER 図の作例が列名だけを並べて主キーを持たず、
ガント図の作例が `relations: []` で依存線を 1 本も持たず、上昇図が目盛の無い価値軸を持つ。
いずれも全ゲートを緑で通過する。**上限しか検査していないので、情報が少なすぎる図は誰も止めない。**

本書はその下限を定める。上限側の正本は `diagram-layout-contract.md` のままで、本書はそれを置き換えない。

> **原則: 情報が多いのが正義ではない。使える情報が多いのが正義である。**
> 本書が要求するのは「読者がその図から判断を下すために要る情報」だけで、
> 網羅性や装飾のための追加は要求しない。むしろ下の I2 は、
> **図が語っていない主張を caption に書くこと**を欠陥として扱う。

---

## 第 1 部 共通必須 (I1-I5) — 全型に効く

型を問わず、次の 5 つが図の**内側**に無ければ、その図は成立していない。
「内側」と書いているのは、図は切り出されて流通するからである。
印刷の抜粋・スライドの投影・画像としての引用のいずれでも figcaption は付いてこない。
**figcaption にしか無い情報は、無いのと同じものとして扱う。**

### I1 出所と時点 — 数値を載せるなら、それがどこから来たか

図に数値がある場合、次の 3 つを図内へ持つ。1 行にまとめてよい。

| 項目 | 内容 | 欠けたときに起きること |
|---|---|---|
| 集計定義 | 何を数えたか (「解約」= 契約終了日基準か通知日基準か) | 定義依存で結論が動くのに、読者がそれに気づけない |
| 時点・期間 | いつのデータか。**相対表記だけにしない** (「4月」ではなく「2026/4」) | 他資料と突合できず、図が単独で根拠になれない |
| 母数 n | 割合を出すなら必須。単一回答か複数回答かも | 68% が 100 人中 68 人か 8 人中 5 人か判らない |

書き方は図の下端 1 行でよい: `2026年度・サポート一次受付・重複除外後 (n=312)`。

**割合を扱う型 (円・積み上げ・ファネル・レーダー・横棒) では n と回答方式は省略できない。**
合計が 100% にならない図 (複数回答) は、その理由を書かないかぎり必ず誤読される。

**検査器の実装 (`scripts/validate-diagram-information.py`)**:
上表の 3 項目は既定では**論理和**で検査する (どれか 1 つあれば I1 は鳴らない)。
これは緩いが、緩さが必要な型がある — roadmap の「60% 完了」やゲージの達成率は
母数が自明であり、n を要求しても書く内容が無い。
そこで**割合を扱う型に限り**、上の太字どおり母数を独立に (論理積で) 要求する。

| 判定 | 根拠 | 理由 |
|---|---|---|
| 割合を扱う型か | ファイル名または `data-diagram-*` 属性が `pie`/`donut`/`funnel`/`radar`/`stacked`/`hbar`/`share`/`composition`・円グラフ/積み上げ/ファネル/レーダー/横棒/構成比/内訳 に一致 | 上の太字の列挙をそのまま述語にした。契約と検査器で列挙が二重管理にならない |
| 母数があるか | 図の内側に `n=` / 母数 / 件中 / 人中 / 社中 / 回中 / 全N のいずれか | 表記の揺れを吸収する。figcaption 側は数えない (§冒頭) |

この限定を外して全図へ掛けると、達成率を持つだけの図が一斉に鳴り、
**警告が多すぎて誰も読まなくなる**。検査の価値は網羅率ではなく的中率にある。
なお型の一致はファイル名を kebab-case として見るので、`-` は語の切れ目として扱う
(`pie-chart.json` は一致する)。`-` を語の内部とみなすと実在の命名がすべて漏れる。

### I2 主張と図の一致 — caption が言う量は、図の中にある

caption・message・注釈が量的な主張 (「速くなる」「費用の山」「律速」「伸びている」)
をしているなら、その量が図の中に無ければならない。

これは追加の要求ではなく**整合の要求**である。満たし方は 2 つあり、どちらでもよい。

- 図に量を入れる (`平均応答が縮む` → `平均 4.2h → 2.6h`)
- 主張のほうを図が支える範囲へ下げる

**やってはいけないのは、量的主張を caption に置いたまま図を定性語のままにすること。**
読者は主張を検証できず、信じるか暗算するかしか無くなる。

### I3 記号の凡例 — 語彙が 2 つ以上あるなら、図内で定義する

線種・色・形・塗りのいずれかで 2 語彙以上を使い分けているなら、
その対応を図内に置く。とくに**線**は誤読の代償が大きい。

連絡経路の線を指揮系統と読まれる、時間順の矢印を依存関係と読まれる、
参照の線を包含と読まれる — いずれも図の結論を反転させる。

線が 1 種類しか無い場合も、その線が**何でないか**を書く必要がある場面がある:
`── 連絡経路 (指揮系統ではない)`。

**凡例は文言ではなく印で見分ける (2026/8)。** `legendStrip` が描く見本の矩形は
`data-legend="1"` を持つ。検査器はこの属性で 3 つのことを決める。

| | 印がある要素をどう扱うか | 印で縛らないと何が起きるか |
|---|---|---|
| 語彙の数え上げ | 見本の塗りを**数えない** | 凡例を描くほど色が増え、凡例を描くほど凡例を要求される自己敗北ループになる |
| 免責の判定 | 印があれば凡例ありと見なす | 「凡例\|実線\|破線…」の文言一致に頼ると、`処理`・`入力`・`境界` のような本文語で誤って免責される |
| 語彙の対象 | `<text>` と `<marker>` の塗りも数えない | 見出しの墨色と矢じりの塗りが「分類の色」に化け、色を 1 つも使い分けていない図が I3 で鳴る |

数えるのは**節点や帯の塗り分け**だけである。文字色は読みやすさの調整であって
分類ではなく、矢じりは線の一部であって独立した意味を持たない。

### I4 軸の宣言 — 位置・大小・順序に意味があるなら名付ける。無いなら「無い」と書く

読者は形状から量を読む。これは規約ではなく反射である。
だからピラミッドの幅・同心円の半径・グリッドの並び順は、
**作図者が意味を持たせていなくても意味を持ってしまう。**

したがって二択になる。

- 意味がある → 軸名と向きを図内へ (`外側ほど優位`・`上ほど代替不能`・`左から着手順`)
- 意味がない → **その旨を書く** (`並びは順不同`・`幅は件数ではない`)

書かないという第三の選択肢は無い。書かなければ、読者が勝手に軸を発明する。

### I5 完了条件 — 判定を促す図は、判定基準を持つ

図が読者へ判定を求めているなら (「二段目で止まるなら三段目は要らない」「Check で止まる」)、
**何をもってその段が終わったと言えるか**が図に要る。

対象になるのは工程・段階・状態・タスクを持つ全型。
「Done の定義」「Exit criteria」「合格基準」いずれの呼び方でもよいが、
**測定可能**でなければならない。「即時参照できる」は基準ではない。「5 分以内に参照」は基準である。

## 第 2 部 型別必須スロット

型ごとの下限。各型は第 1 部に加えて下の項目を持つ。
ここに無い型は第 1 部のみが効く。

### 2.1 実体関連 (ER)

| スロット | 内容 |
|---|---|
| 主キー | 各実体の識別子。複合キーなら構成列すべてに印を付ける |
| 外部キーと参照先 | `FK` だけでは足りない。`FK → 受注.受注番号` まで書く |
| 列の型または意味 | `enum` なら**値域を書く** (`status : enum (下書/確定/出荷済/取消)`) |
| カーディナリティ | 1:1 / 1:N / N:M |
| 対応の必須性 | 必須か任意か |
| 識別関係の別 | 弱実体 (親なしに存在できない) なら明示する |

**参照の取りこぼしを作らない。** 外部キー列を持つのに関係線が無い実体があってはならない。
逆に、どの関係も持たない実体は、線を引くか図から削る。

`buildEr` は `fields` を `String(f)` で、`relations[].label` を自由文字列で描くので、
これらはすべて vendor 改変なしで表現できる:

```json
{ "name": "受注明細",
  "fields": ["受注番号 : PK,FK→受注", "行番号 : PK", "品番 : FK→商品 (必須)", "数量 : int"] }
{ "from": "受注", "to": "受注明細", "label": "1 対 多 (必須・識別)" }
```

### 2.2 状態遷移

| スロット | 内容 |
|---|---|
| 初期状態 | どこから読み始めるか |
| 終了状態 | どこで終わるか。複数あるなら全部 |
| 遷移の契機 | 何が起きて遷移するか |
| ガード条件 | どんな条件下でのみ遷移するか。契機と混ぜない (`承認 [限度内]`) |
| 滞留の上限 | 人手の判断を待つ状態があるなら、待ち続けたときの行き先 |

ラベルは `契機 [ガード]` 形式へ統一する。`限度超過` と `承認` を同じ書き方で並べると、
読者は片方をイベント、片方を条件だと見分けられない。

### 2.3 シーケンス

同期・非同期の別／戻り値／所要時間か SLA／**失敗したときの行き先**。
とくに最後が全作例で欠けていた。

**所要時間と失敗時の行き先は、戻りのラベルへ書く。** これは実装の制約を
回避するための一時策ではなく、本書の恒久的な書き方の約束である。
`buildSequence` に活性化帯 (activation bar) は無く、`alt` 枠も禁止規約なので、
書ける場所は戻りのラベル 1 箇所しかない。逆に言えば、置き場所が 1 つに
決まっているぶん、書き忘れは検査で捕まえられる。

```
残枠を返す (実測 120ms / SLA 500ms)・否認時は受付拒否へ
```

帯を導入すれば時間を面で示せるが、シーケンス図の情報量は
「誰が誰へ何を送り、失敗したらどこへ行くか」で決まる。
時間はその上に載る二次情報であり、**ラベル 1 行で表せるものを
図形の語彙を増やして表す理由が無い。**

### 2.4 スイムレーン・フロー

| スロット | 内容 |
|---|---|
| 起点と終点 | どこから始まりどこで終わるか |
| 担当 | 各工程を誰がやるか (レーンが担当を兼ねるならレーン名で足りる) |
| 受け渡す成果物 | 帯をまたぐとき**何を渡すか**。「渡した」だけでは足りない |
| 分岐の条件 | 判断の閾値まで (`基準内か` ではなく `5万円以内か`) |
| ループの脱出条件 | 差し戻しが何回まで起きるか、どうなれば抜けるか |

### 2.5 アーキテクチャ・システムコンテキスト・データフロー

通信の向きと方式 (同期/非同期・プロトコル)／各層または各ゾーンの**責務**／
流れる単位と頻度／異常系の行き先／依存が切れたとき何が止まるか。

**孤立ノードを置かない。** 本文が触れず関係も持たない箱は、
読者にとって「載せる必要のある箱」と「線を引き忘れた箱」の区別が付かない。

### 2.6 時間軸系 (ロードマップ・ガント・タイムライン・シェブロン・工程段)

| スロット | 内容 |
|---|---|
| 絶対時点 | **年を含む。** 相対週・月のみは不可 |
| 依存 | 先行・後続。時間順に並べただけでは依存を示したことにならない |
| 完了条件 | I5。フェーズごと |
| 現在地 | 進行中の計画なら、今どこか |
| 担当 | 誰が持つか |

ガント図は依存線・マイルストーン・進捗率のいずれかを欠くと、
「遅れたとき何が連鎖するか」が読めず、進捗レビューに使えなくなる。

### 2.7 サイクル系 (サイクル・PDCA・フライホイール・三角循環)

一周の周期 (月次か四半期か)／回る向き／各工程の入力と出力／
**輪が止まる条件**／中心を置くなら中心は総称語の再掲ではなく周回数・現在地・対象を持つ。

「PDCA」の 4 象限に「継続改善」を中心に置くのは、定義の再掲であって情報ではない。

### 2.8 グラフ・チャート

| スロット | 内容 |
|---|---|
| 単位と桁 | 円・件・%・人。千・百万の別 |
| 軸の起点 | 0 起点か。切っているなら**切っていることを書く** |
| 尺度の最大値と向き | レーダー・ゲージ・ヒートマップ。「外側ほど優位」まで |
| 色スケールの境界値 | ヒートマップ。「少ない/多い」だけでは段の意味が読めない |
| 段間の転換率 | ファネル。落差が主題なのに暗算させない |
| 合計 | 積み上げ棒。総額の推移を主張するなら合計値を出す |
| 実績と予測の境目 | 混在させるなら区別する |

**ゲージは期間の経過率を持つ。** 達成率 68% は、期の 5 割経過なら先行、
9 割経過なら未達確定で、示唆が正反対になる。経過率の無いゲージは評価できない。

### 2.9 比較・分類・位置図 (比較表・マトリクス・四象限・ベン図・権限表)

| スロット | 内容 |
|---|---|
| 分類の関数 | 読者が自分のケースを図の上に置けること。境界値・判定基準まで |
| 評価の基準 | 何をもって ○ / × か |
| 単位の統一 | 工数と暦日を同じ表で足し引きさせない |
| 補集合 | ベン図はどちらにも入らない領域の意味と件数 |
| 既定値と例外 | 権限表は表に無い役割・代理・不在時の扱い |
| 判定不能の扱い | 評価できない観点を空欄にせず、そう書く |

**焦点の選定は図の幾何と一致していなければならない。**
四象限で「p1 が最善」と言うなら、p1 が図の上で最善の位置にある必要がある。
一致しないなら、一致させるための軸 (工数の目盛) が欠けている。

### 2.10 主張・提案系 (課題解決・PREP・FABE・バリュープロポジション)

打ち手には**実行主体・期限・コスト**の 3 点。期待効果。前提とリスク。

FABE の Evidence は「検証可能な証拠」を意味する語なので、
出典・時期・件数・ばらつきを持たない Evidence は Advantage の言い換えにすぎない。

バリュープロポジションは**顧客側 (ジョブ・ペイン・ゲイン) が図に無ければ成立しない。**
提供側だけを並べたものは中心付き機能一覧であって、この型ではない。

### 2.11 構造・関係系 (ピラミッド・入れ子・同心円・組織図・人物ネットワーク・マインドマップ)

| スロット | 内容 |
|---|---|
| 序列の軸 | 何の順で並ぶか (I4) |
| 包含の種別 | 部分集合か・制約の継承か・影響範囲か |
| 関係の種類と向き | 組織図は直属と点線報告を描き分ける。ネットワークは働きかけの向き |
| 網羅性 | この枝で全体を覆うか。覆わないなら外に何があるか |
| 決定主体 | 誰が決めるか。変えるのに何が要るか |
| 節点の種別 | 部署と会議体を同じ矩形・同じ線で吊らない |

ステークホルダー図はスタンス (賛成 / 中立 / 反対 / 未接触) を持つ。
これが無いものは関係者一覧表と同じ情報量しか持たない。

## 第 3 部 検査

`scripts/validate-diagram-information.py` が本書を機械検査する。
検査対象は**作例だけでなく生成された成果物も含む** — 作例だけを見る検査は、
「宣言はあるが到達手段がない」型の欠陥を作る。

判定は語彙の存在で行う近似であり、意味の正しさまでは見ない。
そのぶん**取りこぼしはあるが誤検知は少ない**側に倒してある。
検査が通ることは下限を満たしたことを意味し、図がよいことは意味しない。

参照の取りこぼし (I-ER-REF) と孤立節点 (I-REL-ISO) の 2 件だけは、
構造から確定的に判定できるので語彙近似ではなく厳密に見る。
この 2 件は `SEVERITY` へ登録せず error 固定にしてある (`ERROR_BY_DESIGN`)。

**error 重大度の誤検知は、検査そのものを殺す。** 初版はここで 2 度失敗した。
節点の同一性を `name → label → id` の順に「1 つだけ」選んだため、
`nodes` を label で書き `relations` を id で書く入力のほぼ全部へ
「どの関係も持たない」を出した。また `org-chart` が `-chart` の境界一致で
グラフ型と判定され、構造図の必須スロットが掛からなかった。
どちらも `--self-test` の事例として固定してある。

輪の中心・凡例・注記は工程ではないので、関係を持たないことが正しい。
`role` が `core` `center` `hub` `legend` `note` `title` `caption` の
いずれかである節点だけを I-REL-ISO から免除する (両 schema の `diagramNode`
に enum として持たせてある)。
**役割を名乗った節点だけ**を免除するのは、「線が無いこと」を理由に免除すると
検査が空になるためである。

**免除の根拠に `id` を使わない (2026/8 に外した)。** 初版は `id` / `role` /
`kind` / `type` のどれかが役割名と一致すれば免除していた。2 つの誤りがある。

- `id` は識別子であって宣言ではない。`id: "note"` は綴りが偶然そうなった
  だけかもしれず、作図者が「これは注記だ」と述べたことにはならない。
- 本番語彙 (`svgSpec`) の id は `^n-[a-z0-9-]+$` に縛られる。`n-note` は
  役割名と一致しないので、**id 照合では本番の図が構造的に一切免除されない**。
  片方の語彙でしか働かない免除機構は、無いのと変わらない。

`kind` / `type` も外した。`focal` / `store` / `external` は描画スタイルの
語彙であって役割ではなく、どれも線を持つべき節点である。

### 3.1 生成物 (.html) の参照検査 — 復元せず、宣言を運ぶ (2026/8)

参照検査は長く**入力 JSON にしか掛かっていなかった**。描画済み SVG から
実体と関係を復元するには線の端点と矩形を座標で突き合わせるしかなく、必ず
近似が入る。近似で error 重大度の失格を出せば誤検知が出て、上に書いた
「error 重大度の誤検知は検査そのものを殺す」を自分で踏むことになる。

そこで復元をやめ、**レンダラが宣言をそのまま運ぶ**。`render-report.js` の
`declarationAttr()` が、図が申告した実体・節点・関係だけを
`<figure data-srg-declaration="...">` へ載せる。検査器はそれを読んで
JSON 経路と**同一の** `check_referential()` を掛ける。近似は 0 になる。

```
入力 JSON ──宣言──▶ builder ──▶ SVG ──┐
        └─────────宣言をそのまま──▶ figure 属性 ─▶ 同一の参照検査
```

宣言を運ばない図 (本文からの導出図・別レンダラの出力) には属性が付かない。
その図は**参照検査をしていない**のであって、参照が正しいのではない。
集計行は `inspected` (図の体裁を見た数) と `referential` (参照を見た数) を
**別軸で**出す。合算すると、宣言を運ばない図まで「参照は正しい」ことにされる。

slide経路も `render-slide.cjs` が構造図10型の作図宣言をSVG rootへ運ぶ。
`validate-diagram-information.py` はreport/slideで同じ宣言を読み、`inspected`と
`referential`を別軸集計する。宣言の無い図を「参照合格」に数えない。

## 第 4 部 なぜ上限だけが規定されていたか

上限は**作図者を守る**規定である。要素を詰め込みすぎた図は読めない、という失敗は
作図中に目に見えるので、規定として書かれやすい。

下限は**読者を守る**規定で、失敗が作図者から見えない。
主キーの無い ER 図は作図者の画面上では整って見える。
欠けているのは、読者がその図を使って判断しようとした瞬間に初めて現れる。

だから下限は、作図の現場では発見されない。規定と検査で外から入れるしかない。

## 第 5 部 未到達と、その解消の記録 (2026/8 時点)

下限を宣言しても、到達手段が無い箇所は残る。それを黙って緑にしないために書く。

**節を消さずに「解消済み」と追記していく。** 直った経緯は、直した内容より
再発防止に効くことがある。とくに §5.1 は「検査が鳴ったとき、まず疑うべきは
被検査物ではなく述語である」という判断そのものが記録の価値であり、
節ごと消すとその判断だけが失われる。

現在この部で**未解消として残っているのは §5.2 末尾の幾何検査の穴だけ**である
(曲線の交差・文字どうしの衝突・矢じりの向き・`transform` 配下の座標)。
§5.4 は欠番 — 内容は恒久的な書き方の約束として §2.3 へ移した。
番号を詰めないのは、他所からの参照 (§5.2 / §5.6) を壊さないためである。

### 5.1 I3 が鳴っていた 3 件 → 解消済み (2026/8)。原因は凡例文言ではなかった

`er-golden.html` (builders 版) / `medallion-golden.html` / `state-golden.html` に
I3 warning が残っていた。当初これを「凡例の文言が `vendor/scripts/svg-structures.cjs` の定数で、
spec から差し替えられないため」と記録していたが、**原因の見立てが誤っていた**。
実際には 3 件とも凡例を描いており、鳴っていたのは検査器の側である。

- **数え過ぎ**: 語彙カウントが `<text>` の文字色と `<marker>` の矢じりの塗りを
  「分類の色」として数えていた。色を 1 つも使い分けていない図でも 3 色に届く。
- **自己敗北**: `legendStrip` の見本矩形の塗りも数えていた。凡例を描くほど
  色数が増え、凡例を描くほど凡例を要求される閉路になっていた。
- **免責が文言依存**: `凡例|実線|破線|…` の文字列一致で免責していたため、
  凡例を描いていても文言が合わなければ鳴った。

直したのは検査器と `legendStrip` の印 (`data-legend="1"`) であって、
凡例文言の opt 引数化ではない。§I3 の表を参照。

**教訓**: 検査器が鳴ったとき、まず疑うべきは**被検査物ではなく述語**である。
「vendor が握っているから直せない」という因果の帰属は、直せない理由を
外側に置くぶんだけ検証されずに残りやすい。3 件とも実物は正しかった。

### 5.2 `buildHighLevel` が入力に無い線を描く → 解消済み (2026/8)

階層間リンクの入力が無く、添字順の代替規則
`below[Math.min(i, below.length - 1)]` で線を引いていた。
**入力に無い情報を図として断言する**欠陥で、情報が足りない欠陥より重い。
`items[].to` (次段の label または添字) を受ける形へ改め、次の 3 段に整理した。

1. `to` が宣言されていればそれだけを引く
2. 宣言が無く上下の**入力件数**が一致し、どちらの段も上限で切り詰められて
   いない段だけ、上下同位置を対応と読む慣行を適用する
3. どちらでもない段は個々の帰属を主張せず、段レベルのトランクを 1 本だけ引く

代替規則を消して 3 を置いたことが要点である。
「分からないときに何か描く」のをやめ、「分かる粒度でだけ描く」へ落とした。

**規則 2 には抜け穴が残っていた (2026/8 に閉じた)。** 件数の比較が
`Math.min(LEVEL_ITEMS, …)` を**通した後**の値どうしだったため、7 件の段と
9 件の段がどちらも 4 に丸められて「一致」と判定され、存在しない 1:1 対応を
4 本の線で断言していた。代替規則を消しても、**クランプが述語の意味を
書き換える**という同じ結果に別経路で戻っていたことになる。

一般化すると: 表示のための丸めを述語の入力に使ってはならない。
丸めは「見せ方」の決定であり、「事実が何か」の決定ではない。
判定は丸める前の値で行い、丸めが起きた段はそもそも慣行の対象から外す。

**一部だけが `to` を宣言した段**は、宣言された辺だけを引く。残りへ規則 3 の
トランクを足すと、項目の帰属と段の帰属という 2 つの文法が同じ段に同居し、
線 1 本の意味が読者から確定できなくなる。「線が無い = 関係が無い」と
読まれる危険は残るが、無い関係を描く危険より軽い。

**同時に見つかった描画側の欠陥 2 件** (どちらも文言の検査では捕まらない):

- `kit.trunkPaths` が分岐の横走りを**宛先の上辺 `p.y` そのもの**で行っていたため、
  横線が矩形の枠線と同一直線上に重なって消え、矢じりも横向きのまま辺へ刺さっていた。
  読者からは「分岐が描かれていない」ように見える。段間の空きへ `trunkY` を立て、
  最後に垂直で上辺へ落として矢じりを下向きにするよう改めた。
- 同じ段間を走る複数本が全部 `elbowPath` の既定の中点で折れるため、
  区間が重なった 2 本が 1 本に見えて本数が読めなかった。
  `opts.mid` を開け、呼び出し側が本数分の車線へ散らせるようにした。

**教訓**: この 2 件は「必要な情報が spec に載っているか」を見る検査を全て通る。
線は引かれており、値も正しい。壊れているのは**描かれた結果**だけである。
情報の下限は spec を読めば検査できるが、描画の破綻は描いた **SVG の座標** を
読まないと分からない。要素を 1 つずつ見る検査では原理的に届かない
——壊れているのは要素そのものでなく、要素**間の重なりという関係**だからである。

**この穴は塞いだ (2026/8)**: `validate-svg-diagram.py` に幾何関係を見る
3 コードを足した (いずれも warning。ゴールデンは `--strict` なので作例では error として効く)。

| コード | 見るもの | 対応する欠陥 |
|---|---|---|
| D19 | コネクタの直線区間が箱の辺と共線で 12px 以上走る | 線が枠へ溶ける (上記 1 件目) |
| D20 | 別々のコネクタの直線区間が共線で 12px 以上重なる | 本数が読めない (上記 2 件目) |
| D21 | コネクタの直線区間が箱 (帯・枠を除く) の内側を 12px 以上貫く | 無い経路を読ませる |

12px 未満を黙らせるのは、コネクタが必ず箱の辺で終わる以上、閾値 0 では
正常な着地が全件引っ掛かるため。D21 が他の矩形を内包する矩形を除くのは、
レーン帯やグループ枠を横切るのは正当な語彙だからである。

**まだ覆えていない**: 曲線・円弧の交差 (直線区間だけを見ている)、
文字どうしの衝突 (D18 は箱に対する収まりだけ)、矢じりの向きが意味と合っているか、
`transform` 配下・入れ子座標系 (座標から実位置を測れないので見送っている)。
ここは引き続きスクリーンショット目視が最後の砦である。

### 5.3 スイムレーンの線にラベルが無い → 解消済み (2026/8)

`connector()` へ `label` を渡していない唯一のビルダーだった。
`opts.links` (§5.6) を入れたことで辺が `label` を運べるようになったので、
**帯をまたぐ線にだけ**受け渡し物を載せるようにした (§2.4)。
同一レーン内は同じ担当の連続作業で受け渡し物が存在しないため書かない —
全部の線に書くと、意味の無いラベルが意味のあるラベルを埋もれさせる。

### 5.5 schema が線種の凡例を表現できない → 解消済み (2026/8)

`legend.items[].color` を必須から外し `kind: fill | line | dashed | double | thick`
を追加した (`schemas/structure.schema.json` と `report-structure.schema.json` の両方)。
`svgSpec.source` / `svgSpec.asOf` も追加し、出所と時点を図の**内側**へ描くようにした。

**なぜ「内側」なのか**: 本契約は冒頭で「figcaption にしか無い情報は無いのと同じ」と
書いている。図は単独で引用され、スクリーンショットで貼られ、スライドへ切り出される。
そのとき figcaption は付いてこない。出所が図と同じ矩形の中にあるかどうかは、
体裁の問題ではなく**根拠が生き残るかどうか**の問題である。

**実装 (`vendor/scripts/svg-structures.cjs` の `frame`)**: 出所行と明示凡例は
builder が計算したレイアウトの**外**へ帯として足し、viewBox 高をその分だけ伸ばす。
builder の領域計算 (`CANVAS.height` / `kit.area`) に触れないので、
凡例が 2 行へ折り返しても中身と重なりようがない。
14 のビルダーを個別に直す代わりに、干渉しない場所を選んだ形である。

### 5.6 スイムレーンが位置から順序を作っていた → 解消済み (2026/8)

`buildSwimlane` は `order` 未指定の升目へ位置の連番 (`レーン番号 × 工程数 + 列`) を
既定の順序として与え、その順に鎖を引いていた。すると `order` を書かない入力 —
表から起こしたレーン図、`edges[]` を持つ `svgSpec` の射影 (`projectLanes`) — で、
図が「レーン 1 の全工程が終わってからレーン 2 が始まる」と主張していた。
**入力のどこにもそう書かれていない。**

線の根拠は次の 3 段で決める (`swimlanePairs`)。上から順に当たり、
最初に見つかった宣言だけを使う。

| 段 | 根拠 | 引く線 |
|---|---|---|
| 1 | `opts.links` (`svgSpec.edges` の射影) | 両端が解決できた辺だけ。解決できない辺は落とす |
| 2 | `step.order` | order が**書かれている升目だけ**を昇順に鎖へ繋ぐ |
| 3 | 宣言なし | 同一レーン内を `step` 昇順に繋ぐだけ。レーンをまたぐ線は引かない |

段 3 が「同一レーン内だけ」なのは、`step` (工程列) は入力が与えた順序軸であり
投影にすぎないのに対し、レーン間の順序は入力のどこにも無いからである。
レーンをまたぐ受け渡しを見せたければ `edges[]` か `order` を書く。
**書かなければ線は出ない。これは機能の欠落ではなく、嘘をつかないことの代償である。**

#### 型に内在する順序を持つか — 捏造クラスの棚卸し

同じ問いを他の構造ビルダーへも当てる。

| ビルダー | 型に内在する順序 | 宣言が無いときの既定 | 状態 |
|---|---|---|---|
| `buildSwimlane` | `step` (工程列) のみ。レーン間には無い | 同一レーン内の列順だけ | 解消済み (本節) |
| `buildHighLevel` | 段 (level / group) の上下のみ。段内には無い | 段レベルのトランク 1 本 | 解消済み (§5.2) |
| `buildSequence` | メッセージの記述順 (時間軸そのもの) | 記述順。これは入力が宣言している | 問題なし |
| `buildArchitecture` | 無い (ゾーンは分類であって順序でない) | `opts.links` のみ。無ければ線なし | 問題なし |
| `buildDataFlow` | 無い (向きは辺が持つ) | 宣言された辺のみ | 問題なし |
| `buildMedallion` | 段の昇格順 (bronze → silver → gold は型の定義) | 隣接段の連結 | 型が順序を持つので捏造でない |

判定の規準は一つ。**「その順序は型の定義から出てくるか、入力から出てくるか、
描画位置から出てくるか」**。三つ目だけが捏造である。
