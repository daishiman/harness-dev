# Information Design (表現物の情報設計) — deep knowledge card

> knowledge_id: `information-design` / status: `seed-example`。特定の画面様式やチェックリストを絶対視せず、**「誰が・どの文脈で・何を達成するか」から情報の優先順位を先に決める**手順そのものを正本とする。適用先は画面に限らず、report・slide・CLI 出力・通知・エラーメッセージ・ドキュメントなど**あらゆる表現物**。

## 目的

保持しているデータを、受け手が**その利用文脈で最短の認知コストで目的を達成できる形**へ翻訳する。「見た目を良くする」ことではなく、情報の意味的な順序付け・取捨選択・加工を設計判断として明示し、視覚表現をその写像として導出できる状態にする。

## 背景

表現物の品質は「設計 (何を出すか) が終わってから装飾 (どう見せるか) を足す」という工程分割によって上限が決まってしまう。保存形式のまま全要素を等価に並べ、後から色と罫線と説明文を足す作り方は、情報量が多いほど「じっと見ないと何も入ってこない」状態へ収束する。原因は美的センスの欠如ではなく、**優先順位付けという設計判断が省略されたまま形式が先に固定される**という手順の問題である。したがって対策も手順として持てる。逆に、優先順位を決めてから視覚変数へ写像すれば、装飾は「これは押せる」「これは選択中」「ここに機能が隠れている」という意味の担い手になり、説明文で埋める必要が消える。

## 解決する問題

- 保存形式 (DB の値・API のフィールド) をそのまま表示形式として採用し、受け手が頭の中で変換させられる (生年月日を見せて年齢を計算させる、絶対日時を見せて「何日前か」を計算させる)。
- 全要素が同じ大きさ・同じ濃度で並び、どこから見ればよいか分からない (強弱の欠如)。
- ラベル・罫線・説明文など「無くても伝わる要素」が削られず、本体の情報を圧迫する。
- 最初に一つの形式 (表・リスト・箇条書き・JSON ダンプ) を作ってしまい、他の形式との比較機会が失われる (早期形式固定)。
- 装飾が「今風に見せる」ために使われ、操作可能性・状態・重要度といった意味を運んでいない。
- 情報の物理的な近さがグループの意味と一致せず、無関係な要素が隣接して誤読を生む。
- 「設計」と「デザイン」を別工程・別担当に分割し、前工程の出力が後工程の到達可能な品質の上限を決めてしまう。

## 中核概念

- **文脈先行 (context of use first)**: 誰が・どの環境で・どの task を・どの頻度で・失敗したら何を失うか。この 5 点が決まるまで形式を決めない (ISO 9241-210 の context of use)。記録する文脈プロファイルは少なくとも役割・熟練度・利用頻度・端末と入力手段 (支援技術を含む)・通常/最大付近の情報量・誤操作時の損失と回復可能性とし、職種名や表現物の種別だけから密度を決めない。確定できない項目は未知の仮説として記録し、実データや利用観測で更新する。
- **優先順位の明示化 (explicit ranking)**: 「重要そう」ではなく *task 頻度 × 失敗コスト* で順位を付ける。順位は主観の告白ではなく設計判断であり、記録・レビュー・反証の対象になる。
- **グループ化と近接 (grouping / proximity)**: 意味の束を作り、束の境界を余白で表す。線や枠は最後の手段であり、近接で足りるなら引かない (Gestalt の近接・類同)。
- **削減 (elimination)**: 「無くても伝わるもの」は削る。削除は損失ではなく、残す要素の相対的な強さを上げる操作である (Tufte の data-ink ratio)。**削除には理由を残す** — 理由なき欠落は「漏れ」と区別できない。削除は規則ではなく反証可能な**削除仮説**として持つ: 削除候補・代わりに意味を伝える手掛かり・誤読時の影響・検証方法・復元条件。意味が曖昧になる、誤操作コストが高い、検証できない場合は残す。
- **加工 (transformation)**: 保存値と表示値を同一視しない。生年月日→年齢、絶対日時→相対表現、真偽値→状態語のように、利用文脈で意味が立つ形へ変換する。**この自由度は Clean Architecture の依存規則が前提** — 表示が中核ルールから隔離されているからこそ、表示形式を中核に触れずに変えられる (本カードが `depends_on: clean-architecture` である理由)。変換規則は domain model (正本の意味と値) から view model (表記・単位・語彙・順序・集約・権限別可視性) への写像として明示し、金額・比率・状態などの業務値は正本側で導出する — 表示層が独自に再計算すると複数 client で値がずれる。
- **相対表現から正確値への到達**: 「明日」「一週間前」などの相対表現や短縮識別子は走査を速めるが、正確な日時・タイムゾーン・完全な識別子へ同じ文脈から到達できるようにする。tooltip だけに閉じず、詳細表示・補助テキスト・展開などキーボード/タッチ/支援技術でも使える手段を持たせる。監査・予約確定・順序比較では正確値を初期表示にしてよい。
- **形式の比較選定 (form selection)**: 表・グリッド・リスト・カード・図・散文はそれぞれ得意が違う (表=ソート/絞り込み/その場編集、グリッド=視覚要素主体、リスト=順序と混在、カード=機能追加のしやすさ)。**2 つ以上を比較した記録**を残してから選ぶ。これらの形式は例示であり上限付きの完全リストではない (**表現パターンの open-world registry**): pattern ごとに `pattern_id`・解く問題・適合/非適合 task・文脈プロファイル・意味構造・variant・リスク・検証指標・根拠・鮮度を記録し、新しい複合/可視化/段階開示 pattern を発見・評価して統合する。類似 pattern は重複登録せず差分を variant にする。
- **ラベルと意味関係 (labels and relationships)**: 入力欄は placeholder やアイコンだけに依存せず、原則として見えるラベルを保ち、`label` と control・見出しと領域・説明/エラーと対象を意味的に関連付ける (WCAG 1.3.1)。表示専用データの反復ラベルは削除仮説の対象にできるが、`dl/dt/dd` や表見出しなどの意味構造は失わない。操作部品は可視ラベルの有無にかかわらず accessible name を持つ。
- **視覚変数への写像 (emphasis mapping)**: 確定した順位を、位置 (上/左が高位)・サイズ・太さ・色・余白へ写像する。色だけに意味を担わせない (WCAG 1.4.1)。順位の低さを到達不能と同義にしない。削除・加工・写像のいずれも、`usability-accessibility` が要件側で確定する操作契約 (POUR・適合水準・回復導線) を下回ってはならない — 本カードが `depends_on: usability-accessibility` である理由。
- **意味的装飾 (semantic styling)**: 装飾の目的は「押せる」「選択中」「重要」「隠れ機能あり」を表すこと。意味に紐づかない装飾は削減対象。装飾は共通の**視覚文法**に従わせる: 近接=同じまとまり、整列=比較軸と読み順、余白=階層と境界。区切り線は余白だけでは境界が伝わらないときに使い、アイコンは既知の意味を補助するだけでラベルの代わりにしない。画像は識別・比較・状態理解に寄与するときだけ強調し、装飾画像に情報階層を奪わせない。
- **固定数値ではなく実測 (measure, don't fix)**: 項目数・列数・カード数・文字数・余白量に汎用の固定上限を置かない。実データの分布と極端値・viewport・入力手段・性能・task 成否から breakpoint・密度・折返し・段階開示を決め、プロジェクト固有の閾値には根拠と再評価条件を付ける。
- **設計とデザインの不可分性**: 「ここから設計・ここからデザイン」という線引きをしない。情報の順序付けそのものがデザインであり、後段の装飾者がどれだけ優秀でも前段が決めた上限は超えられない。

## 適用条件

- 人間が読む表現物を生成・レビューするとき (UI 画面、report、slide、ダッシュボード、CLI 出力、通知、エラーメッセージ、仕様書)。
- 出せる情報量が受け手の一度に処理できる量を上回り、取捨選択が避けられないとき。
- 受け手と利用文脈が一つに定まる、または文脈ごとに別表現を作る余地があるとき。
- 新規作成だけでなく、情報は揃っているのに発見・理解・操作へ時間がかかる既存の表現物を改善するとき。
- design token や既存 component がある場合も、component を当てはめる前に情報構造と意味関係を確定するとき。

## 非適用条件

- 機械が消費する成果物 (JSON/DB スキーマ/ログの構造化フィールド) — ここでは網羅性・安定性・後方互換が優先し、削減や加工はむしろ有害。
- 監査・法定表示・原本性が要件で、**元の値をそのまま**提示する義務があるとき (加工は併記に留める)。その情報は削除仮説に含めず、可読性は順序・グループ・段階開示・代替表現で改善する。
- 習熟した専任者が長時間・大量に操作する高密度業務画面。一覧性と一括操作の効率が学習容易性より重い場合、表形式・高密度・等価表示が正解になりうる (Nielsen のユーザビリティ 5 指標のうち efficiency を優先する状況)。
- 探索的な使い捨て成果物で、寿命が短く投資が回収できないとき。
- 表現パターンの候補に一次資料・適用条件・検証可能性がまだ無い段階 — 推奨 pattern へ昇格させず探索候補に留める。

## トレードオフ・失敗モード

- **学習容易性 ⇄ 効率性**: 情報を削って強弱を付けるほど初見は分かりやすくなるが、熟練者の一覧性・一括操作は落ちる。どちらを取るかは context of use が決めるのであって、原則が決めるのではない。
- **加工 ⇄ 検証コスト**: 表示値を加工するほど元データとの突合テストが増える。加工の各件に「どの task を助けるか」を書けないなら加工しない。
- 優先順位付けを飛ばしたまま視覚変数だけ調整し、「なんとなく今風」だが読み順が崩れた表現物を作る (最頻の失敗)。
- 削減を進めすぎて、文脈を持たない受け手が識別できなくなる (会員 No. のラベルまで落とす等)。削減の停止条件は「ラベルなしで受け手が識別できるか」。
- 「シンプルにする」を目的化し、必要な状態表示・エラー理由・可逆性の手がかりまで削る。
- 原則を checklist 化して機械適用し、非適用条件 (高密度業務画面・監査表示) に当てはめて品質を落とす。
- 強弱を色だけで表現し、色覚特性・モノクロ印刷・低コントラスト環境で情報が消える。
- ラベル削除を美観ルールとして適用し、フォームの見えるラベル・accessible name・項目間の意味関係・翻訳時の明確さを失う。
- 余白を増やせば読みやすいと決めつけ、大量反復操作のスクロール量と視線移動を増やす。逆に区切り線を増やし、すべての境界を同じ強さにする。
- アイコンだけで操作を表し、文化差・学習差・拡大表示・支援技術で意味が伝わらない。画像の強調が主情報を押し下げ、代替テキストや読込失敗時の情報を欠く。
- 相対時刻や短縮識別子を便利な表示として固定し、監査・同名識別・タイムゾーン境界・期限直前で正確値へ到達できなくする。
- 表示加工を業務値の導出まで広げ、複数 client で結果がずれる。
- 固定上限を「ベストプラクティス」として全表現物へ転用し、実データの長文・多言語・拡大表示・将来の pattern を排除する。
- 情報設計の結論を完成画像か実装コードだけに残し、pattern 選定・削除仮説・正確値への導線・検証結果を次の変更で再利用できない。

## 目的達成への寄与

- 要件定義段階で「この表現物の受け手・task・優先順位」を宣言させることで、実装後の主観的な「なんかダサい」を**設計判断への差し戻し**に変換できる (レビューが好みの表明でなくなる)。
- 順位・グループ・削除理由・加工理由が構造化データとして残るため、生成 AI・人間のどちらが作っても同じ根拠で検証できる。決定論ゲート (`../../../scripts/validate-information-priority.py`) が手順の順序制約 (装飾より前に順位が確定していること) を機械検査する。
- 成果は「見た目の評価」ではなく outcome で測る: 目的達成までの操作数・初見での到達率・誤操作率・問い合わせ件数。装飾の量では測らない。task completion・time-to-find/first-action・取消/回復・検索/絞込/展開の利用も観測し、単一の平均値で確定せず文脈プロファイル別の差・観察/インタビュー・アクセシビリティ確認を併用して pattern と削除仮説を更新する。クリック数だけを価値と読み替えず、計測のために個人情報を過剰収集しない。

## ヒアリング・判断観点

- この表現物を見るのは誰で、その瞬間に何をしようとしているか。片手か両手か、会話しながらか、集中しているか。
- 受け手が最も頻繁に取る行動は何か。それが失敗すると何を失うか。
- 出せる要素のうち、無くても伝わるものはどれか。削ったとき識別できなくなるものはどれか。
- 保存形式のまま出している値のうち、受け手が頭で変換しているものはどれか。
- いま選んでいる形式の対抗案は何か。なぜそれを採らなかったか。
- 使っている装飾のそれぞれは、どの意味 (操作可能・状態・重要度・隠れ機能) を運んでいるか。運んでいないものはどれか。
- この表現物は初見者向けか熟練者向けか。両方なら分けられるか (密度 variant・役割別 view)。
- 削除候補ごとに、意味を代替する手掛かり・誤読の影響・検証方法・復元条件はあるか。フォームの見えるラベルと意味関係を保っているか。
- domain model と view model の境界はどこか。相対値・短縮値・加工値から正確値と出典へ、すべての入力手段で到達できるか。
- 選んだ pattern は registry のどの条件に合い、どの反証で variant 変更または撤回するか。
- 実利用のどの指標と定性観察で目的達成を判定し、どの文脈プロファイル別に再評価するか。
