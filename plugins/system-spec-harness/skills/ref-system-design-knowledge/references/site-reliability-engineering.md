# Site Reliability Engineering — deep knowledge card

> knowledge_id: `site-reliability-engineering` / status: `seed-example`。可用性 100% を目標にせず、目標値・許容誤差・観測手段を先に決めてから基盤構成を選ぶ。

## 目的

実行基盤・環境・リソースの構成を、目標信頼性 (SLO) と運用負荷の観点から選び、稼働中の状態を観測して是正できる形にする。

## 背景

実行基盤の選定は往々にしてサービス名の比較として行われるが、決めるべきは「どの水準の信頼性を、どれだけの運用コストで満たすか」である。SRE はこれを SLI (測る指標)・SLO (満たす目標)・エラーバジェット (許容する逸脱量) として明文化し、機能追加と安定性のどちらに資源を割くかを合意可能な数値に還元する。基盤構成 (環境分離・binding・スケーリング単位・デプロイ境界) はこの目標から導かれる従属変数であり、逆ではない。あわせて、環境差分を人手手順ではなくコードとして持つこと (Infrastructure as Code) が、再現性と復旧速度の前提になる。

## 解決する問題

- 目標信頼性が未定義のまま冗長化・監視を積み、費用と運用負荷だけが増える。
- 環境 (本番/検証/ローカル) の差分が人の記憶に残り、本番でのみ再現する障害が生まれる。
- 稼働中の構成 (環境変数・binding・シークレット) を外から確認できず、障害時に仮説を検証できない。
- 復旧手順が実行されたことのない文書として存在し、実際の障害時に機能しない。
- 手作業の運用 (トイル) が担当者に固定化され、人の交代で運用品質が落ちる。

## 中核概念

- **SLI / SLO / エラーバジェット**: 利用者視点の指標を選び、目標値と許容逸脱量を決め、逸脱時の行動 (機能追加の停止・是正優先) を事前に合意する。
- **観測可能性**: 稼働中の実体 (バージョン・構成値の由来・依存の健全性) を外部から確認でき、症状から原因へ辿れる状態を保つ。
- **環境の再現性 (Infrastructure as Code)**: 環境と binding を宣言として持ち、差分を人手手順ではなく差分適用で解消する。
- **段階適用と復旧**: 変更を段階的に反映し、逆操作 (ロールバック・復元) を実際に実行して検証する。
- **キャパシティと需要**: スケーリング単位と上限、コールドスタートや同時実行の制約を、目標指標に対する影響として扱う。
- **トイル削減とポストモーテム**: 反復手作業を自動化対象として計上し、障害後は非難でなく仕組みの欠落として記録する。
- **前提知識との関係**: 本カードは `continuous-delivery` を前提とする (`depends_on`)。段階適用・逆操作・稼働中の実体の確認は、デプロイパイプラインと単一の正本経路が提供する仕組みの上に成り立つため。

## 適用条件

- 利用者に対する可用性・遅延の期待があり、逸脱を検知して是正する責任を負う。
- 環境が複数あり (本番・検証・ローカル)、差分が事故要因になり得る。
- 観測・デプロイ・復旧を自動化する余地があり、運用担当が継続的に関与する。

## 非適用条件

- 利用者も稼働期間も限定された使い捨て環境に、SLO 運用とエラーバジェット会計を先行適用しない。
- 実測データが無い段階で SLO を数値確定しない (暫定値であることを明示して観測から始める)。
- マネージド基盤が既に保証している性質を、自前の冗長化で二重化しない (責任分界点を先に確認する)。

## トレードオフ・失敗モード

- SLO を高く置きすぎ、変更速度と費用を不必要に犠牲にする。
- 監視項目を増やすこと自体を目的化し、誰も見ないダッシュボードとアラート疲れを生む。
- Infrastructure as Code を導入しても本番へ手作業変更を許し、宣言と実体が乖離する (drift)。
- 復旧手順を一度も実行せず、実際の障害時に前提条件の欠落が判明する。
- 稼働中ビルドの素性を確認する手段を用意せず、「コードは直っている」と「本番が直っている」を区別できなくなる。

## 目的達成への寄与

- 基盤選定の判断を、製品名の比較ではなく目標指標への寄与として記述でき、後から根拠を検証できる。
- エラーバジェットにより、機能追加と安定化の優先順位を都度の力関係でなく事前合意で決められる。
- 稼働実体の観測手段を要件に含めることで、障害の切り分け時間を短縮し、原因究明のラウンド数を減らす。

## ヒアリング・判断観点

- 利用者にとっての「動いている」は何を指すか。それはどの指標で測れるか。
- 目標値を外したとき、何を止め、何を優先するか。誰が判断するか。
- 環境差分はどこに宣言されているか。本番への手作業変更は禁止されているか、検知できるか。
- 稼働中の成果物が、どのコードに対応するかを確認する手段はあるか。
- 復旧手順は実行済みか。最後に実行したのはいつか。
