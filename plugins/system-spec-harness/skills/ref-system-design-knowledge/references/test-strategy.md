# Test Strategy — deep knowledge card

> knowledge_id: `test-strategy` / status: `seed-example`。カバレッジ数値やテスト件数を目的化せず、「どの失敗を、どの層で、どれだけ速く検出するか」を設計する。

## 目的

検証手段を層ごとに配分し、想定する失敗が本番到達前に、原因を特定できる粒度で検出される状態をつくる。

## 背景

テストは書けば書くほど良くなるものではない。層の選択を誤ると、遅くて壊れやすいテストが積み上がり、失敗が原因を指さないまま無視されるようになる。テストピラミッドは「速く安定した低層テストを多く、遅く不安定な高層テストを少なく」という配分の指針であり、Software Engineering at Google は同じ問題をテストサイズ (small / medium / large) と実行時間・依存の観点で定式化している。重要なのは形ではなく、各層が担当する失敗の種類と、失敗したときに読み取れる情報である。

## 解決する問題

- 高層 (E2E) に検証を寄せ、実行が遅く不安定になり、失敗が調査されず無視される。
- テストが実装詳細 (内部構造・DOM 構造・一時生成物の配置) に結合し、リファクタリングのたびに壊れる。
- 契約 (API・スキーマ・列挙値) の不整合が、実行時まで検出されない。
- カバレッジ率が閾値を満たしても、重要な分岐や失敗経路が未検証のまま残る。
- 同じ検証が複数層で重複し、実行時間だけが増えて検出力が上がらない。

## 中核概念

- **層別の責務配分**: 単体は分岐とルール、結合は境界と契約、E2E は主要利用経路の疎通に責務を限定する。
- **テストサイズ (実行環境の制約)**: 依存 (ネットワーク・DB・時刻・並行性) の有無でサイズを分類し、速い層を既定の実行対象にする。
- **観測可能な振る舞いへの結合**: 内部構造でなく外部から観測できる結果と不変条件を検証対象にする。
- **契約テスト**: 提供側と利用側が同じ契約定義を情報源にし、リテラル/スキーマの多重定義を検出する。
- **失敗時の診断可能性**: 失敗名・入力・差分から原因箇所が一意に絞れることを、テスト設計の受入条件に含める。
- **ゲートと改善ループ**: 品質ゲートは合否だけでなく、失敗時の原因分析・修正・同一コマンド再実行までを含む手順として定義する。
- **前提知識との関係**: 本カードは `clean-code` と `usability-accessibility` を前提とする (`depends_on`)。小さく単一目的の単位と意図が読める命名があって初めて層別配分と失敗時の診断可能性が成り立ち、適合水準と回復導線の受入基準が受入/E2E 層で検出すべき失敗の一覧を与えるため。

## 適用条件

- 変更が継続し、回帰の再発コストが検証コストを上回る。
- 検証対象の契約 (入出力・状態遷移・権限) を明文化できる。
- CI などで自動実行でき、失敗が担当者へ届き是正される運用がある。

## 非適用条件

- 仕様が未確定の探索段階で、全層のテストを先行整備しない (残す実装が決まってから固める)。
- 外部サービスの挙動そのものを検証対象にしない (契約の消費側の扱いを検証する)。
- 生成物 (キャッシュ・ビルド出力) の物理配置など、設計契約でない実装詳細を合否条件にしない。

## トレードオフ・失敗モード

- カバレッジ閾値の充足を品質と読み替え、重要な失敗経路の未検証を隠す (Goodhart 化)。
- モックを積み過ぎ、実装と乖離した世界だけで合格するテスト群になる。
- 不安定テスト (flaky) を再実行で通し、検出力を失いながら実行時間だけ払い続ける。
- E2E で網羅しようとして実行時間が伸び、開発中に回らなくなる。
- 検査ツールが情報源の一部しか見ておらず、同一定義の 3 件目がすり抜ける (網羅範囲の未定義)。

## 目的達成への寄与

- 「どの失敗を防ぐためのテストか」を層ごとに記述でき、テスト追加の是非を目的から判断できる。
- 契約テストにより、仕様変更が利用側へ波及する箇所を実装前に特定できる。
- 品質ゲートを改善ループ込みで定義することで、合否表示ではなく是正の完了を確定条件にできる。

## ヒアリング・判断観点

- 本番で起きて最も高くつく失敗は何か。それはどの層で最も速く検出できるか。
- 検査ツールが参照すべき情報源は何件あるか。すべて列挙されているか。
- どのテストが実装詳細に結合しているか。リファクタリング時に壊れてよいのはどれか。
- 失敗時に誰が何をするか。同一コマンドでの再実行まで手順に含まれているか。
