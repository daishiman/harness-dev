# Cloud Architecture Patterns — deep knowledge card

> knowledge_id: `cloud-architecture-patterns` / status: `seed-example`。マネージド基盤の上で「どのデータをどこに置き、どの境界で失敗を許すか」を、サービス名の比較ではなく制約と失敗の向きから決める。

## 目的

マネージドなクラウド基盤 (オブジェクトストレージ・リレーショナル/KV ストア・エッジ実行環境・キュー) を組み合わせるとき、データの配置・整合性の境界・劣化の順序を、後から検証できる根拠とともに決める。

## 背景

クラウド基盤の選定は製品名の比較として語られやすいが、実際に設計を規定しているのは各サービスの制約 (1 行あたりの上限、リクエストあたりの CPU 時間、トランザクションが及ぶ範囲、書込みの伝播遅延) である。これらは「速い/安い」という尺度では表せず、**何が原子的に成立し、何が成立しないか**という不変則の境界として現れる。この境界を明示しないまま構成を組むと、平常時は動作するが、障害時にどちらのデータが正で、どちらを捨ててよいかが誰にも分からなくなる。

とりわけ、バイナリ (画像・添付・ログ) と、それを説明するメタデータ (所有者・作成時刻・寸法) は、同じ「1 件のデータ」に見えて要求される性質が異なる。前者は大きく不変で検索されない。後者は小さく可変で頻繁に検索される。この違いを配置に反映しないことが、クラウド上で最も再現性の高い性能劣化の原因になる。

## 解決する問題

- 大容量バイナリを DB 行へ格納し、本文を必要としない一覧クエリまで巨大な行の読み出しに巻き込む。
- 複数のマネージドサービスに跨る書込みを、暗黙に原子的だと仮定して整合性の破れを設計外に置く。
- 障害時に何を先に諦めるかが未定義で、劣化の仕方が実行環境や実装者ごとにばらつく。
- 署名や認可を通さない公開 URL でバイナリを配信し、識別子の漏洩がそのまま内容の漏洩になる。
- サービス固有の制約 (実行時間・ペイロード上限・同時実行) を非機能要件として書き出さず、規模が伸びた時点で設計をやり直す。

## 中核概念

- **大容量バイナリはオブジェクトストレージへ、メタデータだけを DB へ (blob offloading)**: 検索・整列・結合の対象になるのは小さく可変なメタデータだけである。バイナリはキーで参照し、DB にはキー・バイト数・寸法・MIME 型のみを残す。一覧の読み出し費用を、保存したバイナリの総量から切り離す。
- **原子性の境界を宣言する**: トランザクションが及ぶ範囲を明示し、その外側は補償 (compensating action) か再試行で扱う。跨る書込みには順序を固定し、壊れる向きを回復可能な側 (孤児オブジェクトが残る) へ寄せる。
- **冪等キーによる安全な再送**: ネットワーク境界を跨ぐ書込みは必ず二重に届きうる。呼出し側が生成した鍵で重複を吸収し、再送を例外処理でなく通常経路にする。
- **制約を非機能要件として先に書く**: 実行時間上限・ペイロード上限・同時実行数・行サイズ上限を、選定理由ではなく設計入力として記述する。
- **配信経路と認可の一致**: 保存場所への直接到達を塞ぎ、配信は必ず認可を通す経路を経由させる。識別子は決定的でも内容を推測させない形にする。
- **段階的な劣化の順序**: 容量・遅延・品質が衝突したとき、どれを先に犠牲にするかを仕様として固定し、実装者の裁量に委ねない。
- **前提知識との関係**: 本カードは `clean-architecture` と `site-reliability-engineering` を前提とする (`depends_on`)。保存場所や基盤サービスを中核ルールから隔離する依存規則があって初めて配置と整合性境界を中核に触れずに選べ、劣化順序と制約の非機能要件化は SLO とエラーバジェットを判断基準にするため。

## 適用条件

- マネージドな複数サービス (ストレージ・DB・実行環境) を組み合わせ、単一トランザクションで閉じない書込みがある。
- 利用者が生成するバイナリ (画像・添付) を保存し、その一覧や検索を別途提供する。
- 実行環境に明示的な資源上限があり、超過が機能の失敗として現れる。

## 非適用条件

- 単一ノード・単一 DB で完結し、外部ストレージを持たない構成に、跨る書込みの補償設計を先行導入しない。
- バイナリが小さく件数も限られる場合 (例: 数 KB のアイコン数十件) に、参照の間接化による往復増を払わない。
- 基盤が既に保証している性質 (オブジェクトストレージ側の耐久性・多重化) を、自前の複製で二重化しない。

## トレードオフ・失敗モード

- バイナリを外へ出すと、DB とストレージが別系になり原子性が失われる。書込み順序の固定と孤児回収を設計に含めないと、参照切れが蓄積する。
- 冪等キーを導入すると、鍵の生存期間と保管場所という新しい状態が増える。期限設計を怠ると、正当な再投稿まで重複として捨てる。
- 認可を通す配信は CDN キャッシュを効きにくくする。閲覧者数が大きい経路にそのまま適用すると費用と遅延が悪化する。
- 制約を非機能要件に書いても、実測せずに数値を置くと「守っているつもり」の仕様になる。上限付近の実測を伴わない宣言は根拠にならない。
- 劣化順序を決めても、超過時の記録を残さないと、仕様どおり劣化したのか単に壊れたのかを事後に区別できない。

## 目的達成への寄与

- データ配置の判断を、製品名ではなく「何が原子的か・何が検索対象か」という検証可能な性質へ還元でき、後から根拠を追える。
- 一覧の読み出し費用を保存量から独立させ、利用が伸びても管理画面の応答が劣化しない構造を先に確保する。
- 壊れる向きを事前に選ぶことで、障害時の復旧手順が「どちらが正か」を都度判断しない決定的な手順になる。

## ヒアリング・判断観点

- そのデータは検索・整列・結合の対象か。それとも識別子で引くだけか。
- 1 回の利用者操作が、いくつのサービスへ書込むか。全部成功か全部失敗かを本当に保証できるか。できないなら、どちらが残る方が回復しやすいか。
- 同じ操作が二重に届いたとき、何を鍵にして重複と判定するか。その鍵は誰が作るか。
- 保存物へ識別子だけで到達できてしまわないか。配信経路は認可を通っているか。
- 目標 (容量・応答・品質) が衝突したとき、先に諦めるのはどれか。超過したことは記録されるか。
