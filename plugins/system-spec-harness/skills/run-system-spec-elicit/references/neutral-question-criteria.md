# 中立な問の基準 (N1-N4) と、推奨の示し方

利用者に投げる問の中立性の**正本**はこのファイルにある。問を作る側 (R0-foundation /
R2-interview / R3-reask / R5-decision-guide) と、問を監査する側 (R6-audit-hearing の軸 2 と、
その起動アダプタである C06 `system-spec-hearing-auditor`) は、どちらもここを参照する。
各プロンプトに基準を書き写さない。写した記述どうしがずれると、作る側が基準どおりに書いた
問を監査側が誘導と判定する、という衝突がまた起きる。

## なぜ 1 か所に置くか

以前は R5 が「比較案と AI 推奨を提示する」と定め、R6 と C06 は「望ましい答えを暗示する
片側の問」を誘導と定めていた。どちらも単独では正しいが、推奨を**どこに**置くかを誰も
決めていなかった。そのため R5 に従って選択肢へ推奨の印を付けた問は、R6 の軸 2 で
誘導と判定された。qa_log は question を凍結するので、その検出は問い直しても消えなかった。

この食い違いは、問と推奨を分けることで解ける。推奨は判断の材料として示してよい。
推奨が問そのものに入り込むと、利用者が選ぶ前に答えが決まってしまう。

## 対象の範囲

- **問**: `qa_log[].question` に逐語で残る文。`AskUserQuestion` で示した選択肢の文言と並び順も含む。
- **推奨**: R5 の `decisions[].recommendation` に残る記録。問の外にある。
- 問の判定は、推奨を提示したかどうかでは決まらない。判定の対象は問の文面だけである。

## 基準

| id | 基準 | 違反の例 | R6 軸 2 の観点 |
|---|---|---|---|
| **N1** | 推奨の印を問に入れない。選択肢に「(推奨)」「おすすめ」「一般的には」を付けない。推奨案を先頭に固定したり、既定で選択済みにしたりしない。推奨は比較の後の別の段で示す (下の「推奨の示し方」)。 | 「A (推奨) / B / C のどれにしますか」、「推奨の A でよいですか」 | (b) 片側 |
| **N2** | 利点と不利な点を対称に書く。問が選択肢の説明を含むときは、すべての選択肢に利点と不利な点の両方を、同じくらいの具体さで書く。一部の選択肢の不利な点だけを書かない。 | 「A は手間が少ない。B は保守が重い」(A の不利な点と B の利点が無い) | (b) 片側 |
| **N3** | 前提を埋め込まない。まだ確定していない事柄を既定の事実として書かない。「決めない」を選べるようにする。利用者が選択肢のどれも採らない道 (別案・追加比較・保留) を、選択肢か自由回答のどちらかで必ず残す。 | 「〜ですよね」「当然〜なので」、未確定の方針を前置きにした問、はい / いいえだけの問 | (a) 断定・前提埋め込み |
| **N4** | 1 問 1 論点にする。独立に決められる論点を 1 問に束ねない。 | 「保存先と保持期間と暗号化をこの案でよいですか」 | (c) 多論点束ね |

判定の単位は 1 つの qa entry である。N1-N4 のどれかに当たる問を、R6 は軸 2 の検出として
重大度付きで報告する (重大度の付け方は R6、重大度から観点の合否への対応は
`../../assign-system-spec-completeness-evaluator/references/aspect-criteria.md` の
「ヒアリング監査 (C06) の重大度と判定の対応」が正本)。

## 推奨の示し方 (R5)

推奨を示すのは R5 の責務のままである。示す位置と順序を次のように決める。

1. **比較**: 2-3 案を同じ比較軸で並べる。並び順は比較軸の順か候補の登録順にし、推奨の順にしない。各案に利点と不利な点を書く (N2)。
2. **推奨 (参考)**: 比較の後に、段を分けて「AI の推奨 (参考)」として示す。推奨する案、理由、注意点、信頼度、確認日時と出典を添える。推奨が利用者の判断を代わりに決めるものではないことを明示する。
3. **問**: 最後に、中立な問で選択を求める。選択肢には推奨の印を付けない (N1)。採用・別案採用・追加比較・保留を選べるようにする (N3)。

qa_log には 3. の問を `question` として残す。`provenance` には推奨を提示したことを書く
(例: `AskUserQuestion / 比較表と AI 推奨 (参考) を提示した後に選択を依頼`)。推奨を示した
事実を隠さないことで、監査側は「推奨を見せたうえで利用者が選んだ」ことを確かめられる。
推奨を見せたこと自体は N1-N4 の違反にならない。違反になるのは、推奨が問の文面に入った場合である。

## 既に凍結された問に違反があったとき

qa_log は append-only で、question と answer は書き換えられない。違反のある問は次の手順で閉じる。

1. 同じ論点を N1-N4 に沿って問い直し、利用者の回答を新しい qa entry として記録する
   (`basis: user-decision` と `answered_at` を付ける)。
2. 旧 entry が確定セルの主たる接地根拠 (`qa_ref`) なら、先に R4-reopen で戻し、新しい
   entry で確定し直す。
3. writer の `supersede-qa` op で旧 entry に `superseded_by` を記録する。`note` には、旧い問の
   どの基準の違反を、どう問い直したかを書く。

置き換えが有効になるのは次の 3 つを**すべて**満たすときだけである。

- (a) 新しい問が N1-N4 を満たす (R6 が判定する)
- (b) 旧い問と同じ論点を扱う (R6 が `superseded_note` と両方の問を照合して判定する)
- (c) 利用者の回答が記録されている (writer が `answer` 非空・`basis: user-decision`・
  旧 entry より後の `answered_at` を決定論で検査する)

writer が `supersede-qa` を通しても、それは (c) を満たしたという意味しか持たない。
(a) か (b) を満たさない置き換えは、R6 が無効と判定し、旧い問を判定の対象へ戻す。
有効な置き換えでは、旧い問の検出は「閉じた検出」として報告に残る。検出を消すのではない。
