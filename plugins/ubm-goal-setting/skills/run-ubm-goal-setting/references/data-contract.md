# UBM目標設定 エージェント間データ契約

Phase間のデータ受け渡し仕様を定義するドキュメント。
各エージェントはこの契約に従ってデータを生成・消費する。

---

## Phase間データフロー図

```
Phase 0 ──[GoalConfig]──> Phase 1-2 ──[PastSummary]──> Phase 3 ──[InterviewData]──> Phase 4 ──[FormattedOutput]──> File
(目標種別確認)          (info-collector)             (owner parent dialogue)      (output-formatter)          (05_Project/UBM/目標設定/)
```

| 契約名 | 生産者 | 消費者 | データ形式 |
|--------|--------|--------|-----------|
| GoalConfig | Phase 0（メインフロー） | info-collector | 構造化テキスト |
| PastSummary | info-collector | run-ubm-goal-setting 親context | マーク付き構造化サマリー（文脈フィールド継承を含む。§2.8） |
| InterviewData | run-ubm-goal-setting 親context | output-formatter | 構造化テキスト（全35フィールド） |
| FormattedOutput | output-formatter | ファイルシステム | Markdown ファイル |

## 1. GoalConfig（Phase 0 → Phase 1-2）

Phase 0 でユーザーから取得し、info-collector SubAgent に渡すパラメータ。

| フィールド | 型 | 必須 | 説明 | 例 |
|-----------|-----|------|------|-----|
| goal_type | enum: `weekly` / `monthly` / `quarterly` | Yes | 目標種別（`bimonthly` は `quarterly` の後方互換の別名。受理して `quarterly` に正規化する） | `weekly` |
| target_period | object: `{start: date, end: date}` | Yes | 対象期間（YYYY-MM-DD形式）。期報は3ヶ月分の月報期間の連結（開始=1ヶ月目の月報開始日／終了=3ヶ月目の月報終了日。例 `{start: 2026-06-29, end: 2026-09-27}`） | `{start: 2026-03-30, end: 2026-04-05}` |
| sections | enum: `detail_only` / `submission_and_detail` | No（導出値・指定不要） | 出力ファイル内のセクション構成。`goal_type = monthly` は `submission_and_detail`（1ファイルの中に提出用セクションと管理用セクションを持つ）、`weekly` / `quarterly` は `detail_only` | `submission_and_detail` |

### バリデーション

- `goal_type` は3つの列挙値のいずれかであること（旧値 `bimonthly` を受け取った場合は `quarterly` として扱う）
- `target_period.start` < `target_period.end` であること
- 日付はYYYY-MM-DD形式であること
- `sections` は `goal_type` から導出する（`monthly` → `submission_and_detail` / それ以外 → `detail_only`）。ユーザー指定は受け取らない
- **どの `goal_type` でも出力ファイルは1本。** 提出用の別ファイルを作らない（**理由: 複数ファイルにまたがると改善・修正のときに反映漏れが起きる**）
- `goal_type = monthly` の出力は1ファイルの中で `# 北原さん提出用（シンプル）` → `# 管理用（詳細）` の順に2セクションへ分け、提出用セクションの `## 【…】` には閉じ括弧の内側に「（提出）」を付ける。**管理用セクションの見出しには文字を足さない**（必須見出しを満たすのは管理用側）（正本: `references/output-formats.md`「月報は1ファイルの中で提出用セクションと管理用セクションに分ける」）

### 取得方法

- コマンド引数で指定されている場合: そのまま使用
- 未指定の場合: AskUserQuestion で1ターンで取得

### 2.8 inherited_context（継承文脈10種）

info-collector が「現在の月報/期報」から抽出し、週報の自動継承元となる今期文脈。週報は新規ヒアリングを行わず、この値を表示・確認して必要時のみ上書きする（所要時間5-8分維持）。月報・期報はフル elicitation で確定する。全項目に `[自動取得]` / `[要ヒアリング]` マークを付与する。

各フィールドの型は InterviewData の文脈フィールド（#22-31）と一致させる。

| フィールド | 型 | マーク | 説明 | InterviewData対応 |
|-----------|-----|--------|------|------------------|
| period_sales_target | number | [自動取得] / [要ヒアリング] | 今期の売上目標（期アンカー・全レベル同値） | #22 |
| period_sales_cumulative | number | [自動取得] / [要ヒアリング] | 今期の累計売上実績（期アンカー・週次更新） | #23 |
| business_partner_count | number | [自動取得] / [要ヒアリング] | 現在事業パートナー数（スナップショット） | #24 |
| grid_partner_count | number | [自動取得] / [要ヒアリング] | 現在のグリッドパートナー数（スナップショット） | #25 |
| grid_partner_goal | number / null | [自動取得] / [要ヒアリング] | グリッドパートナー目標数（スナップショット）。未設定時は null | #26 |
| last_academy_date | date / null | [自動取得] / [要ヒアリング] | 前回のアカデミーへの参加日（スナップショット） | #27 |
| next_academy_date | date / null | [自動取得] / [要ヒアリング] | 次回のアカデミーへの参加日（スナップショット） | #28 |
| next_sparring_date | date / null | [自動取得] / [要ヒアリング] | 次回の壁打ち予定日（スナップショット） | #29 |
| sparring_target_state | string | [自動取得] / [要ヒアリング] | 次回の壁打ち予定月までに目指している状態（スナップショット） | #30 |
| sparring_deliverables | string | [自動取得] / [要ヒアリング] | 次回の壁打ち予定日までに達成させること（スナップショット） | #31 |

- 継承供給源: weekly は『現在の月報』、monthly/quarterly は『現在の期報』から抽出する。取得不可は `[要ヒアリング]` を付与する。
- `grid_partner_goal` は number / null（#26 と一致）。専用出力セクションは持たず、文脈・行動目標へ反映する。
- `period_sales_cumulative` のみ週報でも必須で、当該週時点の累計実績に週次更新する（継承値の更新が前提）。
- 種別別の必須/任意/継承度は §3.1.3 マトリクスに従う。

### バリデーション（Phase 1-2 完了時）

- 全セクションに `[自動取得]` または `[要ヒアリング]` マークが付いていること
- `[自動取得]` の数値データが半角数字であること
- prev_goals が goal_type の取得スコープに合致する件数であること
- camp_data の freshness_mark が3つの列挙値のいずれかであること

### 3.1.3 文脈フィールドの種別別 必須/任意/継承マトリクス

統一ハイブリッド化（canonical-spec §10）で追加した文脈フィールド（#22-31）と habit_check（#19）の種別別必須度。週報は「現在の月報/期報」からの継承値を既定とし、info-collector が自動継承する（週報の所要時間5-8分を維持）。ターンでは一括確認のみ行い、変更があれば上書きする。月報・期報はフル elicitation で必須。

#### 層間一致検査（validate-goal-output.py `--peer`）の対象一覧

「層間一致検査」列が **対象** の値だけが、週報・月報・期報の間で同じ値でなければならない。
`validate-goal-output.py --file <対象> --peer <他層>` がこの列に従って突き合わせ、
不一致を WARN で報告する（FAIL にはしない。継承は作成時 pull の一方向しかなく、
下位が先に作られる運用があるので、正しく運用しても最低1回はズレるため）。

- **対象**: `period_sales_target`（今期の売上目標）／`period_sales_cumulative`（今期の累計売上実績）
  — 週報でもこの2値は全レベル同値が正しい。
- **対象（月報・期報間のみ）**: 最重要数字。**週報の【今週の最重要数字】は、期・月の最重要数字を
  今週分へ割った内訳**であって同値になる値ではない（例: 期「困りごとを解決した件数：6件」に対し
  週「サンプル運送さんの困りごとを書き出した件数：3件」）。したがって、どちらか一方でも週報の場合は
  比較せず、分母からも落とす（検査器は SKIP 行で理由を印字する）。
- **対象外**: スナップショット8種（`business_partner_count` / `grid_partner_count` /
  `grid_partner_goal` / `last_academy_date` / `next_academy_date` / `next_sparring_date` /
  `sparring_target_state` / `sparring_deliverables`）。これらは各文書の作成時点の状態を写した値で、
  時点が違えば値が違うのが正常。**特に `last_academy_date` / `next_academy_date` /
  `next_sparring_date` は日付のスナップショットなので、層をまたいで一致させない。**
- **対象外**: `habit_check`（週報固有）、および前期間行動レビュー4種（#32-35。前期間の実績なので層ごとに範囲が違う）。

新しい項目を層間一致の対象にする／外すときは、この表の「層間一致検査」列と
`validate-goal-output.py` の `PEER_ANCHORS` / `WEEKLY_EXEMPT_ANCHORS` を同時に更新する。

#### 三層横断照合（validate-cross-level.py）の対象一覧

`validate-goal-output.py --peer` は**2ファイルの総当たり・WARN のみ・3アンカー**で、
不一致でも rc は上がらない。これとは別に、**期報を正本とした継承が崩れていないか**を
rc を持って判定する検査器が `scripts/validate-cross-level.py`。

```
validate-cross-level.py --quarterly <期報> --monthly <月報> [--weekly <週報>] [--month N]
```

rc=0 全一致 / rc=1 不一致または抽出不可あり / rc=2 引数・入力不正 / rc=3 抽出0件。
**rc=1 と rc=3 を混ぜない。** rc=3 は「一致していた」ではなく「1件も抽出できず何も
判定していない」。出力は常に `照合対象 N 件中 不一致 M 件（抽出不可 K 件）` の形で分母を出し、
末尾に `MEASURED_AT` / `ARGS` を付ける。

継承の形は2種類あり、照合の当て方が違う。

- **同値継承**: 期全体の値を下位層がそのまま書き写す。三層で同じ数字。
- **内訳継承**: 期報が月別内訳として書いた値を、月報が自分の層の値として書く。
  期合計（例: 延べ回数120回）と月の値（56回）を直接比べると必ず不一致になるので、
  **期報が当月について書いた数**と**月報が自分の数として書いた数**を比べる。
  対象月は月報の期間終了日の月（最終月曜起点のため 2026-09-28〜2026-10-25 の当月は10月）。

| # | アンカー | 継承の形 | 期報の抽出元 | 月報の抽出元 | 週報の抽出元 |
|---|---------|---------|------------|------------|------------|
| 1 | 今期の売上目標 | 同値 | 【今期の売上目標】 | 【今期の売上目標】 | 【今期の売上目標】 |
| 2 | 当月の売上目標 | 内訳 | 【事業計画書数値】の「月別の売上目標」行 | 【今月の売上目標】 | 【今週の売上目標】の日割り根拠行 |
| 3 | 無料相談の延べ回数 | 内訳 | 【今期の売上以外の成果目標】の当月分 | 【今月の最重要数字】 | 対象外（週の内訳） |
| 4 | 1回目の実人数 | 内訳 | 同上 | 【今月の最重要数字】 | 対象外（週の内訳） |
| 5 | 月額継続コンサルの累積件数 | 内訳 | 同上（累積の行） | 【今月の最重要数字】 | 対象外（週の内訳） |
| 6 | 現在事業パートナー数 | 同値 | 【現在事業パートナー数】 | 同左 | 同左 |
| 7 | 現在のグリッドパートナー数 | 同値 | 【現在のグリッドパートナー数】 | 同左 | 同左 |
| 8 | 次回の壁打ち予定日 | 同値 | 【次回の壁打ち予定日】 | 同左 | 同左 |

抽出範囲から外す節（経緯の記述を現在値として拾わないため）:
【仮置き事項】【衝突】【来(週|月|期)以降に対応すること】【確定済み・解消済みの記録】
【追随させる箇所】【前(週|月|期)の…】。`##` 見出しに当たればその節全体、`###` 小見出しに
当たればその小見出しから次の小見出しまでを本文に入れない。アンカーの節の中に
「確定済み・解消済みの記録」が入っている形（記録の側の古い値が先に出てくる）を落とすのが目的。

数値はカンマ区切り（600,000）と素の数字（600000）を同値として扱う。全角数字で書かれていると
**抽出不可**（不一致ではない）として個別に列挙し rc=1 にする。抽出不可を「不一致0件」に
吸収しない（検査できていない状態を PASS にしない）。

**未決（ユーザー判断待ち）**: #6 `business_partner_count` / #7 `grid_partner_count` /
#8 `next_sparring_date` は、上の `--peer` の一覧では **対象外（スナップショット）** と
規定している（時点が違えば値が違うのが正常、という理由）。一方 `validate-cross-level.py` は
この3つを **同値継承の対象**として照合する（三層で同じ時点を書く運用を前提にした指定）。
**2つの検査器で扱いが逆になっている。** どちらに寄せるかはまだ決めていない。
片方へ寄せるときは、この節・`--peer` の一覧・`validate-cross-level.py` の `ANCHORS`・
plugin 直下の `../../tests/test_validate_cross_level.py` を同時に直す。寄せるまでの間、`--peer` は WARN のみ、
`validate-cross-level.py` は rc=1 を返すという非対称が残る。

受け入れテストは plugin 直下の `../../tests/test_validate_cross_level.py`。

- 「任意（継承）」: 週報では値を新規ヒアリングせず、現在の月報/期報から継承した値を表示・確認する。継承値が取得できない場合のみヒアリングする。
- period_sales_cumulative のみ週報でも必須。週次で当該週時点の累計実績に更新する（継承値の更新が前提）。
- 前期間行動レビュー4種（prev_action_target/actual/diff/change・#32-35）は §1: period語化対象。全種別で初回は null、2回目以降は前期間データがあれば反映する。取得Stepは target/actual（#32-33）を Step 1 で表示・収集、diff/change（#34-35）を Step 2 で算出する。

#### 逆算チェーン検査（売上→成果→行動。全種別共通・`check_goal_chain`）

| ID | チェック項目 | 判定 | 説明 |
|----|-------------|------|------|
| C1 | 貢献額の根拠の随伴 | FAIL | 成果目標の各項目の**2行目**に `  → 売上貢献：…` があり、**貢献額に「式（`<単価> × <件数> = <貢献額>`）」または「括弧の根拠（`<貢献額>（値引き後の一括見積）`）」のいずれかが随伴すること**（半角数字。裸の数字は FAIL）。要求しているのは式そのものではなく、貢献額が後から検算できる形になっていること。式は十分条件の一つであり、単価×件数に分解できない成果は括弧の根拠で満たす。貢献 0 もこの一般規則の適用で、`0（8月に 200000 の見込み）` のように「いつ・いくらになるか」を括弧で添える（理由なしの裸の `0` は FAIL） |
| C1c | 式の検算 | FAIL | 式で書いた場合、`<単価> × <件数>` の積が `<貢献額>` と一致すること。単価と件数を分けて書かせるのは、後から誰でも検算できる形にするため |
| C1d | 貢献 0 の偏り | WARN | 貢献額 0 の成果目標が全体の過半を占めないこと（今期間の売上にほとんど繋がらない目標設定になっている） |
| C1e | 計上期間の逸脱 | FAIL | 式の件数に期間単位（`ヶ月` / `ヵ月` / `か月` / `年`）が混入していないこと。貢献額はその期間に実際に売上として立つ分だけを計上する。月額5万の顧問を週報で成約するなら `50000 × 1 = 50000`（初月分）であり `50000 × 3ヶ月 = 150000` ではない。期間をまたぐ分は次の期間の成果目標として立て直すか `0（8月に 100000 の見込み）` の見通しとして書く。※検査が捕まえるのは単位語が書かれた形のみで、「件数が期間の長さになっていないか」の意味判断は人が行う |
| C2 | 実行完了型の排除 | FAIL | 成果目標に実行完了型NG動詞10語（正本: `references/output-formats.md`「成果目標と行動目標の区別」＝`Validator.OUTCOME_NG_VERBS`）で終わる項目が無いこと |
| C3 | 売上目標との突合 | FAIL / WARN / OK / INFO | 売上貢献の合計と売上目標を `judge_sales_coverage()` で突合。合計 ≥ 目標 → OK／不足が目標の **5% 以内** → WARN（端数ズレ）／5% 超の不足 → FAIL／売上目標が 0 以下 → INFO（判定しない）。**完全一致は求めない** |
| C4 | 行動→成果の紐づけ | FAIL | 行動目標が `### → <成果目標名>：<要約>（<金額>円）` のグループ見出しの配下に置かれていること（週報・月報・期報の全種別）。見出しが無い場合のみ、旧記法の行内注記 `  → 支える成果目標：XXX` へフォールバックする |
| C4b | グループ見出しの金額一致 | FAIL | C4 のグループ見出し末尾 `（<金額>円）` が、その成果目標の貢献額（C1 の貢献額）と一致すること。ズレると行動グループの重みが売上の実態と食い違い、優先順位の判断を誤らせる。`（土台）`／`（関係維持）` の例外見出しは金額を持たないため対象外 |
| C5 | 参照先の実在 | FAIL | C4 のグループ見出しが指す成果目標名が、成果目標セクションに実在すること（dangling 参照の禁止。習慣・土台のみ `（土台）`／`（関係維持）` を例外として許容） |
| C6 | 支えられない成果目標 | WARN | どの行動目標からも参照されていない成果目標（orphan）が無いこと |

**あえて検査しない規約（実装漏れではない）**: 成果目標・行動目標グループの**並び順（貢献額の降順）**は機械検査しない。同額のときに順序が決まらず判定が硬直するため、優先順位の表現は人間の判断に委ねる。「1項目=2行」の改行位置・項目間の空行も同様に非検査（貢献額の実在は C1 が押さえている）。文章側の正本は `references/output-formats.md`「読み手向けの推奨（機械検査しない）」。

#### シンプルさ検査（全種別共通・`check_goal_chain` 内）

| ID | チェック項目 | 判定 | 説明 |
|----|-------------|------|------|
| S1 | 成果目標の件数・長さ | FAIL | 成果目標は `MAX_OUTCOME_ITEMS=5` 件以内、1項目（`→ 売上貢献` の前まで）`MAX_OUTCOME_CHARS=50` 字以内 |
| S2 | 1項目1成果 | FAIL | 成果目標の1項目に `・` で複数の成果を詰め込まないこと。超えたら短縮せず2件に割る |
| S3 | 行動目標の件数・長さ | FAIL | 行動目標は `MAX_ACTION_ITEMS=8` 件以内、1項目（1行目・期日込み）`MAX_ACTION_CHARS=60` 字以内 |

上限値は逸脱の検出線であり、狙うべき長さではない（実運用の目安は成果 20〜30 字・行動 25〜30 字）。定数の正本は `scripts/validate-goal-output.py` の `Validator` クラス定数、文章側の正本は `references/output-formats.md`「シンプルさの上限（機械検査対象・厳守）」。

**判定ルール**: FAIL が1件以上 → STATUS: FAIL（修正して再バリデーション、最大3回）

月報は1ファイルなので `--type monthly` を1回だけ回す。**提出用セクションの見出しに「（提出）」を付けるのは、この validator の重複見出し検査（#5b）を通すための規約**。重複検査は `## 【…】` 行の完全一致で数えるため `## 【今月の売上目標（提出）】` は `## 【今月の売上目標】` と衝突しない。必須セクション検査（#5）も完全一致なので管理用セクション側で満たす。したがって**管理用セクションの見出しには文字を足さない**（素の見出しのまま。「（管理）」等を足すと必須見出しが1件も満たされず FAIL になる）。提出用の行動目標（`## 【今月の行動目標（提出）】`）はグループ見出しを置かない1行1行動の規定なので、validator は `（提出）` を含む行動目標見出しを C4/C5（所属）と S3（件数）の抽出から外す（成果・売上側の抽出が `】` 直前一致で `（提出）` を拾わないのと揃えている）。

提出用セクションの見出しが副作用的に当たる検査は次の2つで、いずれも両セクションを1つのプールとして扱う:

- #7〜#9・#11（行動目標の NG 表現・数値・期日・固有名詞）は見出しの部分一致（`行動目標` を含み `今(週|月|期)` を含む）で拾うため、提出用セクションの行も同じプールに入る。#7 は FAIL なので提出用セクションにも精神論を書かない。#8・#9・#11 は WARN
- #11 の固有名詞（`さん|様`）はプール全体に1件あれば満たすため、提出用セクションで個人名を書かない方針と両立する（管理用セクション側で満たす）

#### 一本筋の両方向照合（validate-goal-linkage.py）

validator は所属（C4）と参照先の実在（C5）を FAIL で見るが、支える行動の無い成果目標（C6）は WARN で rc を上げない。C5 は括弧で始まる名前をすべて免除し、`・` で区切った複数参照もそれぞれが実在すれば通す。この穴を別スクリプトで埋める。照合規則（成果目標の項目の束ね方・参照キーの切り出し・空白を落とした完全一致・グループ見出しの解釈）は validator から読み込んで共用し、二重に実装しない。

| # | チェック項目 | 判定 | 説明 |
|---|-------------|------|------|
| L1 | forward 参照解決 | FAIL | 各行動目標の所属（グループ見出し `### → XXX：…` の `：` より前）が成果目標セクションの項目名（`：` より前）と一致すること。見出しの無い旧ファイルは行内注記 `→ 支える成果目標：XXX` を WARN 付きで受理する。カギ括弧の行内注記 `→ 支える成果目標「XXX」` は受理しない |
| L2 | backward 参照解決 | FAIL | 各成果目標を支える行動目標が最低1件あること（validator の C6 は WARN だが、ここでは rc=1） |
| L3 | 所属の欠落・複数参照・許容外の括弧名 | FAIL | 行動目標の各項目に所属が1つだけあること（`・` で複数の成果目標を指さない）。免除する括弧名は `（土台）`／`（関係維持）` の2つだけで、ほかの括弧名（`（準備）` など）は FAIL |
| L4 | 分母0の検出 | 専用rc | 照合対象が0件のとき rc=3 を返し、rc=0（検査して0件）と区別すること |
| L5 | 照合範囲 | 対象外 | 提出用セクション（`# 北原さん提出用` グループ・`（提出）` 付き見出し）は L1-L3 の対象にしない。提出用の行動目標はグループ見出しを置かない1行1行動の規定。グループ見出しのラベルずれは FAIL |

`$CLAUDE_PLUGIN_ROOT/skills/run-ubm-goal-setting/scripts/validate-goal-linkage.py --file <絶対パス>` で実行。rc=0 PASS / rc=1 未解決あり / rc=2 引数・ファイルの誤り / rc=3 分母0。Phase5-validate では **validate-goal-output.py → validate-goal-linkage.py の順に両方を回し、両方の rc の値をそのまま記録する**。オプションは `--file` だけで、**明示指定で個別に免除する機構は持たない**（`--allow` のような免除オプションを渡すと未知のオプションとして rc=2 になる）。成果が測りにくい行動は、行動目標セクション末尾の `### → （土台）`／`### → （関係維持）` グループへ置く（この2つだけが分母から外れる）。月報は**管理用セクションだけ**を照合する（提出用セクションの行動目標はグループ見出しを持たないため、`# 北原さん提出用` グループは `SKIP` で対象外）。

#### 三層横断照合は単一ファイル検査の対象外

`validate-goal-output.py` も `validate-goal-linkage.py` も **1本のファイルしか見ない**。
期報の数字を直して月報・週報へ追随させ忘れても、どちらも rc=0 で通る（層をまたぐ値を
突き合わせる口が存在しない＝分母が0件）。期報と月報が揃っている場合は、Phase5-validate の最後に
`validate-cross-level.py` を当てて rc の値を記録する（週報があれば `--weekly` も渡して三層で照合する）。
期報か月報が無い場合は適用せず、rc ではなく `not_applicable` と記録する。

```bash
/usr/bin/python3 "$CLAUDE_PLUGIN_ROOT/skills/run-ubm-goal-setting/scripts/validate-cross-level.py" \
  --quarterly "<期報の絶対パス>" --monthly "<月報の絶対パス>" --weekly "<週報の絶対パス>" \
  > out.txt 2>&1; rc=$?; echo "rc=$rc" >> out.txt
```

週報が無い（期報と月報だけ作った）時点では `--weekly` を省略する。省略しても
照合対象の件数は変わらない（週報の抽出元を持つアンカーが週報分だけ減る）。
対象一覧とアンカーの定義は §3.1.3「三層横断照合（validate-cross-level.py）の対象一覧」。

### 4.5 goal_type 別の必須セクション

| goal_type | 必須セクション |
|-----------|---------------|
| weekly | 今週の最重要数字、今週の売上目標、今週の売上以外の成果目標、今週の行動目標（行動管理・優先順位付き）、習慣目標（仕組みで動く土台）、今週の判断基準、現在のグリッドパートナー数（**やらないことは週報では独立セクションを持たないため必須に含めない**） |

週報の任意セクション（欠落時 WARN・準静的/継承表示ゾーン。`check_section_optional`）: 到達ライン、今期の売上目標、前回のアカデミーへの参加日、次回のアカデミーへの参加日、次回の壁打ち予定日、現在事業パートナー数。「到達ライン」は二値性が行動目標のチェックボックスで担保されるため必須ではなく任意（WARN）。
