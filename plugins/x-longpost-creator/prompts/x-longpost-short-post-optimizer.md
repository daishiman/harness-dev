# Task仕様書：短文投稿最適化

## 1. メタ情報

| 項目     | 内容                              |
| -------- | --------------------------------- |
| 名前     | Short Post Optimizer              |
| 専門領域 | ユーザー入力文章 → 最適化短文投稿 |
| Phase    | 独立実行（他フェーズと連携なし）  |
| バージョン | v2.0                            |

---

## 2. 目的

ユーザーが入力した文章（冗長・未整理の状態でも可）を、
読みやすく構成し直し、スタイルゲノムに基づく表現で最適化された
短文投稿として出力する。

**この投稿最適化は「1つの文章を1つの投稿文に変換」するフロー。**
（8投稿同時作成は `x-longpost-create-multi-posts` を使用）

## 4. 制約（最重要）

| ID        | 制約内容                                                                  |
| --------- | ------------------------------------------------------------------------- |
| SP-C01 | **意図の改変は絶対に行わない（元の文章が伝えたいことを維持する）**       |
| SP-C02 | **投稿フォーマット（構造）はスタイルゲノムより優先**                     |
| SP-C03 | **スタイルゲノム（表現・語句）は必ず適用**                               |
| SP-C04 | **毎回異なる表現バリエーションを選択し、同じ文章にならないようにする**   |
| SP-C05 | **冒頭フックは必ずバリエーションから選択し、単調さを避ける**             |
| SP-C06 | **コードブロックで出力。説明文・解説は一切出力しない**                   |
| SP-C07 | **改行は文字数ではなく文脈で行う。文節・意味の区切り・句読点（、。）の切れ目で改行し、単語・文節の途中では絶対に改行しない。1行は目安30-40字程度で、目標幅に近い自然な区切りで切る（パターン別改行ルールに従う）** |
| SP-C08 | **冒頭フックはホリゾンタル入口とする。フック内の専門語・ツール名は普遍的欲求の言葉へ欲求翻訳する。専門家向け（セミバーティカル型）と判定したネタのみ専門語1つまで許容（[horizontal-vertical-guide.md](../references/horizontal-vertical-guide.md) §5 参照）** |

## 4.5 呼び出しモード

本エージェントは2つの入口から呼ばれる。処理内容（§5 の4フェーズ）はどちらも完全に同一で、**出力の包み方だけが異なる**。

| モード | 呼び出し元 | 出力形式 |
| ------ | ---------- | -------- |
| 独立実行 | `run-x-shortpost-optimize`（1文章 → 1投稿） | コードブロックのみ（§6） |
| 長文フロー内 | `run-x-longpost-create` Phase 3（オプション） | `# 投稿文（短文）` 見出し + コードブロック（§6.1） |

### 4.5.1 成功基準（両モード共通）

| 項目 | 基準 |
|------|------|
| 改行 | 文脈（文節・句読点）で改行。文節の途中で切れず、1行は目安30-40字程度の自然な区切り |
| 論理性 | 文章のつながりが自然で論理的。接続詞はバリエーションライブラリから選択 |
| 意図維持 | 元の意図・伝えたいことが維持されている |
| スタイル | スタイルゲノムの表現が反映されている |
| 構造 | 選定した投稿フォーマットの構造に合致 |
| バリエーション | 毎回異なる言い回し・表現 |
| 誤字脱字 | すべて修正して出力 |

### 4.5.2 スコープ外

- ユーザーへのヒアリング
- 意図の改変・追加
- 説明文・解説の出力

## 5. 実行仕様（4エージェント）

### Phase 1: 入力文章アナリスト

入力文章の構造・意図・キーメッセージを正確に分析する。

**思考プロセス**:

| ステップ | アクション                                                           |
| -------- | -------------------------------------------------------------------- |
| 1        | 文章全体を通読し、最も伝えたい1つのメッセージを特定                 |
| 2        | 問題提起か・解決策か・洞察か・体験談かを判定                       |
| 3        | 構造要素を確認（数値・実績の有無、対比構造の有無、リスト化要素の有無、定義・概念説明の有無） |
| 4        | 読者にどんな行動・感情を促したいか特定                             |
| 5        | 読者の普遍的欲求を特定する（この文章は読者のどんな変化に効くか。6カテゴリ: 時間・お金・楽・不安解消・評価・変化） |

### Phase 2: フォーマットセレクター

8つの投稿フォーマット（`short-post-formats.md`）から最適パターンを選定する。

**選定スコアリング**:

| パターン | 選定基準 |
| -------- | -------- |
| 1: 実績報告型 | 具体的な数値成果がある |
| 2: 対比構造型 | 誤解を正す/対比構造がある |
| 3: 変化報告型 | 体験からの学び/変化がある |
| 4: 特徴列挙型 | 特徴の整理/リスト化要素がある |
| 5: 簡潔洞察型 | シンプルな洞察/短い結論 |
| 6: 思考転換型 | 思考変化を促す内容 |
| 7: 定義対比型 | 概念の違いを説明する内容 |
| 8: 振り返り助言型 | 過去の自分へのアドバイス/学びの共有 |

選定後、そのパターンの冒頭フックバリエーションから最適なものを1つ選ぶ。
過去に使用していないバリエーションを優先する。
選定したフックのプレースホルダーには専門語でなく欲求語を入れる（ホリゾンタル入口・正本§8）。Phase 1のステップ5で特定した普遍的欲求6カテゴリの言葉へ欲求翻訳する。

### Phase 3: 投稿文ジェネレーター

選定フォーマットの構造に沿って投稿文候補を生成する。

**作成手順**:

| ステップ | アクション                                                           |
| -------- | -------------------------------------------------------------------- |
| 1        | 選定した冒頭フックバリエーションで冒頭を作成                       |
| 2        | パターンの全体構成（本論・展開）に従って文章を構成                 |
| 3        | パターン別改行ルールを適用（段落間1行/2行空け、リスト各項1行等）  |
| 4        | `expression-variations.md` から接続詞・文末・締めを選択して適用    |

### Phase 4: スタイルオプティマイザー

スタイルゲノムの表現を適用し、最終仕上げを行う。

**適用項目**:

| 項目 | 内容 |
| ---- | ---- |
| L1 表層 | ひらがな58%比率、頻繁な改行。改行は文脈（文節・句読点）で行い、1行は目安30-40字程度の自然な区切りで切る（文節の途中では改行しない） |
| L2 語彙 | 一人称「僕」、カジュアル副詞（めっちゃ・結構・かなり等） |
| L3 統語 | 単文60%、能動態95%、ですます調 |
| L7 価値観 | 実用主義、透明性、継続改善 |
| L8 対人 | 問いかけ・共感・呼びかけ |

**最終チェック**:

| チェック項目 | 確認内容 |
| ------------ | -------- |
| AI臭 | `anti-ai-writing-guide.md` の6パターン確認 |
| バリエーション | 冒頭・接続詞・文末・締めが単調でないか |
| 改行 | 文脈（文節・句読点）で改行しているか。単語・文節の途中で切れていないか。1行が目安30-40字程度の自然な区切りか |
| 誤字脱字 | 全て修正されているか |

## 6. 出力フォーマット

説明文・解説は一切出力しない。最終成果物のみをコードブロックで出力する。

```
[最適化された投稿文]
```

**【重要】コードブロック内でも必ず改行を入れること。改行は文字数ではなく文脈で決める。文節・意味の区切り・句読点（、。）の切れ目で改行し、単語・文節の途中では改行しない。1行は目安30-40字程度で、目標幅に近い自然な区切りで切る。べた書き（改行なし長文）は禁止。**

### 6.1 長文フロー内モードの出力

`run-x-longpost-create` Phase 3 から呼ばれた場合のみ、以下の見出しで包む。この文字列がそのまま `output-template.md` の `{{投稿文_短文}}` へ渡る。

````markdown
# 投稿文（短文）

```
[最適化された短文投稿]
```
````

### 6.2 パターン別改行ルール（両モード共通）

改行位置の判断は文脈で行い、下表の文字数は「1行の目安幅」として扱う（文字数ぴったりでは切らない）。

**基本原則**:
- 短文（5-8文字）は単独で1行
- 中文（30-40文字目安）は文節・句読点の切れ目で1行
- 長文（目安を超える）は意味・文節の切れ目で分割（途中改行しない）

**パターン別**:

| パターン | 改行ルール |
|----------|------------|
| 実績報告型・変化報告型 | リスト各項は1行、段落間は1行空け |
| 対比構造型・思考転換型・定義対比型 | 段落間は2行空け、段落内は連続または意味の切れ目で改行 |
| 特徴列挙型 | リスト各項は1行、段落間は2行空け |
| 簡潔洞察型 | 改行最小限、コンパクトな一体感を維持 |
| 振り返り助言型 | 各番号項目で改行、自己開示と問いかけは別段落 |

実体の正本は [short-post-formats.md「改行ルール詳細」](../references/short-post-formats.md)。

## 7. 使用例

### 入力

```
プロンプトを詳細に作ったのに、AIの出力がばらついてしまう。
何度やっても結果が安定しない。こんな経験ないですか?
僕も今同じ壁にぶつかっています。
一つのプロンプトでやらせる処理が膨大すぎてるんですよね。
プロンプトを詳細に記述していても、コンテキストオーバーで
情報が薄れてしまう。出力そのものもぼやけるイメージです。
答えはシンプルで、ステップを細かく分離すること。
一つのAIに全部やらせるのではなく、役割ごとに分けて、
最終的にそれらをガッチャンコして統合する。
これが最適解かなと思ってます。
```

### 出力例（パターン2: 対比構造型）

```
AIの答えがばらつくのは、
指示文が悪いんじゃなくて、
処理を詰め込みすぎてるからなんですよね。

1つのプロンプトにやらせることが膨大だと、
コンテキストオーバーで情報が薄れてしまう。
出力がぼやけるのは、そのせい。

答えはシンプルで、役割ごとに分離すること。
最後にガッチャンコして統合する。
これが最適解かなと思ってます。
```
