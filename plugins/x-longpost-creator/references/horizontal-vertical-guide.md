# ホリゾンタル入口×バーティカル中身 設計原則

出典: 三連休（@san_renkyu）「あなたのnoteは、バーティカルすぎる」

このファイルはタイトル・冒頭・本文構成における「入口の広さ」設計の正本である。
他のagents・referencesはこのファイルを参照し、詳細ルールを重複記載しない。

最重要原則: タイトル・入口はホリゾンタル（広く）、中身はバーティカル（深く）。
入口は広く、解決策は深く。まずホリゾンタルに取り、そこからバーティカルに刺す。

---

## 1. 用語定義（全ファイル共通の統一用語）

| 用語 | 定義 |
|------|------|
| ホリゾンタル入口 | 誰でも自分事化できる普遍的欲求ベースのタイトル・冒頭・フック。専門語や属性限定で母集団を狭めない |
| バーティカル中身 | 他の人が書けない深さまで掘った本文。具体的な数字・失敗・手順を全部出す。薄めてはいけない |
| 欲求翻訳 | 専門語・手段の言葉を、読者の普遍的欲求（得たい変化）の言葉へ言い換えること |
| TAMチェック | タイトル・入口を自分事化できる読者母集団の広さの確認。属性の重ね掛けを検出する |
| ネタ性質判定 | ネタが一般向けか専門家向けかを判定し、入口のホリゾンタル度を自動調整する工程 |

---

## 2. 大原則: ターゲットを絞ることと入口を狭くすることは違う

ターゲットを絞るのは正しい。しかし入口（タイトル・冒頭）まで狭くすると、
読者が入ってこられない。

```
【NG - 入口までバーティカル】
40代の地方在住会社員が、生成AIを活用してバックオフィス業務を効率化する方法

→ 40代 AND 地方在住 AND 会社員 AND バックオフィス AND 生成AIに興味。
  条件のANDで母集団が潰れる。マーケットではなく、ほぼ親戚。

【OK - 入口はホリゾンタル、中身はバーティカル】
毎月10時間かかっていた仕事を、ほぼゼロにした方法

→ 仕事を早く終わらせたい人は多い（ホリゾンタルに取る）。
  その中から、生成AIが使えそうな人を本文でバーティカルに落としていく。
```

読者が知りたいのは「書き手が何を知っているか」ではなく「自分がどう変わるか」。
専門性を捨てるのではない。中身はむしろ今より深く掘る。入口だけを地上に置く。

---

## 3. 欲求翻訳（専門語 → 普遍的欲求）

### 3.1 翻訳の基本

読者は専門知識が欲しいのではない。自分の変化が欲しい。

| 読者が言いそうなこと（表面） | 読者が本当に欲しいもの（普遍的欲求） |
|------------------------------|--------------------------------------|
| AIを学びたい | 仕事を早く終わらせたい |
| コピーライティングを学びたい | noteを売りたい |
| 自己分析をしたい | 自分が何をすればいいのか決めたい |
| プロンプトがうまくなりたい | 思い通りの結果をすぐ手に入れたい |
| ツールの使い方を知りたい | 面倒な作業から解放されたい |

### 3.2 普遍的欲求6カテゴリ

入口はこのいずれかに接続する言葉で書く。

| カテゴリ | 入口に使う言葉の例 |
|----------|--------------------|
| 時間 | 早く終わる、時間が浮く、残業が消える、待たされない |
| お金 | 稼げる、売れる、損をしない、費用が消える |
| 楽 | 面倒がなくなる、悩まなくていい、手が止まらない |
| 不安解消 | 失敗しない、怒られない、置いていかれない |
| 評価 | 読まれる、伝わる、任される、選ばれる |
| 変化 | できるようになる、決められる、抜け出せる |

### 3.3 翻訳手順

1. ネタの中心にある専門語・手段（ツール名・技法名・分野名）を特定する
2. 「それによって読者はどう変わるのか」を1文で書く
3. その変化を6カテゴリのいずれかの言葉に落とす
4. 入口（タイトル前半・冒頭1-2文・短文フック行）にはその言葉を使う
5. 専門語・手段は中身（本文・タイトル後半）で出す

翻訳は誇張ではない。中身が実際に提供する変化だけを入口に書く。
中身にない変化を入口に置くのは翻訳ではなく釣りである（§7参照）。

## 4. TAMチェック（属性の重ね掛け検出）

### 4.1 判定手順

タイトル・冒頭に含まれる「限定属性」を数える。

| 限定属性の種類 | 例 |
|----------------|-----|
| 年代・世代 | 40代の、20代向け |
| 地域 | 地方在住の、都内の |
| 職業・役職 | 会社員が、フリーランスの、経営者向け |
| 業務・状況 | バックオフィス業務の、子育て中の |
| ツール・分野名 | 生成AIで、プロンプトの、note運用の |

| 限定属性の数 | 判定 |
|--------------|------|
| 0-1個 | 合格 |
| 2個以上 | 重ね掛け。削るか欲求翻訳する |

### 4.2 母集団の感覚チェック

「このタイトルを見て自分事だと思える人」を思い浮かべ、
条件のANDで母集団が潰れていないかを確認する。
迷ったら「この入口に入れる人は、その辺を歩いている人の何人に1人か」で判断する。

## 5. ネタ性質判定（自動判定）

すべてのネタを一律に最大ホリゾンタル化するのではなく、ネタの性質で入口の広さを調整する。

### 5.1 判定手順

1. このネタが読者に与える変化を1文で書く
2. その変化を求める人の範囲で分類する

| 判定 | 条件 | 入口ルール |
|------|------|-----------|
| 一般向け（ホリゾンタル型） | 変化が6欲求カテゴリに直結し、職種・ツールを問わず求められる | タイトル前半・冒頭に専門語を置かない。完全に欲求ベースで入る |
| 専門家向け（セミバーティカル型） | 変化がその専門語を知る層でしか意味を持たず、読者がその専門語で自分事化する | 専門語を入口に1つまで許容。ただし属性の重ね掛け（§4）は禁止 |

迷ったら一般向け（ホリゾンタル型）に倒す。

### 5.2 判定結果の明示（必須）

タイトル生成の出力には判定結果と根拠を必ず含める。

```markdown
## ネタ性質判定
- 判定: 一般向け（ホリゾンタル型） / 専門家向け（セミバーティカル型）
- 根拠: [読者が得る変化と、その変化を求める層の広さ]
- 入口に使う欲求: [6カテゴリのどれか + 具体的な言葉]
```

判定根拠が明示されていれば、ユーザーは判定を上書きできる。

## 6. タイトルの2層設計

既存の2文構成テクニック（title-guidelines.md §2）とそのまま接続する。

| 層 | 位置 | 役割 | 書き方 |
|----|------|------|--------|
| 第1層: ホリゾンタル入口 | 前半（最初の30文字以内） | 広く取る | 普遍的欲求・変化・悩みの言葉。専門語なし（セミバーティカル型は1つまで） |
| 第2層: バーティカル予告 | 後半 | 深さを予告し期待値を設定 | 数字・手順・失敗・具体性の示唆 |

```
例:
毎月10時間かかっていた仕事を、ほぼゼロにした方法
↑第1層: 時間の欲求で広く入る      ↑第2層: 具体的な変化の深さを予告

読まれない文章の原因は専門性不足じゃない。入口を1行変えた結果
↑第1層: 評価の欲求（読まれたい）  ↑第2層: 具体的な打ち手の予告
```

既存のキーワード30文字以内ルールとの整合: 最初の30文字に置く「重要キーワード」は
欲求翻訳後の言葉とする（専門語ではなく）。

---

## 7. 釣りタイトル化の防止

ホリゾンタル化は「翻訳」であって「誇張」ではない。

| ガード | 内容 |
|--------|------|
| 中身との一致 | 入口に書く変化は、中身が実際に提供する変化に限る |
| バーティカル予告 | 第2層で深さ・具体性を予告し、期待値を正しく設定する |
| 既存チェック維持 | 期待値一致チェック（title-guidelines.md）はホリゾンタル化より優先する |
| 中身を薄めない | ホリゾンタルは入口だけ。本文は数字・失敗・手順を出し切る |

## 8. 適用マップ（どの工程で何をするか）

本表のファイル列は plugin ルート `${CLAUDE_PLUGIN_ROOT}` からの相対パスである。

| 工程 | ファイル | 適用内容 |
|------|----------|----------|
| 入力解析 | prompts/x-longpost-parse-input.md | 構成要素として「読者の普遍的欲求」を抽出する |
| タイトル作成 | prompts/x-longpost-create-title.md | ネタ性質判定 → 欲求翻訳 → 2層設計 → TAMチェック → 判定明示 |
| スタイル適用 | prompts/x-longpost-apply-style-genome.md | 冒頭フック（最初の1-2文）をホリゾンタルに書く。専門語は共感形成後に出す |
| 文章最適化 | prompts/x-longpost-optimize-length.md | 最初の見出しは広く（悩み・欲求）、中盤以降の見出しは深く（手順・数字）。入口の最終確認 |
| スレッド分割 | prompts/x-longpost-split-thread.md | 1投目はホリゾンタルフック。テーマ直提示をしない |
| 短文投稿 | references/short-post-formats.md ほか | フック行のプレースホルダーに専門語でなく欲求語を優先する |

### 本文構成への適用（入口は広く、解決策は深く）

| 位置 | 設計 |
|------|------|
| 冒頭（テーマ提示・問いかけ・共感） | ホリゾンタル。読者の日常の悩み・欲求の言葉で入る。専門語・ツール名は共感形成後に初出させる |
| 中盤以降（原因分析・解決策・実践例） | バーティカル。他の人が書けない深さまで掘る。数字・失敗・手順を全部出す |

### 既存原則との優先関係

中村4原則（[writing-guidelines.md](../skills/run-x-longpost-create/references/writing-guidelines.md) §8）との整合は「適用対象の分離」で取る。

| 対象 | 優先する原則 |
|------|--------------|
| 入口（タイトル・冒頭1-2文・見出し1つ目・短文フック行） | 原則②（冒頭に命をかける）+ 本ガイド（ホリゾンタル入口） |
| 中身（本文・中盤以降の見出し・解決策） | 原則③（とにかく具体的に書く）+ 本ガイド（バーティカル中身） |

ユーザーの意図保持が最上位である点は従来どおり変わらない。

## 9. チェックリスト（正本）

| 項目 | 基準 |
|------|------|
| 入口の専門語 | タイトル前半30文字・冒頭1-2文・短文フック行に専門語・ツール名がない（セミバーティカル型のみ1つまで） |
| 属性の重ね掛け | 限定属性（年代・地域・職業・業務・ツール名）が2つ以上重なっていない |
| 欲求翻訳 | 入口が普遍的欲求6カテゴリのいずれかに接続している |
| ネタ性質判定の明示 | 判定結果・根拠・入口に使う欲求が出力に含まれている |
| 2層設計 | タイトルが前半ホリゾンタル・後半バーティカル予告になっている |
| 中身の深さ | 本文が数字・失敗・手順を出し切っている（ホリゾンタル化で中身を薄めていない） |
| 期待値一致 | 入口の約束と中身の提供が一致している（釣りになっていない） |
