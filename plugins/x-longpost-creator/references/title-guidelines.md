# 読まれやすいタイトル作成ガイドライン

## 概要

SNSのタイムラインやWeb検索結果画面には、わずかな情報しか掲載されない。
記事を読んでほしい人に届けるには、タイトルと見出し画像だけで「読みたい」と思わせる必要がある。

**最重要原則**: 記事の内容が伝わるタイトルをつける

---

## 0. 最上位原則: 入口はホリゾンタル、中身はバーティカル

「内容が伝わる」ことと「入口を狭くする」ことは別物である。この2つは両立する。

- ターゲットを絞ることと入口を狭くすることは違う。入口（タイトル前半・冒頭）は広く取る
- 属性の重ね掛け（年代 AND 地域 AND 職業…）はTAMを潰す。母集団が親戚規模に縮む
- 専門語・手段の言葉は欲求翻訳して、読者の普遍的欲求の言葉で入口に置く
- 内容（中身）はむしろ深く掘る。ホリゾンタル化は入口だけで、本文は薄めない
- 詳細ルール（欲求翻訳表・TAMチェック・ネタ性質判定・2層設計）は horizontal-vertical-guide.md（正本）参照

## 1. 読まれやすいタイトルの条件

### 必須条件

| 条件 | 説明 | 例 |
|------|------|-----|
| 内容が伝わる | 読者がタイトルだけで「自分が読みたいコンテンツだ」と判断できる | ✗「効率化の話」→ ✓「作業時間が10分の1になった開発環境の整え方」 |
| 結論を含む | 記事を読んだ後に得られるものがイメージできる | ✗「AIを使ってみた」→ ✓「AIで開発環境を整えたら、作業時間が10分の1になった」 |
| 期待と満足度の一致 | タイトルの期待と読後の満足感が一致する | 過度な煽りを避け、内容に見合った表現にする |

### 推奨構文パターン（8パターン）

```
パターンA: 結論先出し型
[結論・結果]した[方法・対象]
例: 作業時間が10分の1になった開発環境の整え方

パターンB: 疑問→解答型
なぜ[現象]なのか。[解答のヒント]
例: なぜプロンプトが思い通りに動かないのか。たった1つの見落とし

パターンC: 対比型
[before]から[after]になった[方法]
例: 毎日3時間残業していた僕が、定時退社できるようになった仕組み

パターンD: 具体数値型
[数値]で[効果]を実現した[方法]
例: 1日10分で月収50万円を達成したプロンプト術

パターンE: 共感×成果型【推奨】
[共感ワード]で[困っていた状況]。[ツール/方法]で[成果]できた[結末ワード]
例: スライド作成が苦手で数十時間かかっていた。Claude Codeで2時間に短縮できた理由

パターンF: 告白型
[ネガティブな過去]だった僕が、[ポジティブな現在]になった[結末ワード]
例: プロンプトが全く書けなかった僕が、月100万円稼げるようになったきっかけ

パターンG: 発見型
[行動]したら、[意外な発見]だった
例: AIにプロンプトを任せたら、使い物にならなかった。その原因と解決策

パターンH: 逆説型
[常識]は間違っている。[真実]
例: 「とにかく行動」は間違っている。成果を出す人が先にやっていること
```

### 結末ワードバリエーション

**「〜した話」の代わりに使う表現**

| カテゴリ | 結末ワード | 効果 |
|----------|------------|------|
| 理由系 | 理由、原因、背景、きっかけ | なぜそうなったかへの好奇心 |
| 方法系 | 方法、やり方、仕組み、手順、ステップ | ノウハウへの期待 |
| 結果系 | 結果、効果、変化、成果 | 具体的なアウトカムへの興味 |
| 秘訣系 | 秘訣、コツ、ポイント、原則 | 本質的な学びへの期待 |
| 解決系 | 解決策、対処法、打開策 | 問題解決への期待 |
| 発見系 | 気づき、発見、真実、本質 | 新しい視点への好奇心 |

### 共感ワードライブラリ

**読者の「自分事化」を促す表現**

| カテゴリ | 共感ワード | 例文 |
|----------|------------|------|
| 苦手系 | 苦手、嫌い、避けていた | 「スライド作成が苦手で〜」 |
| 困難系 | 困っていた、悩んでいた、行き詰まっていた | 「プロンプトに悩んでいた僕が〜」 |
| 失敗系 | うまくいかなかった、失敗していた、挫折した | 「何度も失敗していた僕が〜」 |
| 時間系 | 時間がかかっていた、終わらなかった | 「数十時間かかっていた作業が〜」 |
| 能力系 | できなかった、わからなかった、センスがなかった | 「デザインセンスゼロだった僕が〜」 |

## 2. 読みたくなる心理トリガー

### 好奇心ギャップ

**「知りたい」を生み出す情報の出し方**

| テクニック | 説明 | 例 |
|------------|------|-----|
| 一部を隠す | 結論の一部だけ見せて続きを読ませる | 「プロンプトが動かない原因は『たった1つの見落とし』だった」 |
| 意外性を示唆 | 常識と違う結論を匂わせる | 「行動量を増やしても成果は出ない。本当に必要だったこと」 |
| 数字で具体化 | 抽象を具体に変える | 「3つの原則」「2時間に短縮」「10分の1」 |

### 自分事化トリガー

**「これは自分のことだ」と思わせる表現**

```
【効果的なパターン】
1. 苦手・困難の告白 → 共感を引く
   「〜が苦手だった」「〜に悩んでいた」「〜ができなかった」

2. Before→After → 変化への期待
   「数十時間→2時間」「ゼロから月100万」

3. 一人称の使用 → 親近感
   「僕が」「私が」→ 読者も自分に置き換えやすい

4. 具体的な状況描写 → リアリティ
   「1時間の登壇に数十時間かかっていた」
```

### 2文構成の威力

**前半で引きつけ、後半で読ませる**

| 前半（フック） | 後半（ベネフィット/理由） |
|----------------|--------------------------|
| 問題・共感 | 解決策・結果 |
| ネガティブな過去 | ポジティブな現在 |
| 疑問・常識 | 答え・逆説 |

```
例:
「スライド作成が苦手で数十時間かかっていた。Claude Codeで2時間に短縮できた理由」
 ↑前半: 共感（苦手・時間かかる）    ↑後半: 解決（2時間・理由への好奇心）
```

この2文構成は2層設計と対応する。前半（フック）はホリゾンタル入口＝普遍的欲求の言葉で広く取り、後半（ベネフィット/理由）はバーティカル予告＝数字・手順・具体性で深さを示す（正本§6）。

## 3. タイトル作成テクニック

### 3.1 固有名詞・具体情報を入れる

| 要素 | 効果 | 例 |
|------|------|-----|
| 固有名詞 | 信頼性・具体性UP | Claude Code, ChatGPT, Notion |
| 人名 | 親近感・権威性 | 「僕が」「50名のクライアントが」 |
| 数字 | 具体性・インパクト | 10分の1、50名、3つの方法 |
| 疑問文 | 読者の関心を引く | なぜ〜なのか？、どうすれば〜できる？ |

### 3.2 キーワード配置

```
【重要】大事なキーワードは文頭に配置する

理由:
- SNSや検索結果には文字数制限がある
- タイムラインでは最初の30文字程度しか表示されない
- 伝えたいキーワードを制限内に収める

悪い例: 開発環境を整えることで作業時間が10分の1になった話
良い例: 作業時間が10分の1になった。開発環境を整えたらこうなった
```

最初の30文字に置く重要キーワードは欲求翻訳後の言葉とする（専門語・ツール名をそのまま置かない。正本§6）。この「最初の30文字」を字数配分として確定したものが §3.4 の前半26〜32字である。

### 3.3 避けるべき表現パターン【重要】

> **正本宣言**: 本節は禁止表現リストの唯一の正本である。タイトル用（§3.3.1）と本文用（§3.3.2）の両方をここに置く。`prompts/x-longpost-create-title.md`・`prompts/x-longpost-apply-style-genome.md`・`prompts/x-longpost-optimize-length.md`・各 SKILL.md（いずれも plugin ルート `${CLAUDE_PLUGIN_ROOT}` からの相対パス）は実体を持たず、本節への参照のみを持つ。リストを追加・変更する場合はここだけを編集する。

#### 3.3.1 タイトルの禁止表現

```
【禁止】「〜した話」「〜を作った話」型のタイトルは使わない

避けるべき表現:
- 「〜した話」
- 「〜を作った話」
- 「〜してみた話」
- 「〜になった話」
- 「〜だった話」

理由:
- 内容が曖昧で読者の興味を引きにくい
- 結論やベネフィットが伝わらない
- ブログ記事・日記的な印象を与える
- 過去の投稿に多いパターンだが、エンゲージメントが低い傾向

悪い例:
✗ 「AIにプロンプトを作らせても使い物にならないと感じた僕が自分専用のメタプロンプトを作った話」
✗ 「Claudeを使ってコードを書いてみた話」
✗ 「プロンプトエンジニアリングを学んだ話」

良い例:
✓ 「AIにプロンプトを作らせても使い物にならない。その原因と解決策」
✓ 「Claudeで開発速度が3倍に。実際に使っている設定を公開」
✓ 「プロンプト精度を高める3つの原則」
✓ 「なぜプロンプトが思い通りに動かないのか。たった1つの見落とし」

代替パターン:
1. 結論先出し型: [結果・成果]になった。[方法・理由]
2. 疑問提起型: なぜ[現象]なのか。[解答のヒント]
3. 具体数値型: [数値]で[効果]を実現した[方法]
4. 対比型: [before]から[after]へ。[きっかけ・方法]
```

#### 3.3.2 本文の禁止表現

本文（長文投稿パターンA/B・短文投稿）で使用禁止の表現。直接的すぎて飽きる、わざとらしさがあるものを排除する。

| 禁止表現 | 理由 | 代替案 |
|----------|------|--------|
| 「理想はこんな状態です」 | わざとらしい | 理想の状態を直接描写する |
| 「現実は〜」「でも現実は」 | 直接的すぎる | 具体的な課題を描写する |
| 「このまま放置するとどうなるか」 | 直接的すぎる | 具体的な結果を描写する |
| 「最悪のパターンは」「さらに最悪な未来は」 | 直接的すぎる | 具体的な悪い状態を描写する |
| 「こんな人が増えると世界はどうなる」 | 直接的すぎる | 具体的な変化を描写する |
| 「〜と感じたことはありませんか？」 | 毎回同じ | 具体的な状況や引用を使う |
| 「理想的な状態って、どんな感じでしょうか」 | 冗長 | 省略して本題へ |

適用工程: `x-longpost-apply-style-genome`（本文生成時に主担当）→ `x-longpost-optimize-length`（最適化後の再発チェック）。

### 3.4 タイトルの長さと字数配分

**50文字ルールの実体（絶対ルール R1・4箇所一致・違反時のリライト6手順・check ID・終了コード）は [heading-structure-rules.md](../skills/run-x-longpost-create/references/heading-structure-rules.md) が正本。** 本節は文言設計側の推奨レンジと字数配分のみを扱う。

#### 上限と推奨レンジ

| 項目 | 値 |
|------|-----|
| 上限 | **50字（絶対・FAIL・空白含む・コードポイント数）** |
| 推奨 | 35〜48字（50字ちょうどを狙わず余白を残す） |
| 2文構成 | 可（読点やピリオドで区切る）。ただし合計50字以内 |

50文字はファイルシステムの制約ではなく編集規範である。タイムラインで最初に読まれるのは先頭30文字程度であり、そこに核を置いたうえで予告を足すと50文字に収まる。加えて、この文字列は長文Bの先頭行・`# タイトル`・ファイル名のタイトル部にも同一で使われるため、短く保つことが一覧性と命名の一貫性に直結する。

#### 字数配分（2層設計との対応）

| 層 | 役割 | 字数 |
|----|------|------|
| 前半（ホリゾンタル入口） | 共感・問題・普遍的欲求の言葉で広く取る | **26〜32字** |
| 後半（バーティカル予告） | 解決・結果・結末ワードで深さを示す | **8〜18字** |

前半26〜32字は「タイムラインで表示される先頭30文字程度」に核を置くための配分。前半が26字未満だと入口が言い切れず、32字を超えると予告が表示域から押し出される。区切りの読点・句点は前半に数える。

```
例: 推奨レンジと字数配分の両方を満たすタイトル（46字 / 前半30字・後半16字）
「毎朝いちばんに使えるはずの時間が、気づけば動画に溶けていた。場所を変えて取り戻した3つの手順」
 ↑前半30字: ホリゾンタル入口（時間・逃避）   ↑後半16字: 手段と数字で深さを予告

例: 簡潔にまとめた2文構成（31字 / 前半16字・後半15字）
「プロンプトが思い通りに動かない。その原因は『前提の省略』だった」
 前半が26字未満のため入口はやや狭い。テーマが1語で伝わる場合のみ許容する
```

#### 50文字を超えた場合

末尾の切り捨ては禁止。リライトの6手順は [heading-structure-rules.md](../skills/run-x-longpost-create/references/heading-structure-rules.md) §1「R1 違反時の対処」を参照する。リライト時は本ガイドの構文パターンA〜H（§1）・禁止表現（§3.3）・上記の字数配分に沿わせる。

```
Before（60字・違反 / 前半35字・後半25字）
受け取ったメールに片っ端から返信していて、午前中がまるごと消えていた。返信の順番を決めるルールを作ってから手が空いた理由

After（40字・PASS / 前半27字・後半13字）
受け取ったメールへの返信で、午前がまるごと消えていた。順番を決めて手が空いた理由
 ↑前半27字: ホリゾンタル入口（時間の消失）を保持   ↑後半13字: 修飾語を削り結末ワード「理由」を維持
```

#### 検証（必須・機械的に行う）

```bash
node ${CLAUDE_PLUGIN_ROOT}/scripts/validate-title.js --title "[生成したタイトル]"
```

終了コード0（PASS）になるまでタイトルを確定しない。
検証項目は文字数のほか、絵文字なし・禁止表現なし（§3.3）・ファイル名に使えない文字なし。

### 3.5 シリーズ物の扱い

```
避けるべき表現:
- 「前編」「後編」
- 「Vol.1」「Vol.2」
- 「第1回」「第2回」

理由: 後編を読むハードルが上がる

推奨:
各記事が単体でも読みたくなるタイトルにする

悪い例: プロンプト設計術 Vol.1
良い例: 指示が伝わらないプロンプトに足りない「文脈の共有」
```

### 3.6 作品タイプの明記

```
小説や漫画など創作物の場合:
- タイトルは芸術性を重視
- 末尾に【小説】【漫画】【エッセイ】と明記

例:
「月明かりの図書館【小説】」
「AIと僕の奇妙な同居生活【漫画】」
```

## 4. タイトル作成フレームワーク

### 入力要素（parse-inputから取得）

| 要素 | タイトルでの活用 |
|------|------------------|
| キャッチコピー | 核心メッセージの抽出 |
| 最も言いたいこと | 結論・主張の明示 |
| 理想の状態 | ゴール・ベネフィットの提示 |
| 現状の問題 | 共感ポイント・Before状態 |
| 解決策 | 方法・ノウハウの示唆 |
| 具体的な数値・事例 | 信頼性・具体性の付与 |

### タイトル生成プロセス

```
Step 1: 核心メッセージの特定
└─ キャッチコピーと「最も言いたいこと」から抽出

Step 2: ターゲット読者の明確化
└─ 誰に読んでほしいか？

Step 3: ネタ性質判定
└─ 一般向け（ホリゾンタル型）か専門家向け（セミバーティカル型）かを判定し入口の広さを決める

Step 4: 欲求翻訳
└─ 専門語・手段を普遍的欲求6カテゴリの言葉に翻訳し、入口（前半）に置く

Step 5: ベネフィットの明示
└─ 読者が得られる価値は？

Step 6: 構文パターンの選択
└─ A〜Hのパターンから最適なものを選択

Step 7: キーワード配置の最適化
└─ 重要キーワード（欲求翻訳後）を前半（入口26〜32字）に配置し、後半は予告8〜18字に収める

Step 8: 期待値の調整
└─ 内容と期待が一致しているか確認

Step 9: 機械検証
└─ node ${CLAUDE_PLUGIN_ROOT}/scripts/validate-title.js --title "..." を3案すべてに実行し、
   終了コード0（PASS）の案だけを次フェーズへ渡す（§3.4）
```

このプロセスは Phase 1.5（create-title）で実行する。ここで確定したタイトル文字列が、以降の見出し1・長文Bの先頭行・`# タイトル` セクション・ファイル名で一字一句そのまま使われる（[heading-structure-rules.md](../skills/run-x-longpost-create/references/heading-structure-rules.md) §2「タイトルの4箇所一致」）。

## 5. チェックリスト

### タイトル完成後の確認

| 項目 | 確認内容 |
|------|----------|
| **50文字以内** | **`node ${CLAUDE_PLUGIN_ROOT}/scripts/validate-title.js --title "..."` が終了コード0か（絶対ルールの正本は [heading-structure-rules.md](../skills/run-x-longpost-create/references/heading-structure-rules.md) R1・推奨レンジは§3.4）** |
| **字数配分** | **前半（入口）26〜32字・後半（予告）8〜18字に収まっているか（§3.4）** |
| 内容伝達 | タイトルだけで記事の内容がわかるか |
| 結論含有 | 読者が得られるベネフィットが明確か |
| キーワード配置 | 重要キーワードが最初の30文字以内にあるか |
| 具体性 | 固有名詞・数字・疑問文のいずれかが含まれているか |
| 期待値 | タイトルの期待と記事内容が一致しているか |
| 単体完結 | シリーズ物でも単体で読みたくなるか |
| **禁止表現** | **「〜した話」「〜を作った話」型になっていないか** |
| **共感ワード** | **「苦手」「悩んでいた」など読者の自分事化を促す表現があるか** |
| **2文構成** | **前半で共感/問題、後半で解決/ベネフィットの構造になっているか** |
| **結末ワード** | **「理由」「方法」「秘訣」など好奇心を引く結末ワードを使っているか** |
| 入口の専門語 | 前半30文字に専門語・ツール名がない（セミバーティカル型は1つまで） |
| TAMチェック | 限定属性（年代・地域・職業・業務・ツール名）が2つ以上重なっていない |
| 2層設計 | 前半がホリゾンタル入口・後半がバーティカル予告になっている |

## 6. 出力形式

### タイトル候補（3パターン）

構文パターンA〜H（§1）から、ネタ性質に合う3種を選んで案を作る。下記は選定例。

```markdown
## タイトル候補

### パターンA（結論先出し型）
[タイトル案1]
- 強み: [このタイトルの特徴]
- 想定読者: [ターゲット]

### パターンB（疑問→解答型）
[タイトル案2]
- 強み: [このタイトルの特徴]
- 想定読者: [ターゲット]

### パターンC（具体数値型）
[タイトル案3]
- 強み: [このタイトルの特徴]
- 想定読者: [ターゲット]

### 推奨
[最も適切なタイトル] (理由: [選定理由])
```
