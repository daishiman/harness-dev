# 見出し構造の絶対ルール（正本）

長文Aパターンの見出し1・見出し2に関する絶対ルールと、その機械検証手順を定める正本。

| 関連正本 | 担当範囲 |
|---------|---------|
| 本ファイル | 見出し構造の絶対ルール（R1/R2/R3）・4箇所一致・check ID 一覧・終了コード・リライト6手順の実体 |
| [title-guidelines.md](../../../references/title-guidelines.md) | タイトルの文言設計（構文パターンA〜H・共感/結末ワード・心理トリガー・禁止表現・字数配分） |
| [heading-title-guide.md](heading-title-guide.md) | 見出し2の書き方の実質正本（役割名NG・内容の核心を見出しにする原則・NG/OK例） |

## 1. 3つの絶対ルール

例外は認めない。守れていない状態で次フェーズへ渡してはならず、完了報告もしてはならない。

| ID | 絶対ルール | 根拠 |
|----|-----------|------|
| R1 | 見出し1（`# タイトル`）は50文字以内（コードポイント数・空白含む）。本文中にちょうど1つ | 編集規範として設けた上限（下記の根拠を参照） |
| R2 | 見出し1の後に見出し2（`##`）が必ず1つ以上存在する | 見出し2がないとAパターンが文脈区切りのない一枚岩になり、読者が構造を追えない |
| R3 | 長文Bパターンでは、Aパターンの見出し2に対応する行を `【】` で囲む（`【見出し文言】` の単独1行。文言・順序はAの見出し2と完全一致。先頭のタイトル行と本文行は囲まない） | Bはコードブロック内のプレーンテキストで `##` が使えず、見出しと本文の区別がつかないため |

### R1 の根拠

50文字はファイルシステムの制約ではなく編集規範である。タイムラインで最初に読まれるのは先頭30文字程度であり、そこに核を置いたうえで予告を足すと50文字に収まる。加えて、この文字列は長文Bの先頭行・`# タイトル`・ファイル名のタイトル部にも同一で使われるため、短く保つことが一覧性と命名の一貫性に直結する。

編集規範であっても上限値は絶対（FAIL）として扱う。警告への降格はしない。

### R1 違反時の対処

**末尾の切り捨ては禁止。** 文意が途切れ、見出し1とファイル名の意味が壊れる。

1. 前半のホリゾンタル入口（普遍的欲求の言葉・26〜32字）は保持する
2. 後半のバーティカル予告を圧縮する（修飾語・重複する状況描写を削る。8〜18字が目安）
3. 固有名詞・数字は残す
4. [title-guidelines.md](../../../references/title-guidelines.md) の構文パターンA〜Hに当てはめ直す
5. 50文字以内に収まるまで手順2〜4を最大3回繰り返す
6. 3回で収まらない場合は軸が2つある。投稿の軸を1つに絞ってから作り直す

### R2 違反時の対処

**見出し2を生成し直す。** 本文の文脈の区切りを特定し、[heading-title-guide.md](heading-title-guide.md)（見出し2の書き方の正本）に従って3〜8個（実運用中心は5〜8個）の見出し2を配置してから再検証する。各見出し2は12〜28字を目安とし、役割名（導入・課題・解決策・まとめ等）をそのまま見出しにしない。

### R3 違反時の対処

**Bの見出し行を `【見出し文言】` の形へ直す。** Aの見出し2（`##` 行）を上から順に取り出し、同じ文言・同じ順序でBの対応行へ `【】` を付ける。文言は言い換えず一字一句そろえる。先頭のタイトル行（F1の対象）と本文行には `【】` を付けない。囲みを付け足したり外したりしても本文の文言は変えないため、F4のA/B同値は影響を受けない（F4はBの `【…】` 行を比較対象から除く）。

### リード文の扱い

見出し1と最初の見出し2の間には、冒頭フックのリード文を置いてよい（AI文章編集の原則②「冒頭に命をかける」）。ただし置けるのはリード文のみで、見出しを挟まず、空行を除き8行・300文字以内に収める。

## 2. タイトルの4箇所一致

同一のタイトル文字列が次の4箇所で使われる。4箇所すべてが一致していなければならない。

| 使用箇所 | 形式 | 検証 |
|---------|------|------|
| 長文Aパターンの見出し1 | `# タイトル` | H1/H8（基準） |
| 長文Bパターンの先頭行 | プレーンテキストのタイトル（`【】` で囲まない） | F1 |
| `# タイトル` セクションの値 | プレーンテキストのタイトル | F2 |
| ファイル名のタイトル部 | `X長文投稿-prompt作成 - YYYY-MM-DD_[サニタイズ済タイトル].md` | F3 |

サニタイズは `\ / : * ? " < > |` を除去し、空白を `_` に置換するのみ（`${PLUGIN_ROOT:-${CLAUDE_PLUGIN_ROOT}}/scripts/generate-filename.js` の `sanitizeTitle` と同一ロジック）。**長さによる切り詰めはしない。**

ファイル名は必ずスクリプト経由で生成する（手書きで組み立てない）。

```bash
node ${PLUGIN_ROOT:-${CLAUDE_PLUGIN_ROOT}}/scripts/generate-filename.js --date "YYYY-MM-DD" --title "[見出し1と同一のタイトル]"
```

| 終了コード | 意味 | 次アクション |
|-----------|------|-------------|
| 0 | PASS | 出力された `fullPath` をそのまま使う |
| 1 | タイトルが50文字超 | 切り詰めず、R1の手順でリライトしてから再実行 |

## 3. 機械検証

### 3.1 タイトル単体（Phase 1.5 create-title）

```bash
node ${PLUGIN_ROOT:-${CLAUDE_PLUGIN_ROOT}}/scripts/validate-title.js --title "[タイトル案]"
```

終了コード 0=PASS / 1=FAIL / 2=引数エラー。3案すべてに実行し、推奨タイトルがPASSしない状態で次フェーズへ渡さない。

### 3.2 見出し構造（Phase 2 optimize-length）

`--text` に渡すのは **`# タイトル` 行を含むパターンA全文**。`prompts/x-longpost-output-file.md` の `{{投稿文_長文A}}`（タイトル行を除く本文）とは別物なので混同しない。

```bash
node ${PLUGIN_ROOT:-${CLAUDE_PLUGIN_ROOT}}/scripts/validate-headings.js --text "[# タイトル 行を含むパターンA全文]" --title "[Phase 1.5 で確定したタイトル]" --strict-h2-count
```

`--text` を使うときは `--title` が必須（未指定は exit 2）。本スキルでは H5（見出し2が3〜8個）を警告で見逃さないため `--strict-h2-count` を常に付ける。タイトル比較を意図的に外す場合のみ `--allow-no-title` を付ける。

### 3.3 生成ファイル全体（Phase 3 output-file・出力直後）

```bash
node ${PLUGIN_ROOT:-${CLAUDE_PLUGIN_ROOT}}/scripts/validate-headings.js --file "[生成ファイルの絶対パス]" --title "[Phase 1.5 で確定したタイトル]" --strict-h2-count
```

`--file` でも `--strict-h2-count` を付ける（未指定だと H5 が警告扱いのまま常に PASS する）。`--title` を併せて渡すと H8 も判定され、4箇所一致が全項目そろう。`## Aパターン` / `## Bパターン` 直後のコードブロックを自動抽出し、F1〜F3 のタイトル整合、F4 のA/B本文同値、F5 のB本文に1行2文が無いこと、F6 のB見出しの `【】` 表記とAの見出し2との一致をまとめて検証する。

### 3.4 check ID 一覧

| ID | 内容 | 判定 | FAIL時の対処 |
|----|------|------|-------------|
| H1 | 先頭の非空行が見出し1 | FAIL | 先頭に `# タイトル` を置く |
| H2 | 見出し1が本文中にちょうど1つ | FAIL | 余分な `#` を `##` へ降格する |
| H3 | 見出し1が50文字以内 | FAIL | R1の手順でリライト（切り捨て禁止） |
| H4 | 見出し1の後に見出し2が存在 | FAIL | R2の手順で見出し2を生成し直す |
| H4b | 見出し1と最初の見出し2の間はリード文のみ（8行・300字以内） | FAIL | リード文を圧縮する。H4未達（見出し2ゼロ）のときは `severity:"skipped"` となり failed に載らない |
| H5 | 見出し2が3〜8個 | 警告（本スキルは常にFAIL） | 既定 `--min-h2 3 --max-h2 8`。実運用中心は5〜8個。`--strict-h2-count` 指定時のみFAILとなるため、本スキルでは全実行で同フラグを付ける |
| H6 | 見出しに絵文字なし | FAIL | 絵文字を除去する |
| H7 | 見出し3以下（`###`）不使用 | FAIL | `##` へ統合する |
| H8 | 見出し1が `--title` と完全一致 | FAIL | `--text` 使用時は `--title` 必須（未指定は exit 2）。不一致なら見出し1かタイトル指定のどちらかを揃える |
| H9 | 見出し2の長さが12〜28字 | 警告 | 短すぎる見出しは役割名化しやすく、長すぎる見出しは本文化する。[heading-title-guide.md](heading-title-guide.md) の3ステップで核心へ凝縮する |
| H10 | 見出し2が役割名でない | FAIL | [heading-title-guide.md](heading-title-guide.md) のNG役割名リスト（導入・背景・課題・解決策・まとめ・結論・考察・補足など）と完全一致する見出しはFAIL。内容の核心を表す具体的な見出しへ書き換える |
| F1 | Bパターン先頭行が見出し1と一致 | FAIL | Bパターン先頭行を見出し1と同一文字列に直す |
| F2 | `# タイトル` セクションの値が見出し1と一致 | FAIL | 同上 |
| F3 | ファイル名のタイトル部が見出し1（サニタイズ後）と一致 | FAIL | `generate-filename.js` の出力に合わせて付け直す |
| F4 | Aの Markdown 見出しを除いた本文と、Bの先頭タイトルを除いた本文が空白・改行正規化後に同値。Bの `【…】` 見出し行は比較対象外 | FAIL | 内容を足し引きせず、A/Bを同じ本文へ戻す |
| F5 | Bの非空本文行に2文以上を詰めない（`【…】` 見出し行は対象外） | FAIL | 終端記号が2つ以上ある行を分割する。終端記号があるなら行末に置く |
| F6 | Bの見出しが `【】` で囲まれ、Aの見出し2と順序込みで一致 | FAIL | Bの見出し行を `【見出し文言】` の形にし、Aの見出し2と同一文言・同一順序へ揃える。本文行・タイトル行は囲まない |

### 3.5 オプション

| オプション | 既定値 | 用途 |
|-----------|-------|------|
| `--max-title` | 50 | 見出し1の上限文字数 |
| `--min-h2` / `--max-h2` | 3 / 8 | 見出し2の個数の目安 |
| `--strict-h2-count` | 無効 | H5を警告からFAILへ格上げ（本スキルでは常に指定する） |
| `--strict-adjacent` | 無効 | リード文を一切許さず、見出し1の直後を見出し2に強制 |
| `--max-lead-lines` / `--max-lead-chars` | 8 / 300 | リード文の上限 |
| `--allow-no-title` | 無効 | `--text` 使用時に `--title` 必須の制約を外す（H8をスキップ） |

### 3.6 終了コード

| コード | 意味 | 対処 |
|-------|------|------|
| 0 | PASS | 次フェーズへ進む |
| 1 | FAIL | failed に載った check ID の対処列に従って直し、再実行する |
| 2 | 引数エラー | `--text` 使用時の `--title` 未指定などを確認する |
| 3 | テンプレート構造不一致（`## Aパターン（文脈改行型）` 直後にコードフェンスが無い） | 旧テンプレ形式の可能性がある。新規生成物で出た場合は expand-template.js の展開失敗を疑い、テンプレートから作り直す |

## 4. パターンAの見出し配置の実例

```
# プロンプトが思い通りに動かない原因と解決策

プロンプトが思い通りに動かない。そう感じたことはありませんか？
僕も最初はそうでした。何度書き直しても、AIの返答がズレる。

## 原因は思ったよりシンプルだった

でも、原因は意外とシンプルだったんです。
それは「前提の省略」でした。

## 前提を書き足すだけで返答が変わる

（本文）

## 明日から使える3つの書き方の型

（本文）
```

見出し1の直後の2行がリード文（冒頭フック）。その後に見出し2が3個以上続く。各見出し2は12〜28字（H9）で、役割名（導入・課題・解決策・まとめ等）を使っていない（H10）。

## 4.1 パターンBの見出し表記の実例

§4 と同じ内容をBパターンで書くと次の形になる。先頭のタイトル行はベタ書き（`【】` なし）、見出しは `【】` の単独1行、本文は文脈（文節・句読点）で改行する。

```
プロンプトが思い通りに動かない原因と解決策

プロンプトが思い通りに動かない。
そう感じたことはありませんか？

【原因は思ったよりシンプルだった】

でも、原因は意外とシンプルだったんです。
それは「前提の省略」でした。

【前提を書き足すだけで返答が変わる】

（本文）
```

見出しの文言と順序はAの見出し2と完全に一致する（F6）。`【】` を外した本文はAと同値でなければならない（F4はBの `【…】` 行を除いて比較する）。

**制約**: F4 は「Bの `【…】` 単独行＝見出し」という前提で比較対象から除くため、A側の**本文**に `【…】` だけの単独行を置いてはならない。置くとB側の同じ行が見出しとして除外され、A側だけに残った分がF4の不一致になる。強調が必要なら `【】` 以外の表記を使うか、同じ行に本文を続ける。

## 5. 設計判断の記録

当初 R2 を「見出し1の**直後の非空行**が見出し2」として実装したところ、`05_Project/X/` の実運用5件中4件がFAILした。計測の結果、見出し1と最初の見出し2の間には0〜6行・0〜183文字のリード文（冒頭フック）があり、これはAI文章編集の原則②に沿った正しい書き方だった。

そのため R2 は「見出し1の後に見出し2が必ず1つ以上存在する」（絶対ルール）とし、隣接強制は `--strict-adjacent` のオプション扱いへ変更した。リード文の量的上限は H4b で担保する。

同様に、既存仕様の「見出し2は3個から5個程度」は目安表現であり実運用は5〜8個だったため、v3.13.0 で既定レンジを 3〜8 に確定し、H5 は既定で警告のみとした。

見出し1の50文字上限についても、当初は「ファイル名が壊れる」ことを根拠にしていたが、実測ではファイル名のタイトル部は224文字まで書き込み可能で、Obsidian の Wikilink も121文字で正常に解決した。上限の根拠は技術的制約ではなく編集規範であるとv3.13.0で改めた（§1「R1 の根拠」）。上限値そのものは変更していない。

F5 も当初は「Bの非空本文行が1行につきちょうど1文」として実装していたが、この判定は実運用の正しい出力をすべてFAILにしていた。このスキルのB改行は文字数ではなく文脈（文節・句読点の切れ目）で切るため、1文が複数行にまたがるのが正しい書き方であり、「ちょうど1文」を要求すると文脈改行そのものが違反になる。そのため F5 の判定を「1行に2文以上を詰めない（終端記号が0個または1個で、あるなら行末）」へ緩和した。禁じたかったのは1行への詰め込みであって、1文を複数行へ分けることではない。`【…】` 見出し行は終端記号を持たないため F5 の対象外とする。
