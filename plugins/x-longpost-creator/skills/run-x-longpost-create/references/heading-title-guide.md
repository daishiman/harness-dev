# 見出しタイトル作成ガイド

> 旧名「見出しタイトル作成ガイド」。v3.3.0 で見出しへの絵文字使用が全面禁止となり、v3.11.0 で絵文字カタログを廃止して見出しタイトル作成ガイドへ全面改訂した（旧内容は git 履歴に保存）。ファイル名は参照互換のため維持している。

## 絶対ルール

**タイトル・見出し（#/##/###）・本文・すべての成果物に絵文字は一切使用しない。**

- 見出しは内容を具体的に表現したテキストのみで構成する
- 装飾は記号や絵文字に頼らず、見出しの言葉そのもので表現する
- 意味の象徴・強調・分類のいずれの目的でも絵文字は使わない
- 検証: `node ${PLUGIN_ROOT:-${CLAUDE_PLUGIN_ROOT}}/scripts/check-no-emoji.js --file <path>` で絵文字ゼロを機械的に確認できる

## 見出しタイトル作成の原則

### 最重要: 本文の内容を具体的に反映させる

**避けるべき汎用的なタイトル（構成の役割名をそのまま見出しにしない）:**
```
## 問いかけ
## 理想の状態
## 現状の問題
## 原因分析
## このままだと
## 最悪の未来
## 解決策
## まとめ
```

**目指すべき具体的なタイトル:**
```
## 「続ければ成果が出る」と信じていた
## 行動→結果→改善のサイクルが回る状態
## インプレッション数すら見ていなかった
## 習慣化のステージを抜け出せなかった
## 届けたい人に届かない
## 「続けても意味がない」と諦めてしまう
## フィードバックをかける
## まずはここから始める
```

### ホリゾンタル入口との関係

最初の見出しは広く（読者の悩み・欲求の言葉）、中盤以降の見出しは深く（手順・数字）。
詳細は [horizontal-vertical-guide.md](../../../references/horizontal-vertical-guide.md) §8 を参照。

### タイトル作成の3ステップ

| ステップ | 内容 | 例 |
|---------|------|-----|
| 1. 本文を読む | そのセクションで最も伝えたい核心を特定 | 「毎日投稿していたのにインプレッション数を見ていなかった」 |
| 2. 核心を短縮 | 12〜28字に凝縮（H9 の判定レンジと一致） | 「インプレッション数すら見ていなかった」 |
| 3. 絵文字ゼロ確認 | 絵文字・装飾記号が付いていないことを確認し、言葉だけで内容が伝わるか見直す | インプレッション数すら見ていなかった |

### 良いタイトルの特徴

| 特徴 | 説明 | 良い例 | 悪い例 |
|-----|------|--------|--------|
| **具体性** | 何が起きているかイメージできる | 30分の作業が5分で終わるように | 効率化できた |
| **行動・状態** | 動詞や状態を含む | フィードバックをかける | 解決策 |
| **感情・体験** | 読者が共感できる表現 | 「このまま続けても意味がない」と感じる | 最悪の未来 |
| **数値・固有名詞** | 具体的な数字や名前 | 半年以上毎日投稿していた | 長期間継続していた |
| **引用・セリフ** | 心の声や実際のセリフ | 「今日も投稿できた」で満足していた | 達成感だけで終わっていた |

## セクション別タイトル作成例

役割名（NG）ではなく、内容の核心（OK）を見出しにする。

#### 問いかけセクション（導入）
本文の冒頭の問いや思い込みをそのままタイトルに:
- NG: 問いかけ
- OK: 「続ければ成果が出る」と信じていた
- OK: 仕様書は詳しいほど良いと思っていた
- OK: 手作業でも仕方ないと諦めていた

#### 理想の状態セクション
達成したい状態を具体的に描写:
- NG: 理想の状態
- OK: 行動→結果→改善のサイクルが回る状態
- OK: 必要な情報だけを適切に取得できる
- OK: 15分の作業が5分で完了する

#### 現状の問題セクション
実際に起きていた具体的な問題を記述:
- NG: 現状の問題
- OK: インプレッション数すら見ていなかった
- OK: 仕様書が10万文字を超えて精度が落ちた
- OK: 毎回同じ手順を手作業で繰り返していた

#### 原因分析セクション
なぜその問題が起きたかの核心:
- NG: 原因分析
- OK: 習慣化のステージを抜け出せなかった
- OK: 情報を詰め込みすぎて取得精度が低下
- OK: 「手間はかかるもの」という固定観念

#### 危機感セクション（このままだと）
放置した場合の具体的な悪影響:
- NG: このままだと
- OK: 届けたい人に届かない
- OK: 開発するほど精度が落ちていく
- OK: 時間だけが消費されて成果が出ない

#### 最悪の未来セクション
最も避けたい結末を感情込みで:
- NG: 最悪の未来
- OK: 「続けても意味がない」と諦めてしまう
- OK: AIツール自体を使わなくなる
- OK: 努力が報われないまま終わる

#### 解決策セクション
具体的な解決アクションを動詞で:
- NG: 解決策
- OK: フィードバックをかける
- OK: スキルを分類ごとに分離する
- OK: 決定論的処理をスクリプト化する

#### まとめセクション
次のアクションを明確に:
- NG: まとめ
- OK: まずはここから始める
- OK: フィードバックの仕組みを作る
- OK: 改善結果を共有していく

## 組み合わせパターン

### 問題解決型投稿の例

```
## 「続ければ成果が出る」と信じていた
## インプレッション数すら見ていなかった
## 習慣化のステージを抜け出せなかった
## 届けたい人に届かない
## 「続けても意味がない」と諦めてしまう
## フィードバックをかける
## まずはここから始める
```

### 体験談型投稿の例

```
## 月1回のミーティングで気づいた
## 30分の作業を効率化することばかり考えていた
## 効率化より効果を追求すべきだった
## インプレッション数を指標にする
```

### 技術改善型投稿の例

```
## 仕様書は詳しいほど良いと思っていた
## 10万文字を超えて精度が落ちた
## LLMが必要な情報を取得できていない
## スキルを分類ごとに分離する
## タスク仕様書に必要なスキル名を記述
## 精度と保守性が両立する状態へ
```

### 比較型投稿の例

```
## 以前：手作業で15分かかっていた
## 今：スキル化で5分で完了
## 時間だけでなく精度も向上
## 苦手な作業もAIに任せられる
```
