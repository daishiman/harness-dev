# 文書の章立て

ヒアリング.md・要件定義.md・仕様書.md・変更点.md の見出しと表の列。
見出しの文字は validate-briefing-docs.mjs が完全一致で調べる。番号、句点、空白も含めて変えない。
要件定義.md と仕様書.md の形は、実装のスキル (/build-app など) がそのまま読む入力でもある。

## 共通の決まり

- 1 行目は `# <種類>: <タイトル>`。タイトルは briefing.json の `title` と同じ。
- 要件定義.md と仕様書.md は `版: vX.Y` と `更新日: YYYY-MM-DD` の行を持つ。ヒアリング.md は `更新日:` だけ。
- 版の正は 要件定義.md の 2 行目。仕様書.md の版と更新日はそれと同じにする (ずれると VERSION-MISMATCH、DATE-MISMATCH)。
- 文の終え方と長さは [quality-rules.md](quality-rules.md) の「3. 言葉」を読む。
- 人は役割名 (配車の担当者、運転手) で書くのを基本にする。素材にある人と会社の名前を書いてよいかは、briefing.json の `data_policy` で決まる ([quality-rules.md](quality-rules.md) の「名前と値の扱い (data_policy)」)。

### 番号

| 記号 | 何の番号 | どこで振るか | 書き方 |
| --- | --- | --- | --- |
| H | 聞いたこと | ヒアリング.md 1〜4 章 | 質問ごとに決まった番号 (hearing-guide.md 4 章の表の H01〜H36) を使う。章をまたいで重複させない。`要望` の行は 1 章の表の最後に、文書全体の最後の番号の続きで足す (雛形なら H37 から) |
| F | できること | 要件定義.md 6 章 | F01 から |
| Q | 決めること | 要件定義.md 9 章 | Q01 から。決まっても番号は消さない |
| S | 画面 | 要件定義.md 5.2 と 6 章 | S01 から、5.2 これから で初めて出てくる順。仕様書 1 章と 3 章の見出しも同じ番号と名前 |
| D | データ | 仕様書.md 4 章 | D01 から |
| R | 処理のルール | 仕様書.md 5 章 | R01 から |
| C | 変更 | 変更点.md の版ごと | 版ごとに C01 から振り直す |

### 根拠の書き方

表の「根拠」列は空にしない。値は次の 4 つのどれか。

| 値 | 意味 | 例 |
| --- | --- | --- |
| `素材:<ファイル名>[#場所]` | 素材に書いてある | `素材:配車表.pdf#1ページ上段` |
| `聞き取り:Hxx` | ヒアリングで聞いた | `聞き取り:H03` |
| `例` | 素材にも聞き取りにもない仮の値 | `例` |
| `決めること:Qxx` | まだ決まっていない。案で書いてある | `決めること:Q02` |

`例` が多い表は、打ち合わせで聞くことが多いという印。無理に根拠を作らない。

## ヒアリング.md

```markdown
# ヒアリング記録: <タイトル>
更新日: YYYY-MM-DD

## 1. 目的と範囲
## 2. 画面の共通ルール
## 3. しくみと基盤
## 4. 運用
## 5. あとで相談すること
```

- 1〜4 章は表 `| 番号 | 質問 | 回答 | 出どころ |`。
- 出どころは `聞き取り` / `素材:<ファイル名>` / `既定案` / `未定` / `要望` のどれか。`要望` は、名前を挙げて頼まれた機能の行 (質問 = どんな機能を頼まれたか、回答 = 頼まれた中身)。扱いは [quality-rules.md](quality-rules.md) の「1. シンプルさ」を読む。
- 5 章は箇条書き。未定 の行 (「- H17: ログインする人と方式を決める」) だけを書く。広げる案は H06 の回答にまとめ、仕様書 8 章の候補はそこから取る。
- 書くのは run-briefing-hearing だけ。質問・既定案・欄ごとの書き方は [hearing-guide.md](../skills/run-briefing-hearing/references/hearing-guide.md)。

## 要件定義.md

```markdown
# 要件定義書: <タイトル>
版: v0.1
更新日: YYYY-MM-DD

## 1. 目的
## 2. 今の困りごと
## 3. 範囲
### 3.1 最初の版でやること
### 3.2 やらないこと
## 4. 使う人と端末
## 5. 業務の流れ
### 5.1 今
### 5.2 これから
## 6. できること
## 7. 守ること
## 8. 用語
## 9. 決めること
```

| 章 | 形 | 書くこと |
| --- | --- | --- |
| 1. 目的 | 2〜3 文 | 何のために作るか |
| 2. 今の困りごと | 箇条書き | 素材と聞き取りで分かった困りごと |
| 3.1 最初の版でやること | 箇条書き 3〜5 個 | 「こういうことがやれます」。`docs.first_version_items_warn` を超えると warn |
| 3.2 やらないこと | 箇条書き | 最初の版に入れないこと |
| 4. 使う人と端末 | 表 `\| 使う人 \| 人数 \| 端末 \| 主にすること \|` | 役割ごとに 1 行 |
| 5.1 今 / 5.2 これから | 番号つき箇条書き 3〜6 段 | 仕事の流れ。これからは人としくみの段を分ける |
| 6. できること | 表 `\| 番号 \| できること \| 画面 \| 最初の版 \|` | 番号 F01..、画面は `S01, S02`、最初の版は `○` か `あとで`。ヒアリング.md の `要望` の行から来た機能は、できること の終わりに `(要望:Hxx)` を付ける (無いと REQUEST-MISSING) |
| 7. 守ること | 箇条書き | 速さ・安全・バックアップ・使いやすさ。ヒアリングで答えがあれば、量 (H30)・止まったとき (H35)・使う時間帯 (H36) も 1 行ずつ足す |
| 8. 用語 | 表 `\| 用語 \| 意味 \|` | 言い換えずに使った語と、案件だけの言葉 |
| 9. 決めること | 表 `\| 番号 \| 決めること \| 案 \| 誰に聞くか \|` | 番号 Q01..。決まったら行は消さずに、案 を答えに、誰に聞くか を「決定 (<決まったときの版>)」にする。6 章で `(要望:Hxx)` の行を `あとで` に回したら、決めること に `要望:Hxx` を書いて聞く (無いと REQUEST-DEFERRED-NO-Q) |

- 3.1 の項目は、6 章の `最初の版 = ○` の行と同じ中身にする。overview のボードにもそのまま載る。
- ヒアリング.md の 未定 は、9 章に Q として移す。

## 仕様書.md

```markdown
# 仕様書: <タイトル>
版: v0.1
更新日: YYYY-MM-DD

## 1. 画面一覧
## 2. 画面の共通ルール
### 2.1 骨組み
### 2.2 ヘッダー
### 2.3 メニュー
### 2.4 フッター
### 2.5 色の役割
### 2.6 モーダル
### 2.7 メッセージ
### 2.8 空のときと読み込み中
## 3. 画面ごとの項目と動き
### S01 <画面名>
## 4. データの形
### D01 <データ名>
## 5. 処理のルール
## 6. しくみと基盤
## 7. 権限と運用
### 7.1 権限
### 7.2 運用
## 8. 最初の版に入れないもの
```

| 章 | 形 | 書くこと |
| --- | --- | --- |
| 1. 画面一覧 | 表 `\| 画面番号 \| 画面名 \| 使う人 \| 端末 \| ひとことで \|` | 最初の版の画面だけ。`docs.screens_warn` を超えると warn |
| 2.1〜2.8 | 箇条書き | ヒアリング.md 2 章の答え。既定案なら既定案のまま |
| 3. 画面ごと | 下の「画面の書き方」 | 1 章の画面すべて |
| 4. データの形 | `### D01 <データ名>`、そのすぐ下に `1 件 = <何を 1 件と数えるか>` の 1 行 (例: `1 件 = 配車表 1 枚`。無いと DATA-ONE-MISSING)、そのあとに表 `\| 項目 \| 型 \| 必須 \| 例 \| 根拠 \|` | しくみが覚えておくもの。型 の数は単位をかっこで書く (`数 (円)`、`数 (個)`、`数 (件)`)。番号は `番号` と書く (単位が無いと DATA-UNIT-MISSING) |
| 5. 処理のルール | 表 `\| 番号 \| ルール \| いつ \| 根拠 \|` | 番号 R01..。計算、自動の判定、並べ方 |
| 6. しくみと基盤 | 表 `\| 項目 \| 方式 \| 理由 \|` | 下の 7 行を必ず置く。欠けると warn |
| 7.1 権限 | 表 `\| 役割 \| できること \| できないこと \| 見える範囲 \|` | 要件定義 4 章の使う人ごと。見える範囲 は「すべての配車表」「自分が送った配車表だけ」のように、その役割が見られるデータの範囲 |
| 7.2 運用 | 箇条書き | 管理する人、困ったときの連絡先、データを残す期間 |
| 8. 最初の版に入れないもの | 箇条書き (下の「次に広げる候補の書き方 (8 章)」) | 次に広げる候補を 4 個まで |

6 章の 7 行 (項目の文字はこのとおり):

| 項目 |
| --- |
| 動かす場所 |
| データの置き場所 |
| ログイン |
| 外部とのつなぎ |
| 自動で動く処理 |
| バックアップ |
| 通知 |

方式は ヒアリング.md 3 章の回答から書く (決まっていなければ [writing-patterns.md](../skills/run-briefing-docs/references/writing-patterns.md) の「仕様書.md」の 6 章の型)。

### 実装へ渡す情報の記入先

ボードは、読む人が画面構成・操作・状態を直感的に理解するために使う。仕様書には、その画面と動作を再現できる詳細を残す。ボードを簡潔にするために、仕様書の情報まで削らない。

既存の2.1〜2.8・3・4・5・6・7章を使い、以下の本文ラベルを記入する。既存表の列と章立ては変えず、本文を補う。共通値は2章を正本にし、各画面は参照と差分だけを書く。

| 記入先とラベル | 記録する内容 |
| --- | --- |
| 2.1 `共通配置:` | ヘッダー・メニュー・本文・フッターの位置と固定/スクロール。PC/スマホでの順序、幅の扱いと切替条件。未確定の寸法は案とする |
| 2.1 `画面区分:` | 管理画面/ユーザー画面/共用のどれを持つか、対象役割、入口と共通部品。管理画面を作らない場合も理由を記録。役割が2つでも別画面が必須とはしない |
| 2.2 `表示内容:` | アプリ名・画面名・ログイン中の役割、戻る/終了の位置。管理者と利用者で異なる表示 |
| 2.3 `項目と順序:`・`アイコン:` | メニューの並び、現在位置、役割別の表示。アイコンの意味・使用箇所・名称またはローカル素材参照、文字ラベル/読み上げ名、装飾か操作か。形だけで操作を伝えない |
| 2.4 `固定領域:`・`ボタン:` | 下部の位置と固定条件。主/補助/危険操作の区別、文言・位置、押せる条件、処理中・無効時の表示、連打時の扱い。画面固有の値は3章 |
| 2.5 `色と意味:` | 操作・注意・失敗・選択中の役割、対応する文字/印。色だけに依存しない |
| 2.6 `モーダル:` | 開く条件、表示内容、確定/取消の文言、背景/閉じる/Escの扱い、フォーカスの移動と復帰、処理中に閉じられるか。使わなければ理由を書く |
| 2.7 `結果と直し方:` | 成功/入力誤り/権限不足/通信失敗の文言と出す場所、消える条件、入力を残すか、再試行への導線 |
| 2.8 `状態表示:` | 通常/空/読み込み中/処理中/失敗/完了と、利用者が次にできる操作。該当しない状態は理由付きで除外 |
| 各Sxxの `配置:`・`画面区分:`・`状態:` | 上下左右の配置、共通ルールとの差分、管理者/利用者の表示差、画面固有の状態遷移。既存の項目表と操作表に対応づける |
| 4章のデータ表 | 画面の項目から保存データへの対応、識別子、関連、保存/削除、機微な値の扱い。詳細は表の後の本文にD番号で記録 |
| 5章のルール表 | 入力検証、計算、状態遷移、重複実行防止、失敗/再試行と取引の成立条件。画面に返す結果も書く |
| 6章の7行表の後 `処理境界:` | 画面側/サーバー側の責任、入力と出力、使うデータ/外部連携、同期/非同期、失敗時の責任。具体化済みの処理名・通信方式はR/D番号と結ぶ |
| 同 `安全対策:` | 認証・認可、サーバー側での役割/データ範囲の検証、入力/アップロード検査、通信/保存の保護、秘密値の置き場所、操作記録。秘密値そのものは記載しない |
| 同 `稼働構成:` | 実行/保存/ファイル/定期処理の構成と境界、開発・検証・本番の区別、配置地域・ドメイン・公開範囲、設定/配布/戻し方。件数の見込み (H30) と、今あるデータを移す範囲 (H31)。製品名や上限は根拠があるものだけ確定する |
| 7.1の権限表 | 管理者/利用者ごとの閲覧・作成・変更・削除・管理操作と対象範囲。画面で隠すこととサーバーで拒否することを区別する |
| 7.2 `監視と復旧:` | 異常検知・通知先・連絡先・調査記録、控えの保存期間、戻せる時点と復旧時間の目標、復元確認、障害/削除/退職時の担当。止まったときのしのぎ方 (H35) と、止めて直してよい時間帯 (H36) |

記入の判定は実際の内容で行う。空ラベル、コメント、記入指示、`未定` の一語だけでは埋まったとしない。未確認の内容は `案: <仮の内容> (Qxx)` と根拠・確認先を残し、要件定義9章の決めることへつなぐ。`既定案` は合意済みの事実ではない。案が作れない場合は、不明な対象・困ること・誰に確認するかを具体的に書く。

旧資料の不足は補足を促す warn として扱い、一律に新しい必須 error にしない。案が具体的に書かれていても「設計確定」とは報告しない。安全対策や基盤の製品・構成を、聞いていないのに実装済みと断定しない。

### 画面の書き方

お手本は `examples/sample-haisha/打ち合わせ資料/仕様書.md` の「### S01 配車表を送る」を読む。

- 見出しの番号と画面名は 1 章の表と完全に同じ。
- 冒頭の箇条書きは 目的 / 使う人 / 端末 / 開き方 / ボード の既存5行、この順。2つの表のあとに、配置 / 画面区分 / 状態 の本文ラベルを補足する。新しい必須見出しや表列は作らない。
- その下に表を 2 つ置く。項目の表 `| 項目 | 種類 | 必須 | 初期値 | 説明 | 根拠 |` と、操作の表 `| 操作 | 動き | 次の画面 |`。
- 端末は `スマホ` / `PC` / `スマホと PC` のどれか。
- ボードは briefing.json の pages の `no` (2 桁)。複数はカンマ区切り。画面ごとに phone か pc のボードを 1 枚置く (無いと SCREEN-BOARD-MISSING。[workflow.md](workflow.md) の「既定のページ構成」)。
- 次の画面は `S01` の形か、`同じ画面` か、`なし`。

画面ごとに写して埋める型 (山括弧は記入指示であり、完成値ではない):

```markdown
### S01 <1章と同じ画面名>
- 目的: <利用者が達成すること>
- 使う人: <役割>
- 端末: <スマホ / PC / スマホと PC>
- 開き方: <入口と前提>
- ボード: <対応する2桁番号>

| 項目 | 種類 | 必須 | 初期値 | 説明 | 根拠 |
| --- | --- | --- | --- | --- | --- |
| <項目名> | <入力/表示の種類> | <○/なし> | <値またはなし> | <配置、入力条件、検証、表示条件> | <根拠> |

| 操作 | 動き | 次の画面 |
| --- | --- | --- |
| <画面と同じ文言> | <位置/主副/有効条件。押す→処理中→成功/失敗。確認小窓・取消・再試行の扱い。対応R番号> | <S番号/同じ画面/なし> |

- 配置: <2章の共通配置を参照し、上/左/中央/下の部品順・端末差分を書く>
- 画面区分: <管理画面/ユーザー画面/共用。役割別表示と7.1の権限の参照>
- 状態: <通常/空/処理中/失敗/完了の表示と可能な操作。2.8からの差分>
```

ボードにはこのうち画面で見える配置・文言・状態と、判断に要る操作だけを描く。処理の実装・安全対策・稼働構成は5〜7章に残し、ボードからは必要な仕様節を示す。

### 次に広げる候補の書き方 (8 章)

```markdown
- 読み取りの学習: 選んだ候補を覚えて、次から候補の 1 番目に出す。最初の版に入れるかは Q06 で聞く。
  - 備え: 直す前の値と、候補から選んだ欄を、行ごとに消さずに残す (D02)。
  - 時期: 次の版
- 取り込み先のシステムと直接つなぐ: 書き出しと取り込みの手間をなくす。相手のソフトの対応しだい。
  - 備え: 書き出した行に日時の印を付け、2 回送らない (D02)。
  - 時期: その先
```

- 1 段目は `名前: 何ができるか 1 文`。future のボードを置くときは、名前をボードと同じにする。
- 字下げした 2 行を必ず置く (欠けると FUTURE-FIELD-MISSING)。
  - `備え:` は最初の版で今やっておくこと。データだけ (消さずに残す / 分けて置く / 印を付ける) で、使うデータの番号 (D01..) を添える。無ければ「なし。」と、足すときに何を作り直すかを 1 文。
  - `時期:` は `次の版` (使ってみてから足す) か `その先` (相手のソフトしだいで、まだ見えない) のどちらか。
- 備えのために、最初の版の画面・ボタン・メニューを増やさない。備えで足したデータの項目は 4 章の表に「例」で置く。

## 変更点.md

- 1 行目は `# 変更点: <タイトル>`。版ごとに `## v0.2 (YYYY-MM-DD)` の見出しと、表 `| 番号 | 変更 | 場所 | きっかけ |` を置く。
- 決めること が答えで閉じたら、変更 の欄に「Q03 を決定: <答え>」と書く。
- お手本は `examples/sample-haisha/打ち合わせ資料/変更点.md` を読む。
- 新しい版を一番上に足す。一番上の版は 要件定義.md の版と同じ。
- v0.1 では版の節が無くてよい。
- 番号は版ごとに C01 から振り直す。
- 場所は「文書名 章」か「NN のボード」。きっかけは打ち合わせメモのどの話かが分かるように書く (人は役割名で書く)。
- 確認点の答えで足す行の きっかけ は「確認点N の聞き取り (Hxx)」と書く。
- 書くのは run-briefing だけ。
