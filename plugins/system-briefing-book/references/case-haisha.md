# お手本: 配車表の読み取り

plugin の `examples/sample-haisha/` は、架空の案件を、このプラグインの型に合わせて作り直したお手本。
「手書きの配車表をスマホで撮って読み取り、事務所の PC で確かめて、取り込み先のシステムへ渡す」という案件を、型どおりに書いてある。
4画面のお手本 v0.2 と、6画面の配車参考 v0.4 は範囲が違う。構造比較と高再現の受入の正本は [workflow.md](workflow.md) の「再現の測り方」。
データの方針は `masked` (伏せる)。会社・人・場所・車・電話番号・製品名はすべて架空で、紙の写真は使わず、架空の配車表の図を描いてある。ボードの meta には「画面の中の名前と値は例です」の札がある。

## フォルダの形

```
sample-haisha/
  素材/                架空の配車表の図、聞き取りメモ、CSV の列見本
  打ち合わせ資料/
    briefing.json
    ヒアリング.md
    要件定義.md         版 v0.2
    仕様書.md           版 v0.2
    変更点.md           v0.2 の変更が入っている
    _src/               tokens.css、common.css、NN_*.html、assets/
```

PNG とまとめ HTML は置いていない。作業用の場所へ写してから、render-board-png.mjs と build-briefing-book.mjs で作る (setup.md の「3. 動くか試す」)。

## 読む順番

1. **briefing.json の pages**: 全体で何枚、どの型を、どの順に並べたかを見る。画面は 4 つで、1 枚ずつボードにしてある (02〜05)。紙の欄が画面のどこに入るかがこの案件の要なので data-map を、`あとで` に回した要望 (学習) のしくみを見せるために mechanism を足してある。画面の共通ルールと裏側のしくみは仕様書 2 章と 6 章にだけ書き、ボードにはしていない。
2. **要件定義.md の 3.1 と 6 章**: 最初の版でやることが 3〜5 個に絞られ、6 章の `○` と同じ中身になっていることを見る。名前を挙げて頼まれた機能 (照合の候補を出して選ぶ、選んだ候補を学習する) には `(要望:Hxx)` が付いている。学習は `あとで` に回し、入れるかを 9 章で聞いている。まだ決まらないログインする人と方式も、9 章の決めること に回してある。
3. **00 の overview ボード**: 3.1 と同じ数・同じ言い回しで「こういうことがやれます」が 1 枚に収まっていることを見る。今の手間の数字 (`.facts`) と、紙のサムネイル (`data-source`) も見る。
4. **仕様書.md の 3 章と、phone / pc のボード**: 項目表の項目名・ボタンの文言が、ボードの画面の中と同じになっていることを見る。どの画面のボードにも要件の札 (`.reqs`) があり、要件定義 6 章の F 番号とつながっている。
5. **06 の data-map と 07 の mechanism のボード**: data-map は、書き出す列の区分を棒と凡例 (`.bar`、`.legend`) で見せる。mechanism は仕様書 8 章の候補 (学習) のしくみで、kicker が「次の版の候補」になっている。
6. **ヒアリング.md**: 出どころの列 (聞き取り / 素材 / 既定案 / 未定 / 要望) を見る。既定案で進めた所と、未定 を 決めること に回した所、頼まれた機能を 要望 の行に残した所が分かる。
7. **ボードの右の 決めること と 要件定義 9 章**: ボードの `ask` の注記が 9 章の Q 番号でつながっていることを見る。話の出てくるボードが無い Q05 は、9 章だけにある。
8. **変更点.md**: 打ち合わせのあとに版を v0.1 から v0.2 に上げた例。何が、どこで、なぜ変わったかが 1 行ずつ書いてある。

## よいところ

### シンプル

- 最初の版でやることが少ない。「撮る → 読み取る → 確かめる → 渡す」の流れだけで、何ができるシステムかが伝わる。
- 画面ごとに主なボタンが 1 つ。スマホは下の帯に主なボタンを置き、次にすることが迷わず分かる。
- 広げる案を最初の版に混ぜていない。仕様書 8 章の 次に広げる候補 にまとめ、打ち合わせで深掘りする形にしてある。
- 1 ボードの注記が `board.notes_note` 個以内 (assets/data/quality-thresholds.json)。注記の種類 (できること / しくみ / 決めること) で、読む人が「何の話か」をすぐ分けられる。

### 正確

- 表の値に根拠が付いている。書き方は [document-structure.md](document-structure.md) の「根拠の書き方」を読む。
- 紙の欄で読めない所を推測で埋めない。data-map のボードでは注意の行 (`.mrow.warn`) にして `決めること:Qxx` を付ける形をとる。
- 画面番号と画面名が、仕様書 1 章 → 3 章 → briefing.json → ボードの見出しで同じ。
- 判断材料 5 つ (今の手間の数字、紙の架空図、CSV の列の区分、要件の札、あとで に回した要望のしくみ) がボードにそろっている。compare-briefing-profile.mjs で 2 本目の基準点と並べられる。

### 言葉

- 技術の言葉を使わず、現場の言葉で書いてある ([plain-language.md](plain-language.md) の言い換え)。
- 言い換えずに使った語は、要件定義 8 章に意味が書いてある。
- データの方針が `masked` なので、人は役割名、会社は「(例)A運送」、製品は「取り込み先のシステム」のように、役割で書いてある。`source` の案件では素材の名前のままでよい ([quality-rules.md](quality-rules.md) の「名前と値の扱い (data_policy)」)。

### 見た目

- ボードはどれも 1 枚で伝えることが 1 つ。いちばん大きく見えるものが、その 1 つ。
- 色は既定の配色 (standard。jp-web-design の標準カラー) のまま、tokens.css の役割の名前だけで塗ってある。色の値を直接書いていない。
- 端末の画像は `data-export` で切り出し、overview と screen-map で使い回している。描き直していないので、画面が変わっても 1 か所直せばそろう。

## まねるとき

- ページの数と並びは、[workflow.md](workflow.md) の「既定のページ構成」から始める。お手本はそれに data-map と mechanism を 1 枚ずつ足した形。
- data-map と mechanism を置くかは、同じ表の条件で決める。条件に当たらない案件では置かない。
- ボードの言い回しはまねてよいが、値は必ず自分の案件の素材と聞き取りから取る。お手本の値を写さない。
- お手本は plugin の中にあるので書き換えない。試すときは作業用の場所へ写す。

## 参考を再現する場合の対応表

対象参考: 「配車表 読み取りシステム 要件定義(打ち合わせ用 v0.4)」、2026-10-01。§5 は6画面、§6・§6-1 は学習を現在の機能として含む。お手本の版 v0.2 とは別系列であり、同じ版番号へそろえない。

| 対応項目 | 参考 v0.4 の扱い | お手本 v0.2 の扱い | 再現時に記録・受入すること |
| --- | --- | --- | --- |
| ログイン | 画面1。管理者のみ、スマホ／PCで同一アカウント。方式は打ち合わせで決める (§4) | 独立した画面を持たず、対象者・方式は決めることに置く | 対応する画面・ボード・権限を明記。方式未定と画面省略を混同しない |
| 照合マスタ | 画面6。覚えた対応の取消・固定、CSV更新。登録の操作は不要 (§5、F-12・F-14) | 独立した画面を持たない | 対応する画面・操作・仕様節を明記し、参考画像と照合する。更新時に学習済み対応を消さない条件も保つ |
| 学習 | F-13・F-14、画面4・6、画像09。選択を覚え、同条件で3回続けば自動。変更で学習中へ戻る | あとで／仕様書8章／mechanism の次版候補 | 要件番号・状態遷移・画面表示を対応づけ、初版として受け入れる。次版へ移す場合は利用者の合意と差を記録する |

この表だけで照合済みとはしない。再現する案件では、残りの画面と機能も含めて実際の出力番号と確認結果を埋め、未対応は未受入として報告する。受入方法と記録先は共通の「再現の測り方」に従う。
