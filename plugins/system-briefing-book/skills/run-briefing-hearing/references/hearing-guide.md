# ヒアリングの質問と既定案

仕事の場面を短く聞き、回答を要件と仕様へつなぐ。質問・選択肢・聞く回・行き先・回答から拾う観点・設計の仮案の唯一の正本は [hearing-catalog.json](../../../assets/data/hearing-catalog.json)。このガイドは聞き方と回答の扱いを定める。

## 1. 既定案の一覧

既定案をここへ転記しない。catalog の各質問にある `design_default` を読む。これは設計者が提案する仮案であり、利用者の回答ではない。

| catalog の欄 | 使い方 |
| --- | --- |
| `id`・`key`・`section` | 固定H番号・ガイド内の記号・記録する章 |
| `question`・`options` | 業務担当者へ出す問いと、素材に合わせる選択肢の型 (例であり回答済みの事実ではない) |
| `round` | 聞く回。null は素材・ほかの回答から埋め、不明は仮案と未定を残す |
| `destinations` | 要件定義と仕様書への行き先 |
| `capture` | 回答・素材から拾う観点。すべてを追加質問として読み上げない |
| `design_default` | 回答を基に設計者が具体化する案。根拠のない決定に変えない |

保存期間、閲覧・編集・削除範囲、認証、失ってよい記録、停止時間は、聞いていなければ未定にする。仮の方式を置いて進める場合も、確認対象と確認先を残す。ログインした全員に情報を見せる、社内ならログイン不要、夜間は停止可能と推定しない。

## 2. 聞き方

- AskUserQuestion で1回4問まで、全部で6回まで。聞き足しは1〜2回まで増やせる。Codexでは [execution-contract.md](../../../references/execution-contract.md) のホスト差に従い、同じ問いを文で出す。
- 質問は利用者が知っている仕事の場面で聞く。製品、画面の骨組み、小窓、保管方式、細かい上限は選ばせず、回答から設計者が案を作る。
- 選択肢は2〜4個。catalog の型を素材と前の回答の言葉に合わせ、先頭は「(おすすめ)」。業務上の判断材料がなければ「素材から読んだ案」を事実扱いにせず、自由入力で場面を聞く。
- 選択肢は仮の具体例であり、実際の案件に合う根拠があればその業務事実へ差し替える。素材がなくても選べる具体例を2つ以上出し、当てはまらなければ自由入力で聞く。おすすめを個別に選び、問いの具体的な内容を確認できた場合は聞き取りにする。「整理する」「確認する」「あとで」だけの返答は回答済みにせず、未定のHとQへつなぐ。
- 説明は現場の言葉で1文。専門語は [plain-language.md](../../../references/plain-language.md) に従う。headerは12文字以内。
- 回の初めに「案で先に進めてよければ、その他の欄に『全部おすすめ』と書いてください。未確認のことは、あとで確かめる項目に残します」と添える。
- 1問は一つの業務場面に絞る。役割ごとの編集と削除など分けるべき答えは、回答を別々に記録する。captureの全項目を一度に問い詰めない。
- 素材で答えが分かる質問は聞かない。出どころは `素材:<ファイル名>`。以前の画面は参考例であり、今後も同じ配置にする合意ではない。

例 (B6: 取り消しにくい作業):

```yaml
question: "押し間違えると取り消しにくい作業は、どれですか"
header: "取り消せない作業"
multiSelect: false
options:
  - label: "削除や送信の前に確かめる (おすすめ)"
    description: "素材の仕事から、押す前に内容を見直す場面を整理します。"
  - label: "承認や確定も確かめたい"
    description: "後の仕事に影響するので、内容を見直してから進めます。"
  - label: "取り消して直せればよい"
    description: "押した後でも、仕事を戻してやり直したいです。"
```

### 聞き足しと促し方

核心の5問 (A1使う人、A2困りごと、A3最初に必要な仕事、A6先々、A7仕事の流れ) だけ、あいまいなら聞き足す。それ以外は未定と確認先へ回す。

あいまいな答えは、誰・何・量がない、気持ちの言葉だけ、素材と食い違う、いくつも混ざる、「わからない」。次の型で1文だけ促す。

| 型 | 問いの例 |
| --- | --- |
| 最近の場面 | きのう配車表が届いてから打ち直すまで、何をしましたか |
| 具体例から選ぶ | 手間なのは、打ち直す・同じ行を写す・間違いを直す、のどれですか |
| 数や時間 | 配車表は1日に何枚届きますか |
| 外すと困るもの | 撮る・確かめる・書き出す、のうち最初にないと困るものはどれですか |
| まとめ直す | 配車の担当者が送り、請求の担当者が確かめて渡す、という流れですか |

A1〜A3とA7で選択肢を作れないときは、選択肢を出さずこの型で自由入力を求める。聞き足しは1問2回まで、2回目は別の型。「わからない」の後はあと1回までで、合計2回を超えない。followupではこの回数を数え直す。聞き足しも1回4問・追加2回以内に収め、残りは最小の仮案と未定へ回す。

## 3. 答えの扱い

| 答え | 出どころ | 扱い |
| --- | --- | --- |
| 具体的な業務の答え・自由入力 | 聞き取り | 回答を要約する。核心であいまいなら先に聞き足す |
| 仮案の選択・「全部おすすめ」 | 既定案 | 案で進む意思として残す。未確認の業務条件や安全・保持・復旧は未定の行を残す |
| 「わからない」「あとで」 | 未定 | 進める案、不明な点、確認先を書く。核心の「わからない」は上限内で1回促す |
| 素材で分かった | 素材:<ファイル名> | 素材にある事実だけを書く |
| 名前を挙げて頼まれた機能 | 要望 | 1章の末尾にH37以降で足す。後回しにしても行は残す |

- 「全部おすすめ」は残りの質問を省いて案を作る同意であり、収集済み・合意済みを意味しない。確かめていない事実や重要条件を `聞き取り` にしない。
- 未定は5章に `Hxx: 確かめる事柄。確認先: <役割>` と残し、要件定義9章のQへH番号付きでつなぐ。
- 途中で出た将来の案はH06へ集める。ただし明示的に頼まれた機能は `要望` として別に残す。[quality-rules.md](../../../references/quality-rules.md) の「1. シンプルさ」に従う。
- 聞かなかった項目にも固定H行を残す。素材で埋まれば素材、具体的な仮案なら既定案、不明なら未定と確認先。空欄を埋めただけで収集完了にしない。

## 4. 質問の一覧

[hearing-catalog.json](../../../assets/data/hearing-catalog.json) の `questions` を章順に読む。記号A1などはガイド内の呼び名、記録には固定 `id` を使う。H01〜H24を含む既存の番号を変えない。章順と番号順が異なるのは意図した互換性である。

質問を変更するときはcatalogだけを直す。[hearing-catalog.mjs](../../../scripts/lib/hearing-catalog.mjs) が同じ正本を読み、scaffoldはヒアリング雛形の行を生成し、検査は固定質問の集合を使う。既存の記録は上書きしない。素材から必要と分かった補足、追加要望、未定の補足は、文書全体の最後のH番号の次から足す。

### 回答同士のつながり

- A1で社外の人が出たら、その人の見てよい範囲をD4へ、使えるアカウントをC3へつなぐ。不明なら未定にする。
- A7は今とこれからの流れを、人の段としくみの段に分けて「こういう流れですか」と確かめる。承認・差し戻し・失敗時の流れも素材から拾い、不明はQへ送る。
- B11 (利用開始・終了の流れ) で担当者まで分かったらD1 (判断と実行の担当) を同じ出どころで埋め、重ねて聞かない。
- B9で管理を外に頼むのにB11でアプリ内管理を希望するなど、答えが食い違えば案と不明点を分ける。一方を勝手に捨てず未定へ回す。
- A6の候補は4つまでを目安に優先順で整理する。最初の版の画面・ボタンは増やさず、備えは「消さずに残す/分けて置く/印を付ける」のデータだけ。備えがなければ「なし」と、あとで作り直す所を添える。明示された要望は候補数を理由に消さない。
- 将来の説明も見たいと言われた場合だけfutureボードを足す。「今は考えない」ならA5の範囲外を候補とし、備えはなしにする。

### 回答に残す設計情報

質問ごとの `capture` と `destinations` を使い、素材・回答で分かることを拾う。画面・データ・処理・基盤・権限・運用の具体的な記入先は [document-structure.md](../../../references/document-structure.md) の「実装へ渡す情報の記入先」が正本。ここに同じ記入先一覧を複製しない。

captureは面談で一度に全部決めるための質問ではない。業務の回答と設計者の案を分け、未知の製品・地域・構成・保存条件・安全対策を補って `聞き取り` にしない。元の回答から分からない細部は `未定` のH補足行と5章へ残す。質問数を増やさず要件定義Qで担当者へ渡す。ボードは画面に見える情報、仕様書は設計情報を持つ。

## 5. 回の組み方

catalog の `round` の1〜6を順に使い、各回4問以内にする。使う人と流れ、管理と権限、情報、操作、安全と停止、先々と運用の順。素材や前の回答で分かった質問は省く。`round: null` は直接聞く枠に足さず、素材から埋めるか案・未定へ送る。

聞き足しはあいまいな回答の直後に、全部で2回まで。残りを全部おすすめで進める場合も、catalogの全H行を記録する。運用がまだ決められない時点なら無理に選ばせず、確認先と未定を残す。

## 6. 素材から先に埋めるときの目安

帳票や表は残す情報・量・見せる相手、組織図は使う役割と担当、手順メモは受け渡し・例外・時間帯、画面の写しは現在の操作の手がかりになる。各質問のcaptureに照らして事実だけを拾う。ソフト名だけで連携方式を確定しない。名前や値はbriefing.jsonの `data_policy` に従う。

## 7. ヒアリング.md の書き方

お手本は `examples/sample-haisha/打ち合わせ資料/ヒアリング.md`。過去資料の質問文は当時の記録として保持し、新規作成ではcatalogの問いを使う。

| 欄 | 書き方 |
| --- | --- |
| 質問 | catalogのquestionをそのまま使う。追加要望は「<機能>を頼まれた」、未定の補足は確認対象が分かる問い |
| 回答 | 役割・対象・場面を短く書く。聞けた理由は次の1文。案と事実を混ぜない |
| 回答 (既定案) | 「案:」で始め、案件の言葉に合わせた仮案を書く。design_defaultの解説を回答済みの事実として写さない |
| 回答 (未定) | 「決まるまで <案>。<確認対象と確認先>」。案が作れなければ不明な対象・困ること・確認先を書く |
| 出どころ | 聞き取り / 素材:<ファイル名> / 既定案 / 未定 / 要望 |

H06には将来の候補と、将来のボードを足すかをまとめる。仕様書8章はここから書く。役割名は全資料で同じ言葉を使う。5章は未定のH行だけを箇条書きにし、Q番号は要件定義を書くときに付ける。

### 確認点で出た答えの書き方

followupでQに具体的な答えが出たら次のように反映する。

- 既存Hがあるときはその回答と出どころを更新する。未定が解消した場合だけ5章から該当行を除く。
- Hがないときは近い章の末尾に最後のH番号の次を足す。もとの番号は振り直さない。
- 案の選択でも、確認対象を理解して具体的に決めた答えなら `聞き取り`。単なる「全部おすすめ」は仮案のまま残す。
- 「打ち合わせで聞く」「わからない」「あとで」のQと選ばなかったQは変えない。
- 更新日を今日にし、答えが出たQとHの組を呼び出し元へ返す。文書への反映はrun-briefing-docsが行う。
