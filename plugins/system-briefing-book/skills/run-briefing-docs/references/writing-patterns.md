# 文書の書き方のお手本

要件定義.md と 仕様書.md の欄ごとの、文の型・長さ・お手本・悪い例と直した例。
見出しと表の列は [document-structure.md](../../../references/document-structure.md) が正本。ここは「中身をどう書くか」だけを決める。
お手本は主に `examples/sample-haisha/打ち合わせ資料/` から引いている。追加の記入例は仮の案と明記する。値は写さず、型だけをまねる。

## 番号の振り方

| 記号 | 振る順 |
| --- | --- |
| S | 最初の版の画面だけに振る。要件定義 5.2 これから で初めて出てくる順に S01 から。5.2 に出ない画面は、そのあとに 6 章の順で |
| F | 6 章で `○` の行を先に、`あとで` の行をあとに。`○` の行は 3.1 と同じ順 |
| D | しくみが覚えるものを、大きいもの → 中身 → 記録の順 (配車表 → 配車の行 → 書き出しの記録) |
| R | 働く順 (送ったとき → 読み取るとき → 確かめたとき → 書き出すとき) |
| Q | 素材を読んで分からなかったことを先に。そのあとに、ヒアリングの 未定 を出てきた順に (Q04 = H17 のように)。最後に、あとで に回した `要望` を |

## 要件定義.md

| 欄 | 文の型 | 長さ | お手本 |
| --- | --- | --- | --- |
| 1. 目的 | 「<今の手間>をなくす。」と「<変えないこと>は変えずに、<すること>だけで、<結果>になるようにする。」。3 文目は要るときだけ | 2〜3 文 | 手書きの配車表を、取り込み先のシステムへ打ち直す手間をなくす。 |
| 2. 今の困りごと | 「<いつ>、<何を>している。<どれくらい>かかる。」。数か回数を入れる | 3〜5 個 | 毎日、手書きの配車表を見ながら、取り込み先のシステムへ 1 行ずつ打ち直している。1 時間ほどかかる。 |
| 3.1 最初の版でやること | 「<どこで>、<する>」の短い句。主語は人かしくみ | 3〜5 個、1 個 20 字まで | スマホで撮って送る |
| 3.2 やらないこと | 「<やらないこと>。<代わりにどうなるか>。」。誤解されやすい範囲の外側を選ぶ | 2〜4 個 | 紙の配車表をやめること。紙は今までどおり書く。 |
| 4. 使う人と端末 | 主にすること は動詞で終える 1 句 | 役割ごとに 1 行 | 配車の担当者 / 2 / スマホ / 手書きの配車表を撮って送る |
| 5.2 これから | 「<誰>が、<何を>する (Sxx)。」。1 段 1 文、画面番号を括弧で。主語が前の段と同じなら省く | 3〜6 段 | スマホで撮って送る (S01)。 |
| 6. できること | `○` は 3.1 と同じ順・同じ動詞。`あとで` の行は 仕様書 8 章の候補と 1 対 1。`要望` から来た行は、終わりに `(要望:Hxx)` | `○` は 3.1 と同じ数 | 配車表を撮って送る / 照合の候補を出して選ぶ (要望:H37) |
| 7. 守ること | 「<観点>: <数か状態>。」。数が仮なら (例) | 4 行。量・止まったとき・使う時間帯の答えがあれば 7 行まで | 速さ: 写真を送ってから 1 分ほどで、一覧に読み取った行が並ぶ (例)。 |
| 8. 用語 | 「<何か>。<どこにあるか / 何のためか>」 | 1〜2 文 | モーダル / 画面の上に重ねて出す小窓 |
| 9. 決めること | 決めること は「〜してよいか」か「<何>の方法」。あとで に回した `要望` は「<頼まれた機能>を最初の版に入れるか (要望:Hxx)」。案 は おすすめの答え 1 つと、短い理由 | 1 行 | 「〃」は、上の行と同じ値として読んでよいか / 上の行の値を入れて、黄色で知らせる |

| 欄 | 悪い例 | 直した例 | 直した理由 |
| --- | --- | --- | --- |
| 2 | 業務が非効率である | 毎日 … 1 行ずつ打ち直している。1 時間ほどかかる。 | 場面と数が無いと、読む人が自分のこととして読めない |
| 3.1 | OCR による帳票データの自動抽出機能 | しくみが行ごとに読み取る | 専門用語と「〜機能」の名詞を使わない。動きで書く |
| 7 | 必要に応じて高速に応答する | 写真を送ってから 1 分ほどで、一覧に読み取った行が並ぶ (例)。 | 「必要に応じて」で終えない。数で言い切る |
| 9 | 〃の扱いについて検討が必要 | 「〃」は、上の行と同じ値として読んでよいか (案: 上の行の値を入れて、黄色で知らせる) | 問いの形にし、おすすめの答えを添える。打ち合わせで「はい / いいえ」で決まる |

## 仕様書.md

| 欄 | 文の型 | お手本 |
| --- | --- | --- |
| 1. ひとことで | 動詞で終える 1 句。20 字まで | 紙を撮って送る |
| 2.1〜2.8 | 共通値と例外を分け、必要な内容を省かず短い行で。「〜する」「〜を出す」で言い切り、画面に出る文字は「」で例を添える | 書き出す前の確かめだけに出す。「21 行を書き出しますか」のように、何が起きるかを 1 行で書く。 |
| 3. 目的 | 「<何を>して、<どこへ / 何のため>」 | 手書きの配車表を撮って、事務所に送る |
| 3. 開き方 | どこから、どう開くか | スマホのブラウザでアプリを開く (ホーム画面に置いておく) |
| 3. 項目の説明 | 何を入れるか。例外のときにどうするか | 紙の右上の日付。違うときだけ直す |
| 3. 操作の動き | 押すと何が起き、画面に何が出るか | 写真を送る。上に「送りました」と出て、しくみが読み取りを始める |
| 4. データの形 | 表の前の `1 件 =` は、数えるときの 1 つを名詞で。項目名は素材の列名どおり。例の値は `data_policy` に従う (`source` は素材の値、`masked` は素材の形をまねた例の値)。型の単位は [document-structure.md](../../../references/document-structure.md) の 4 章 | 1 件 = 配車表の 1 行 / 車番 / 文字 / ○ / 0215 / 素材:配車表_例.svg#1列目 |
| 5. 処理のルール | 「<条件>なら、<しくみが何をする>」 | 読み取りに自信がない欄は黄色にし、その行を確認待ちにする |
| 6. しくみと基盤 | 7行の方式は名詞句。実装詳細は表の後の本文ラベルへ。決まっていなければ「案: 〜 (Qxx)」。理由は読む人の得 | ログイン / 案: 会社の Google アカウント (Q04) / 新しいパスワードを覚えなくてよい |
| 7.1 見える範囲 | その役割が見られるデータの範囲を「<どれ>の<データ名>」で | すべての配車表 / 自分が送った配車表だけ |
| 7.2 運用 | 「<誰>が、<何を>する」か「<何を>するのは、<誰>。」 | 使う人を足したり外したりするのは、発注側の責任者 1 人。 |
| 8. 最初の版に入れないもの | [document-structure.md](../../../references/document-structure.md) の「次に広げる候補の書き方 (8 章)」 | 読み取りの学習: 選んだ候補を覚えて、次から候補の 1 番目に出す。 |

| 欄 | 悪い例 | 直した例 | 直した理由 |
| --- | --- | --- | --- |
| 3 操作 | 送信処理を実行する | 写真を送る。上に「送りました」と出て、しくみが読み取りを始める | 押した人に見えることを書く |
| 5 | OCR 信頼度が閾値未満の場合はフラグを立てる | 読み取りに自信がない欄は黄色にし、その行を確認待ちにする | 画面でどう見えるかまで書く |
| 6 理由 | スケーラビリティが高いため | 事務所に機械を置かなくてよい。外にいる人のスマホからも届く | 技術の良さではなく、使う人の得で書く |
| 8 備え | 備え: 学習用の画面を最初から用意しておく | 備え: 直す前の値を、行ごとに消さずに残す (D02)。 | 備えはデータだけ。最初の版の画面を増やさない |
| 8 時期 | 時期: 未定 | 時期: その先 | 時期は `次の版` か `その先` の 2 つ。相手しだいで見えないものは その先 |

仕様の詳細を短く記録する例 (架空の案。Q番号は案件の番号に置き換える):

- `配置: 2.1のPC配置を使う。本文の上に絞り込み、左に一覧、右に選んだ行の詳細を置く。スマホの順序は案としてQで確認する。`
- 操作表の `動き`: `右下の主なボタン。必須項目がそろうと押せる。押すと処理中になり連打を止める。成功で完了、失敗で入力を残して再試行できる。保存条件はR番号を参照。`
- `安全対策: 案として、各処理の入口で役割と対象データの範囲を照合する。画面で操作を隠すだけでは許可しない。方式と確認方法をQで決める。`

ラベルと記入範囲は document-structure.md の「実装へ渡す情報の記入先」に従う。共通の説明を各画面へ丸ごと複製せず、差分と参照先を残す。空ラベルやコメントは埋まった扱いにしない。規格上の記入と意味の充足は別で、レビューでは配置・操作・状態から同じ画面が作れるか、バックエンドの境界・安全対策・運用の未決点が特定できるかを確かめる。

## 書く前に確かめること

- 3.1 と 6 章の `○` と overview のボードが、同じ数・同じ順になっている。
- 6 章の `あとで` の行が、すべて 8 章の候補にある。
- 8 章の 備え で足したデータの項目が、4 章の表に「例」で置いてある。
- 8 章の 時期 の行は `次の版` か `その先` だけ。句点を付けない。

- 仕様書2・3章に画面区分/配置/ボタン/モーダル/アイコン/状態を残し、4〜7章に処理・データ・安全・基盤を記録する。未確定は案とQを残し、決定済みと混ぜない。
