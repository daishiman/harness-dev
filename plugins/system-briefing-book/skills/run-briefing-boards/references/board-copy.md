# ボードの言葉のお手本

ページの選び方、ファイル名と見出し、注記と画面の中の言葉の型。
型と部品の正本は [page-patterns.md](../../../references/page-patterns.md)。ここは「どのページを置き、何と書くか」だけを決める。
お手本は `examples/sample-haisha/打ち合わせ資料/` から引いている。future だけはお手本の案件に無いので、雛形 `assets/templates/board-future.html` から引いている。値は写さず、型だけをまねる。

## 画面のボード (02〜07) の置き方

1. 仕様書 1 章の画面 (= 最初の版の画面) を、1 枚に 1 つずつ置く。画面を外さない。
2. 並びは S 番号の順 (要件定義 5.2 これから で初めて出てくる順)。
3. 型は 仕様書の 端末 で決める。`スマホ` は phone、`PC` は pc。`スマホと PC` は、要件定義 4 章でその画面を主に使う人の端末にする。
4. 何枚まで置くかと、多いときの相談は [workflow.md](../../../references/workflow.md) の「既定のページ構成」を読む。

## ファイル名と見出し

| 型 | file の slug | title (h1) |
| --- | --- | --- |
| overview | `overview` | 全体図 |
| screen-map | `screen-map` | 画面の一覧と流れ |
| phone / pc | `s0N-<英語 1 語>` (s01-send、s02-list、s03-check、s04-export) | 仕様書の画面名そのまま |
| data-map | `data-map` | <素材の名前>の欄と画面の項目 (紙の欄と画面の項目) |
| mechanism | `mechanism` (2 枚目からは `mechanism-<英語 1 語>`) | <処理の名前>のしくみ (読み取りのしくみ、学習のしくみ) |
| future | `future` | 将来の広げ方 |

- kicker は雛形が入れる (mechanism で 8 章の候補を描くときだけ書き換える。[page-patterns.md](../../../references/page-patterns.md) の mechanism)。lead は雛形が briefing.json の `message` から入れる。lead と message は同じ文のままにし、直すときは両方を直す。
- data-export の名前は file の slug と同じにする (`s01-send` → `assets/export/s01-send.png`)。

## message (そのページで伝えること)

伝えることは 1 つ。文は 2 つまでにし、2 文目は 1 文目の補足 (楽になる所、先の見通し) にする。3 文になるなら、ページを分けるか片方を捨てる。

| 型 | 文の型 | お手本 |
| --- | --- | --- |
| overview | 「<変えないこと>は変えずに、<すること>だけで、<結果>。」 | 紙の書き方は変えずに、撮って送るだけで、取り込み先のシステムへ渡せるようにする。 |
| screen-map | 「画面は N つ。<端末>で<する>、<端末>で<する>。」 | 画面は 4 つ。スマホで送り、PC で確かめて書き出す。 |
| phone / pc | 「<その画面ですること>だけ。<楽になる所>。」か、するときの見どころを 1 文 | 紙を撮って送るだけ。入れるのは日付だけで、それも最初から入っている。 |
| data-map | 「<素材>のどの欄が、<どこ>に入るか。」 | 紙のどの欄が、画面とデータのどこに入るか。 |
| future | 「今は<操作>、次の版では<新しい操作や結果>。」 | 今は候補を選び、次の版では前に選んだ候補が先頭に出る。 |

## 注記

| 種類 | `<b>` (20 字まで) | `.sub` (1〜2 文) | お手本 |
| --- | --- | --- | --- |
| can | 使う人ができること、変えなくてよいこと | どうなるか。使う人の得 | 紙を撮るだけ。書き方は今のまま / 1 回に 1 枚。写りが悪いときは「撮り直す」。 |
| how | 操作後にどう変わるか | 人から何が見えるか。内部実装は省く | 「送る」で、しくみが読み取りを始める / 上に「送りました」と出る。1 分ほどで、事務所の一覧に並ぶ。 |
| ask | 要件定義 9 章の 決めること を短く | 「案: <9 章の案>。<なぜか、どう確かめるか>」 | 「〃」は上の行と同じか / 案: 上の行の値を入れて、黄色で知らせる。人が見て確かめる。 |

- 番号は画面の上から下、左から右の順。ask も、指す場所の順に入れる。
- phone / pc は can を中心に、mechanism は how を中心に。1 枚で 3 種類をそろえなくてよい。
- `ask` の `.q` には 9 章の Q 番号。9 章に無い話は注記にせず、先に 9 章へ足してもらう。誰に聞くか が「決定 (<版>)」の Q は ask にせず、決まった中身を画面に描く。

| 悪い例 | 直した例 | 直した理由 |
| --- | --- | --- |
| OCR エンジンで自動認識 | 送ると「読み取り中」、終わると「確認待ち」になる | 画面に出る状態で説明する ([plain-language.md](../../../references/plain-language.md)) |
| UX を向上させる | どの画面も、主な操作は 1 つだけ | 何がどう良いかを、画面で見える形で書く |
| 要検討 | 案: 取り込み列の見本と同じ並び。試して決める。 | 案が無いと、打ち合わせで答えが出ない |

## 画面の中の文字 (phone / pc)

- ボタンの文言と項目名は、仕様書 3 章の 操作 と 項目 から 1 文字も変えない。
- 主なボタン (`.btn-primary`) は 1 つ。仕様書の操作の表で、次の画面へ進むか しくみを動かす操作を選ぶ。
- 人や会社の名前、日付や数は、briefing.json の `data_policy` に従う。`source` は素材のまま。`masked` は「配車 A さん」「取引先Y」のような役割の名前と、素材の形に合わせた例の値。表は [quality-rules.md](../../../references/quality-rules.md) の「名前と値の扱い (data_policy)」。

## screen-map

- タイルの文は 仕様書 1 章の「ひとことで」、`.act` は「主な操作: <主なボタンの文言>」。
- タイルの絵は、各画面のボードの切り出し (`assets/export/<slug>.png`)。
- 矢印の上の言葉は、次の画面へ進むボタンの文言そのまま (送る、開く)。メニューで移るときは「メニュー」と書き、how の注記で説明する。

## data-map

- 列の区分の棒の `.seg` は「<区分の短い名前> <列の数>」(紙から 9、しくみ 3、決める 1)。
- `.legend` は区分の名前そのまま (紙から読む / しくみが入れる / いつも同じ値 / 空欄のまま / 決めること)。

## future (置くときだけ)

- 段の `.chip` は「今つくる / 使ってみてから / 相手のソフトしだい」。仕様書8章の時期と同じにする。
- 候補は名前・利用者の操作・見える結果だけを書く。備えのデータ項目・保持方法・連携方式は仕様書8章を参照する。
- 最初の版の画面・ボタンを、将来の候補のために増やさない。

## 仕様書との分担

- ボードの配置・主なボタン・モーダル・アイコン・状態は仕様書2・3章と合わせる。管理画面/ユーザー画面/共用の区分は利用者が分かる形で示す。
- 一覧の件数、処理中、押せない理由、成功/失敗、次の操作を優先する。意味のない飾りのアイコンは足さない。
- サーバーの構成、認証の内部手順、保存や監視の実装はボードへ移さない。仕様書4〜7章に保持し、必要な根拠だけ節番号で示す。
- 仕様が足りなければ、足りない章と画面番号を呼び出し元へ返す (書き足すのは run-briefing-docs)。ボード担当が未知の内部動作や製品を決定しない。
