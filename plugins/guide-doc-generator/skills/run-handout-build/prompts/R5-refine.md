## Layer 1: 基本定義層

### 1.1 不変ルール

- 指摘が返るまでこの責務を始めない。こちらから周回を回さない。
- ヒアリングをやり直さない。覆った項目だけを更新する。
- 資料全体の粒度を上げない。粒度を上げるのは利用者が指した箇所だけである。
- 生成済み HTML を直接編集しない。直すのは構成データであり、HTML は必ず
  R3-render の決定論経路で作り直す (OUT2 の byte 一致が壊れるため)。
- 反映の判断基準は `config/handout-visual-policy.json#content_selection` に従う。
  指摘への対応が「項目を足す」形になるときは、同時に何を落とすかを決める。

### 1.2 倫理ガード

- 指摘を要約して解釈し直さない。「つまりこういうことですね」と言い換えた時点で、
  利用者が実際に指した箇所が見えなくなる。指摘は原文のまま扱う。
- 指摘されていない箇所を「ついでに」直さない。ついでの修正は差分を追えなくし、
  次の指摘が前回の修正のせいなのか元からなのか判別できなくする。
- 仮置きが覆ったときは、覆ったこと自体を報告する。黙って差し替えると、利用者は
  自分の指摘が反映されたのか元からそうだったのか分からない。

## Layer 2: ドメイン定義層

### 2.1 責務

- 担当: 指摘の受理、差し戻し先の判定、覆った仮置きの更新、再生成の起動、
  変更点の提示。
- 非担当: 構成データの設計 (C05)、値の妥当性判定 (C12)、資料の生成 (C11)、
  ゲートの集約 (C09)。

### 2.2 ドメインルール

- 1 件の指摘に対して差し戻し先は 1 つに決める。複数責務へ同時に投げない
  (どの変更がどの指摘に対応するのか追えなくなる)。
- 第1稿で回さなかった工程 (`config/handout-visual-policy.json#draft_first.skipped_in_draft`
  に挙がる挿絵生成と可読性レビュー) は、この周回から回してよい。現物が出た後に
  初めて効く工程だからである。
- 決定論ゲート (C16/C17/C18/C22) は毎周回そのまま通す。数百ミリ秒で終わるため、
  推敲のたびに検査を省く理由がない。
- 反映後も図解密度と散文量の警告は 0 件でなければならない。指摘に応えるために
  散文を足して警告が復活したなら、それは応え方が間違っている。

### 2.3 差し戻し先の判定

差し戻し先は「その指摘で**どのフィールドが変わるか**」だけで決める。指摘の口調や
大きさでは決めない。

| 指摘の種類 | 変わるフィールド | 差し戻し先 |
|---|---|---|
| 仮置きの値が違う (読者・到達レベル・覚えてほしいこと等) | `hearing_result` の 1 項目 | R1-elicit (当該項目のみ更新)。項目が変われば構成も変わるため、続けて R2-design へ流す |
| ここはもっと詳しく / ここは削って | 当該 section の `detail_level` と parts の中身 | R2-design。資料全体の粒度は動かさない |
| この節は要らない / 順番を変えたい / 図解にしてほしい | sections の構成・parts の種別 | R2-design |
| 文字が小さい・色が読みにくい・印刷が崩れる | 構成データは変わらない | R3-render (テーマと描画の問題)。構成データを触らない |

判断に迷う 2 点を先に決めておく。

- **「もっと詳しく」を R1 へ戻さない**。詳しさは `detail_level` であって、ヒアリング
  項目ではない。ここを R1 へ戻すと再ヒアリングになり、1.1 の不変ルールと矛盾する。
- **仮置きが覆ったときだけ R1 へ戻る**。このとき戻すのは覆った 1 項目だけで、
  他の項目を聞き直さない。更新した項目は `resolved_provisional` として報告する。

どの行にも当てはまらない指摘は、勝手に近い行へ寄せず `unaddressed` へ載せて
利用者に聞く。寄せた時点で、指摘と違うものが直る。

### 2.4 入力契約

| field | required | 説明 |
|---|---|---|
| feedback | yes | 利用者の指摘。原文のまま |
| config_path | yes | 第1稿の構成データ |
| out_dir | yes | 第1稿の出力先。同一バンドルへ上書きする |
| provisional_fields | yes | 第1稿で仮置きした項目の一覧 |

### 2.5 出力契約

- `changed_fields` — 更新した構成データのフィールドと、変更前後の値。
- `resolved_provisional` — 指摘によって確定へ変わった仮置き項目。
- `unaddressed` — 反映しなかった指摘と、その理由。空配列でもよいが省略できない。
- `rerun_scope` — この周回で再実行した責務の一覧。

## Layer 4: 共通ポリシー層

### 4.1 失敗時

- 指摘の意図が読み取れない場合、推測で直さず 1 問だけ聞く。推測で直すと、次の
  周回で「そこじゃない」と言われて 1 周まるごと無駄になる。
- 反映すると他の指摘と矛盾する場合は、反映せず `unaddressed` へ矛盾の内容とともに
  載せる。片方を黙って優先しない。

### 4.2 観測

- 何周目の指摘か、どの責務へ戻したかを記録し、ゴールシークの中間記録へ残す。

### 4.3 セキュリティ

- 出力先バンドルの上書きは C19 の解決に従う。構成データの sha256 が変わる以上、
  別ディレクトリが切られることがある点を報告に含める。

## Layer 5: エージェント定義層 (ゴール駆動の実行主体)

### 5.1 担当 agent

- 本 skill 自身 (inline)。設計のやり直しが要る指摘のときだけ C05 へ委譲する。

### 5.2 ゴール定義

- 目的: 利用者が現物を見て言葉にした指摘を、最小の差分で資料へ反映する。
- 背景: 利用者が本当に直したい点は、質問に答えている段階ではなく現物を見た段階で
  初めて言葉になる。だから第1稿は確定を待たずに出し、精度はこの周回で取り戻す。
- 達成ゴール: 指摘した箇所だけが変わり、それ以外が変わっていない資料が出ている状態。

### 5.3 完了チェックリスト (ゴール到達の停止条件)

- [ ] 全ての指摘が `changed_fields` か `unaddressed` のどちらかに載っている
- [ ] 指摘されていない箇所を変更していない
- [ ] 覆った仮置きを更新し、覆ったことを報告に含めた
- [ ] 資料全体の粒度を上げていない (指された箇所だけを上げた)
- [ ] 図解密度・散文量の警告が 0 件のままである
- [ ] 決定論ゲートが全て exit0 で、OUT2 の再現一致が保たれている

### 5.4 実行方式

- 指摘を 1 件ずつに割り、それぞれの差し戻し先を 2.3 の対応表で決める。
- 同じ責務へ戻る指摘をまとめて 1 回で反映する。責務ごとに 1 周する。
- 反映後は R3-render 以降をそのまま通し、変更点だけを提示する。

## Layer 6: オーケストレーション層

### 6.1 上位接続

- 呼び出し元: run-handout-build のゴールシークループ (第1稿の提示後)
- 差し戻し先: R1-elicit (項目の更新) / R2-design (構成の作り直し) / R3-render (再生成)
- 後続: R4-verify。周回のたびにゲートと出力先ルーティングを通す。

### 6.2 並列性

- 単発。同一資料に対して複数の周回を並行させない。

## Layer 7: UI / 提示層

### 7.1 提示形式

- 変更点だけを差分として示す。資料全体を再掲しない。
- 反映しなかった指摘は理由とともに明示する。黙って落とさない。

### 7.2 言語

- 日本語 (フィールド名は英語)。

## 出力指示

指摘を原文のまま受け取り、1 件ずつ差し戻し先を決めて最小の差分で反映する。
更新したフィールド、確定へ変わった仮置き、反映しなかった指摘と理由、再実行した
責務の一覧を返す。
