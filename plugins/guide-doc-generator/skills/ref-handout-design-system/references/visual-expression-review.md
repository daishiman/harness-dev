# 図解の意味と見た目の確認

実行規則・閾値の正本は `config/handout-visual-policy.json`、候補と入力形は
`config/handout-diagrams.json`。本書は独立レビューで使う問いを持つ。

| 観点 | 読み手として確認すること | 不成立の例 |
| --- | --- | --- |
| 図の必要性 | 文章の関係が図で速く掴めるか。文章だけに有利な関係を残していないか | 先頭に挿絵があるだけで、分岐条件を長文にする |
| 主張 | この図で何を判断するかが一文で言えるか | 図種の名前だけが題で、結論が分からない |
| 関係 | 主体・対象・方向・条件・単位・時間が説明と一致するか | 独立した選択肢を時間順のフローにする |
| 接続 | 線の始点と終点が箱の辺へ届き、矢頭が接続先を指すか | 空中で切れた線、箱を貫通する線、浮いたノード |
| 分岐と合流 | 出口条件が区別でき、回収する成果物が分かるか | 全出口が同じラベル、合流点の意味が不明 |
| 数値 | 根拠・分母・単位・軸・期間があるか | 架空の増加率、面積が実測と見える概念図 |
| 配置 | 一方向に追えるか。ラベルと線、文字と箱が衝突しないか | 交差線の接続が曖昧、凡例だけ遠く離れる |
| 文字 | 実表示で本文と同様に読めるか。小さくして無理に詰めていないか | 図全体の縮小、長いラベルの欠落、セル外へのはみ出し |
| 色 | 資料のテーマと一貫し、同じ色が同じ意味を担うか | 節ごとの別パレット、淡色同士、色だけの正誤表示 |
| 操作 | キーボードでも図内を移動・拡大・閉じる操作ができるか | マウスのみ、閉じ方が不明、フォーカスが背景へ逃げる |
| 詳細 | 閉じても主張と次の行動が通じ、summaryで中身を予測できるか | 必須の判断条件を隠す、全項目が「詳細」 |
| 重複 | 図・挿絵・表・本文がそれぞれ別の情報を担うか | 図の全ラベルを同じ順で本文に再掲する |

図種の例から選択を始めず、原文から主張と関係を抽出して候補を比較する。
たとえば「小さい依頼は直接頼む。大量の調査は任せる。繰り返す仕事は専用化する」は
順次に実行する三工程ではない。比較カードか条件つきの判断図が候補になる。
一方「依頼を送る→担当が処理する→結果を返す」は順序を持ち、担当間の受け渡しが
主題ならシーケンス、操作順だけが主題ならフローを選べる。

不適合は `visual-fit`、文章だけに関係が残る場合は `concreteness`、図と文章の
重複や情報過密は `card-granularity` / `sentence-flow` の既存軸で指摘する。
未接続や欠落で意味を誤解する場合は high。意味は通るが読み返しが必要なら medium。
機械検査が既に報告した同一欠陥を意味レビューへ再掲しない。

HTMLとSVGのソースだけでは重なりや実際の文字サイズを確定できない。表示確認が
できなかった場合は共通の `visual-evidence-contract.md` に従い、その面を `not_reviewed` の
`reason_code: display_unavailable` へ理由つきで残す。構文が通ったことを
見た目の合格へ読み替えない。

Mermaid・PlantUML等の専用描画では原文に対応するソースも残し、SVG/PNGとして事前に
描画して `IMG` へ接続する。クラス図やER図の多重度など、ネイティブの関係図で保持
できない意味を箱と矢印へ黙って落とさない。描画・素材埋め込み・自己完結検査を通す。
